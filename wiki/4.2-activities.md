## Overview

Activities are the deterministic boundary of the Temporal worker. Everything the workflow isolate cannot do — call a language model, drive Docker, talk to GitHub or Slack, read and write PostgreSQL — happens inside an activity, and the interpreter reaches them only through proxies. The directory holds 114 files, 61 of them non-test, and every activity a workflow may invoke is re-exported from one barrel at [packages/worker/src/activities/index.ts](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/index.ts). Several modules are in-process helpers that registered activities call directly: `runAgent`, `allowedPaths`, `agentRunFinalize`, `scheduledFireAuthorization`, `standaloneGateRunner`, `utils` and `workspace`. The tables below mark them, and the barrel is the arbiter of what is registered.

The catalog groups the modules by concern. Four conventions recur across them:

- An `AgentTracer` is persisted in a `finally` block so a failed attempt still leaves trace rows, and any workspace a module provisions is destroyed in the same `finally`.
- A call to a language model that fails leaves a trace row too, attributed to the model that was bound and priced from whatever usage had already been recorded. The reviewers, the security gate, the planner and decomposer, the merge-conflict resolver, the evaluation judge, `commitToMemory` and `runAgent` all do this.
- An activity that builds a repository reference loads the row with its `installation` relation, selecting both the installation id and its host, because `toRepoRef` needs both to pick the right credential.
- An activity whose workflow keeps no run row (authoring, scheduled evaluation, lesson consolidation, dependency inference) runs inside `withSpendOwner`, so its trace rows carry the team and organization the spend belongs to, and its budget is the runless token cap summed from those rows.

Workspace mechanics, agent and model resolution, tracing and cost accounting, the implementer runtime seam, agent runs and the model catalog are boundaries this page cites and does not cross — see [Docker Workspaces](./4.4-docker-workspaces.md), [Agent Layer](./4.3-agent-layer.md), [Observability and Cost](./4.5-observability-and-cost.md), [Agent Runs and Implementer Runtimes](./4.6-agent-runs-and-implementer-runtimes.md) and [Model Catalog and Pricing](./4.7-model-catalog-and-pricing.md). Who may reach a repository, and whose token an activity acts with, is covered in [Repository Access and Credentials](./3.4-repository-access-and-credentials.md).

## The software-engineering path

```mermaid
flowchart TD
    VC[validateContext] --> PD[planDecomposition]
    PD --> EI[executeImplementation]
    EI --> MB[mergeBranches]
    MB -->|conflict| RMC[resolveMergeConflict]
    EI --> QG[runLint / runTypecheck / runTests / runBuild / runVulnScan / runPerfBench]
    QG -->|failed| GF[executeGateFixImplementation]
    GF --> QG
    EI --> RN[runReviewNetwork]
    RN -->|rejected| RF[executeReviewFixImplementation]
    RF --> RN
    RN -->|approved| PR[createOrUpdatePullRequest]
    PR --> CI[waitForCiByPolling]
    CI -->|failed| CF[fetchCILogs then executeCIFixImplementation]
    CF --> CI
    CI -->|passed| CM[commitToMemory]
```

The diagram is a composite of the engineering activities, not one template. The default engineering specification wires validation, implementation, the review loop, the pull request, the continuous-integration wait and fix loop, and memory; the quality gates and the decompose-and-merge steps are wired by the gate and decomposition example specifications, and the code-and-CI template wires gates straight into the pull request and CI loop. The routing between them is always the interpreter's, not an agent's. Every fix arrow re-enters through the same shared session described below, so a gate fix, a review fix, and a continuous-integration fix push through identical scanners.

The templates are written with authoring helpers (`reviewLoop`, `ciLoop`, `openPullRequest`) that expand into flat nodes. The review and continuous-integration retry limits are therefore not values the activities read: each helper takes a `limit` that defaults to three and writes it into a condition node (`context.reviewRetries >= 3`, `context.ciRetries >= 3`), and the interpreter applies it.

## Context gathering and validation

| Activity | Does | Inputs → outputs |
| --- | --- | --- |
| `validateContext` | Runs the tool-free `validateContext` agent to extract success criteria, then upserts a `ContextSnapshot`. An LLM failure degrades to empty criteria rather than failing the run, and the degradation is logged and recorded as a `context_validation.degraded` trace event, because an empty list silently switches off the domain-logic reviewer's criteria check. A cancelled activity stops instead of persisting. | `RunRequest`, optional prompt override → `{ contextSnapshotId, successCriteria }` |
| `resolveWorkspace` | Materialises the workspace context for a run by connection type: git repository identity, document or record locator, issue-tracker handle, or an empty `api_only` context. A git repository's clone URL is built from its own host override, or from the instance's configured host when it has none, never from a hard-coded github.com. | `{ workspaceProvider, connectionId, payload }` → tagged `WorkspaceContext` union |
| `readSource` | Connection-parameterised read. Notion, Zendesk and issue-tracker connections are read for real; a `git_repo` returns a pointer the engineering path already covers; `http_api`, `hubspot`, `mcp` and `slack_workspace` return a placeholder. | `{ connectionId, query }` → `ReadSourceResult` |
| `detectRepoDependencies` | Deterministic cross-repo edge detection from manifests, `CODEOWNERS` and `.gitmodules`; writes resolved edges plus unresolved suggestions. Each candidate repository carries its host, so a dependency URL naming a host matches only the repository on that host. | `{ repoId }` → `{ edgesUpserted, scanned, suggestions }` |
| `inferRepoDependencies` | Language model proposes likely cross-repo edges from repo metadata, written as `proposed` unless confidence clears the auto-promote threshold. Its spend is attributed to the subject repository's team. | `{ repoId }` → `{ proposed, autoPromoted }` |
| `getReposForDependencyScan` | Deployment-wide sweep listing active git connections for the scheduled dependency scan. | none → `RepoForDependencyScan[]` |

## Planning and decomposition

| Activity | Does | Inputs → outputs |
| --- | --- | --- |
| `planDecomposition` | Calls the decomposer persona with its resolved skill fragments and returns the subtask list for per-branch fan-out. It runs, is priced and is traced as `decomposer`, which inherits the planner's model. | `RepoWorkRequest` → `DecompositionResult` |
| `planEpic` | Decomposes a multi-repository epic into per-repo entries, then unions the planner's guessed ordering with the durable dependency graph, dropping any edge that would close a cycle. | `EpicPlanRequest` → `EpicRepoEntry[]` |
| `analyzePrd` | Judges a product requirements document for engineering readiness and lists gaps. | `RepoWorkRequest` → `PrdAnalysis` |
| `decomposePrd` | Breaks the document into epics and stories with acceptance criteria and story points. | `RepoWorkRequest` → `PrdDecomposition` |
| `createTrackerItems` | Best-effort creation of tracker epics and stories from the decomposition. | decomposition → `{ createdItems, failedCount }` |
| `submitPrdWorkRequests` | Starts one runnable workflow per approved story. Workflow ids come from the shared allocator, which qualifies the id with the repository's host and checks the host-less form a run may already be in flight under; a story whose ticket already has a run in flight is skipped, and a repository with no owner or name is skipped. When per-user credentials are enabled, every story carries the PRD run's `launchedById`. | decomposition → `{ workRequestIds }` |
| `planChannelTask` | Splits a general channel task into at most four parallel subtasks. | `{ task, … }` → `{ subtasks, subtaskCount }` |
| `runChannelSubtasks` | Executes those subtasks with a worker pool of three and synthesises one answer. A refusal because the channel's model has no price is the answer to the whole task and propagates rather than being swallowed as one blank branch. | subtasks → synthesised text |

The planner and decomposer leave a failed-call trace row whenever their call throws or returns unusable output, and both refuse an unpriced model under a USD cap before calling it. That is observability and budget policy, covered in [Observability and Cost](./4.5-observability-and-cost.md); the activity contract above is unchanged. The PRD activities heartbeat while their model call runs, which is also how a cancellation reaches them.

| --- | --- | --- |

## Quality gates

Six gate activities share one runner. Command resolution is strictly first-match: the step node's `config.command`, then the connection's `gateCommands` override, then the built-in default. The runner never throws on a non-zero exit; it returns `passed: false` and lets the interpreter apply the node's failure policy. When no command resolves anywhere the gate returns `passed: true` with a no-op summary, so the specification, not the activity, decides whether a missing command matters. A gate that cannot check its branch out from origin throws instead, so the activity retries: running the gate against the default branch would report a change it never inspected as green.

| Activity | Default command | Artifact kind |
| --- | --- | --- |
| `runLint` | `yarn lint` | `gate.lint` |
| `runTypecheck` | `yarn typecheck` | `gate.typecheck` |
| `runTests` | `yarn test` | `gate.tests` |
| `runBuild` | `yarn build` | `gate.build` |
| `runVulnScan` | `yarn npm audit --severity high` | `gate.vuln` |
| `runPerfBench` | none; operators must supply one | `gate.perf` |

Each returns `{ passed, summary, artifactId, exitCode, signal?, command? }`; `command` is the command that actually ran after resolution, so a gate fix re-runs exactly the check that failed. Full output goes to a `WorkflowArtifact`; the inline summary is truncated to four kilobytes on character boundaries so it fits the metadata cap on `workflow_steps`. `runGateStandalone` in [packages/worker/src/activities/standaloneGateRunner.ts](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/standaloneGateRunner.ts) is the same execution without the Temporal or work-request coupling, used by the offline evaluation harness against a pinned commit.

The gate-fix path is the only one with an `afterGenerate` hook: it re-runs the failed gate inside the workspace, using the command the failed gate reported, and folds the outcome into the implementation notes, while tests still run afterwards as a regression check so a fix that silences the gate but breaks tests is caught.

`resolveMergeConflict` is the one fix activity that does not go through the shared session. It has its own workspace and replays the unmerged tail branch by branch. The resolver agent never runs git: the activity lists the conflicted paths once with `git diff -z`, runs the resolver, then checks each conflicted file for a leftover conflict marker (a line opening or closing a hunk, never the bare `=======` separator, which is also a Markdown heading underline). It stages exactly the conflicted paths, confirms git holds no unmerged path, and commits. After every branch has resolved, the diff of what the resolver wrote is put through the code-security scan and the blocking security gate before the target is pushed, so a critical finding never reaches the remote branch. A lesson is recorded through the time-capped background writer when every branch resolved. The resolver calls are traced and priced under the `mergeConflictResolver` role, and a call that throws leaves a failed-call row.

The retired-installation and scheduled-fire checks live inside `createWorkflowRun` rather than as new activity calls because the workflow's command sequence is replayed against committed history fixtures, and an added call would break every one of them. The scheduled-fire refusal is thrown, not returned as an `{ error }`: a returned error becomes a plain workflow error that Temporal retries forever, which under a skip-overlap schedule would swallow every later fire. The retirement check is also the one access condition a deferred run re-reads when it actually starts, since it needs no user; the requester's repository access was decided when the task was created.

## Identity and repository access inside activities

Several mechanisms in this directory decide whose authority an activity acts with or whether it may act at all. The enforcement rules themselves are in [Repository Access and Credentials](./3.4-repository-access-and-credentials.md); this section is only where they surface in activity code.

| Mechanism | Where | What it does |
| --- | --- | --- |
| `syncRepoAccess` | registered activity, started by a scheduled workflow with no arguments | Materialises GitHub permission answers into the access projection so listings read rows instead of calling GitHub. Walks each active repository's owning-team and shared-team members once each; narrowed by optional `connectionId` and `userId`. A member with a saved credential is asked through that token, others through their recorded login. |
| Login ownership check | inside `syncRepoAccess`, once per user | Verifies each stored GitHub login still names the account it was stored for, asking the host the stored account id belongs to with that host's own platform credential, and clears one that has been re-registered or has no linked account. A host with no credential to ask with is unverifiable and nothing is cleared; the sweep logs the hosts it could not authenticate. Counts clearings in `reassignedLogins` and `unlinkedLogins`. |
| Launcher identity | `createWorkflowRun`, `submitPrdWorkRequests`, and the SCM provider | `createWorkflowRun` writes `launchedById` and the Temporal run id on the run row. Activities read it through `currentRunLauncherId()`, which returns null unless the row belongs to this execution, so a re-used workflow id never inherits an earlier launcher. `submitPrdWorkRequests` copies it onto every story it starts. |
| Scheduled-fire authorization | `createWorkflowRun` → `assertScheduledFireAuthorized` | A schedule's fire starts the workflow with no gateway route in front of it, so the launch decision is taken again at the fire for the schedule's acting user: the schedule is active and has an active user to run as, the repository is active and still owned by or shared with the schedule's team, the repository access gate allows that user, the user is still a member of the organization (an administrator is exempt), and the organization is under its monthly cap. A refusal is a non-retryable `SCHEDULED_FIRE_REFUSED` that names the reason and is audited once an hour per distinct refusal; restoring access resumes the schedule with no other action. |
| Channel code-task gate | `createChannelCodeTaskRun` | Applies the Slack repository access decision for the requester before any run row exists. |

`syncRepoAccess` never overwrites an answer with a failure: a lookup that could not be made leaves the previous row and its `checkedAt` in place, so the row ages out through the staleness window instead of becoming a denial GitHub never issued. Because the activity runs from a schedule with no run row, its trace persists nothing; the operator-facing signals are log lines, which is why the ownership-takeover case is logged rather than only traced.

The channel gate is consulted only when the access gate is on. With the gate off, an `@mention` still needs no linked account; under advisory mode the decision logs what it would refuse without refusing. Its advisory logger is wrapped so that a failing log line can never be the reason a task does not start. The general channel route is untouched in every mode, since it answers questions and needs no identity.

The credential choice itself is not made in these activities. Any activity that builds a repository reference and calls `getScmProvider` acts as the launcher when per-user credentials are enabled and the launcher saved a usable token, and as the platform otherwise; an unreadable saved credential fails non-retryably as `CREDENTIAL_UNREADABLE`.

## Deep dive: executeImplementation

The activity starts by refusing a model that has no price when a USD cap is watching the call, before a clone or a container exists. It then loads the repository row with its installation, builds the clone credentials from that reference, and provisions a workspace on `<branchPrefix>/<ticketId>`, or on `<featureBranch>/<subtaskId>` when a subtask is supplied. It captures the base commit for the historical-replay tier before any work begins. On a Temporal retry it first fetches and hard-resets to whatever the previous attempt pushed. This matters because the activity can fail after its push — during the diff read, the scanners, or the security gate — and workspace creation always cuts a fresh branch from the default branch, so an unsynchronised retry would rebuild the change from scratch and have its push rejected as non-fast-forward.

When the step sets `allowedPaths`, the activity starts a path guard at that point, after any retry sync and before any agent turn. The guard reads two commit shas from the worker's own side, never a ref the agent could move. After the commit it pins the committed sha once and compares that commit's tree against the session's starting tree; a change outside the allowed paths fails non-retryably before the push. What is pushed, reported as the diff and returned as `headSha` is that same commit. A step with no `allowedPaths` runs the commands it always ran.

The repository's configured `gateCommands.runTests` is the test command when it is set; otherwise the command is guessed from `package.json`. The runtime that drives each turn is chosen from the `workspace.implementerRuntime` setting, and the prompt suffix that carries skill fragments comes back from that choice, since the Mastra loop discloses skills through a tool and the harness takes them inline. Before the loop the activity assembles the system prompt from four best-effort blocks, each wrapped so a failure degrades to an empty string rather than blocking implementation: those skill fragments, lessons retrieved from past workflows by semantic similarity, a bounded rendering of any referenced Figma design, and the active one-hop cross-repo dependency graph. Only the cross-repo block has an optional second tier that also clones upstream repositories into the workspace, and it is opt-in.

The test-driven loop runs at most `maxTddIterations` times. That bound is not a constant in this file: it comes from the `WorkflowDefaults` singleton resolved at the top of the activity, which falls back to five when the row is unset, so an operator raises or lowers it from the administration interface without a deployment. Each iteration checks for cancellation, checks the budget, and hands the previous iteration's test result, folded into the user message, to `runImplementerTurn`; then it runs the detected test command with stderr folded into stdout and parses the output together with the exit status. A pass needs a zero exit and evidence that tests ran — a parsed count of at least one passing test and no failures, or a runner line such as `ok <package>` — so a suite that exits zero having tested nothing does not stop the loop. The loop breaks on the first passing run; otherwise it exhausts the bound and the implementation notes say so.

The other bounds in this area resolve from different places. The evaluation harness reads `maxEvalIterations` from the same singleton, defaulting to three, once per case and arm. `resolveMergeConflict` takes `maxAttemptsPerBranch` from its input, which the interpreter binds from the step's inputs or config, and floors anything that is not a finite number of at least one to one. Within a single turn the model's tool steps are capped by the `workspace.agentMaxSteps` setting (default 50, between 5 and 500), resolved with the agent and passed to whichever runtime drives the turn. An agent run clamps its own step and wall-clock caps to the `workspace.agentRun*` ceilings. A workflow that keeps no run is held to the `workflow.runlessMax*Tokens` caps. The review and continuous-integration retry limits are not activity values at all: they are condition nodes the authoring helpers write into the specification, applied by the interpreter, and the fix session runs the agent exactly once per call.

After the loop the activity stages everything, commits only when something is staged, checks for cancellation, and pushes. It then reads the diff against the default branch, always quoting the operator-editable default branch name so it cannot smuggle shell syntax into the container. Two scans follow, and their behaviour differs by design. The static code-security scan is advisory: its findings ride along on `CodeResult.codeSecurityFindings` for the security reviewer to weigh, and a scanner that cannot run degrades to no findings rather than aborting a run that has already pushed. The model-driven security gate is blocking, and is covered below. The `finally` block closes any MCP client, persists the trace, best-effort stamps the baseline commit, and destroys the workspace.

## Deep dive: the shared fix session

The three fix activities are wrappers around one function, `runImplementerFixSession`. Each supplies a mode, an agent key, a default system prompt, a commit message, a cost-event name, a notes builder, and a mode-specific payload merged into the user message alongside the last twenty kilobytes of the previous diff. The review fix additionally forwards `allowedPaths`.

The session runs as the persona named by the agent key. Its Agent row supplies the system prompt, tools, skills and MCP binding, and, through `inheritsModelFrom`, the model, so a persona can override the implementer's model without a code change. The usage is attributed to that key and the trace persists under it. The session refuses an unpriced model under a USD cap first, before it has a workspace.

It resolves the target repository from the identifier stamped on the previous result, falling back to a branch-name lookup only for results that carry no repository identifier; both paths load the installation relation, because a repository in another GitHub organization would otherwise be cloned through the default installation and fail as if it did not exist. It fetches and hard-resets to the remote branch head, because workspace creation clones the default branch and does not carry the implementer's pushed commits. When the session is guarded, its path check is measured from the branch tip it started from, and the whole change is reported against the original run's base when the previous result carries one, which the session then carries forward. It runs the agent once rather than in a loop through `runImplementerTurn`, then runs tests as a regression check. It applies the same two diff scanners and the same blocking security gate as the initial implementation path, so no fix commit reaches the pull request unscanned. In its `finally` the trace persistence starts before the workspace is destroyed and is awaited after, so teardown does not wait on the trace write.

## Deep dive: the review network

`runReviewNetwork` resolves the three personas in parallel — `securityReviewer`, `domainLogicReviewer` and `performanceReviewer` — each by its own Agent key, so each carries its own prompt and skills and inherits the `reviewer` model unless its row sets one. The parent `reviewer` row is resolved too, but only its prompt is read, and only when an administrator has customised it. That row is seeded with the domain-logic prompt, so handing it to every persona would make all three review domain logic; it is treated as customised only when it differs both from the built-in constant and from the domain persona's row. Each persona's base prompt is then chosen most-specific first: its own customised row, then a customised parent prompt, then its seeded text, then the built-in constant. A step-level prompt on the review node outranks all of these inside the orchestrator and replaces all three base prompts, while each persona keeps its own skills and context suffixes. The activity loads the cross-repo dependency block, whose primary consumer this is — a breaking-change verdict needs the downstream consumer list — and hands everything to the orchestrator in the agent layer.

Prompt assembly differs per persona. The domain-logic prompt gains the run's success criteria with an instruction to report any unmet one as an `UNMET_SUCCESS_CRITERION` finding. The security prompt gains the advisory static-scan findings carried on the code result. All three gain the cross-repo block and their own skill fragments.

The unpriced-model check and the budget are asserted once before the fan-out, not once per reviewer, so three concurrent reads of the same ledger row cannot disagree. The three reviewers then run under `Promise.allSettled`. A reviewer that crashes is not dropped and does not fail the activity: it is converted into a critical verdict with a `REVIEWER_CRASH` finding whose suggested fix is manual review. The crashed call itself still leaves a failed-call trace row, priced from any usage it had already recorded and attributed to the persona's own model, so the cost of a reviewer that was paid for and then failed to produce a verdict is not lost. Approval is unanimous — the aggregate is approved only when every verdict is approved — and the rejection summary flattens every finding from every dissenting reviewer into the exact string the review-fix activity consumes.

Each verdict is structured output constrained by a schema with a reviewer enumeration and a severity of pass, informational, warning, or critical. This is workflow-driven fan-out with structured results: the interpreter decides to run the network, and only the typed verdicts cross the boundary back.

## Deep dive: the security gate

`scanDiffForSecurityIssues` is the post-diff gate, and it is a different mechanism from the review network. The network gives three personas an opinion on the whole change and routes on their verdicts; this scans the diff alone with the `securityReview` agent and can fail the activity outright. Before the call it refuses an unpriced model under a USD cap and asserts the budget.

The agent returns structured output: a list of findings with category, file, optional line, severity, and a suggested fix, plus a boolean. The processor then overrides that boolean — any finding at critical severity forces `passed` to false regardless of what the model claimed. Every path that pushes agent-written code inspects the result and, on failure, raises a non-retryable `ApplicationFailure` with the type `SECURITY_GATE_FAILURE`, carrying the findings on the failure details and a rendered summary in the message. Those paths are `executeImplementation` and the shared fix session, each right after reading the pushed diff; `resolveMergeConflict`, on the diff of what the resolver wrote and before it pushes the target; and the trusted publish of an agent run, on the committed change. Non-retryable is the point: retrying would re-run the same scan against the same diff.

The scan persists its own trace in its own `finally`, under the `securityReview` role, so a scan that throws still leaves a failed-call row, attributed to the bound model, apart from the calling activity's trace. Because the gate runs on the initial implementation and on all three fix paths, removing the `securityReview` agent row breaks every implementation run wherever those steps are installed.
