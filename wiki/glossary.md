## About this glossary

Every term below is defined by something that exists in source at the indexed commit: a Prisma model, a Zod schema, a TypeScript union, or an exported constant. Terms about who may reach a repository and whose credential a run uses link to [Repository Access, Sharing, and Per-User Credentials](./3.4-repository-access-and-credentials.md), where they are explained in full. Terms about the platform's own MCP endpoint and its OAuth server link to [MCP Server and OAuth](./3.5-mcp-server-and-oauth.md); agent runs and implementer runtimes to [Agent Runs and Implementer Runtimes](./4.6-agent-runs-and-implementer-runtimes.md); the model catalog and pricing to [Model Catalog and Pricing](./4.7-model-catalog-and-pricing.md). Terms are ordered alphabetically and grouped by initial letter, with one `Sources:` footer per group.

## A

**Activity** — A Temporal activity: the deterministic boundary between the replaying workflow isolate and the non-deterministic outside world (LLM calls, Docker, the GitHub API, the database). Every activity the worker registers is re-exported from a single barrel, and the interpreter reaches them through the `STEP_EXECUTORS` map keyed by step name. Workflow code may only `import type` from outside `@temporalio/workflow`, so all real I/O lives behind this boundary.

**Acts-as user** — The user a schedule launches its runs on behalf of, held as the nullable `actsAsUserId` on `ScheduledWorkRequest`. It is the user who last defined what the schedule does: the one who created it, or who changed its description or template. Every fire, whether by cron or by hand, launches as that user: the schedule's stored Temporal arguments carry it as `launchedById` when it is set and omit it otherwise, so a schedule with no acts-as user runs on the platform credential. Firing a schedule by hand re-binds it to the person firing before anything runs, and that person is judged as the caller. See [schedules](./3.4-repository-access-and-credentials.md#schedules-identity-team-and-concurrent-edits).

**Agent** — A first-class, versioned database row that carries an agent's identity plus optional overrides for model, system prompt, skills, tools, a pinned provider credential, and an `mcp`-type Connection whose tools it may bind. It is the single source of truth for per-key configuration; a null override field means "inherit from the next scope up". Agents are scoped through the same cascade as every other config table, and partial unique indexes per scope mean writes use `findFirst` plus a conditional create rather than `upsert`.

**Agent key** — The free-form camelCase string that identifies an agent, such as `implementer` or `securityReviewer`. There is deliberately no database enum for it, so a new agent ships as seed data rather than a migration. `MODEL_BACKED_AGENT_KEYS` lists only seven agents that carry their own `modelSpec`, drive cost pricing, and get a label in the model-config UI; it is not the universe of agents.

**Agent node** — A workflow node type that runs a library Agent by reference and records its output at `nodes.<id>.output` like any step. Its `agentRef` is either a bare key (float to the latest active version) or `key@version` (pinned). A per-node `systemPrompt` overrides the Agent's own prompt, and `userMessage` supplies the literal prompt payload.

**Agent run** — An ad-hoc launch of one library Agent against one repository, with no workflow authored for it. `POST /api/v1/agent-runs` (the CLI's `agent run` and `agent rerun` and the dashboard's agent-run form call it) writes a `RunInput` and starts a `WorkflowRun` of the [Agent Run template](#a). The launch names an `agentRef` (`<key>` or `<key>@<version>`), a prompt of up to 20,000 characters, and a delivery of `none` (show the diff), `branch` (push a branch) or `draft_pr` (also open a draft pull request), plus optional `maxSteps` and `maxWallClockSeconds` caps that can only lower the ceilings set by the `workspace.agentRun*` settings. Nine agent keys, the ones that back platform mechanisms such as `securityReview` and `evalJudge`, cannot be launched. The gateway checks for good error messages and the worker re-validates everything, because other launch paths reach the same template. See [agent runs](./4.6-agent-runs-and-implementer-runtimes.md#part-one-agent-runs).

**Agent Run template** — The hidden system template behind agent runs: a `WorkflowTemplate` named `Agent Run` whose `origin` is `system:agent-run`, with a spec of one internal step, `runAgentTask`, then a terminate node. The workspace, the gate and the push all live inside that step, so there is no node an author could remove or route around. The name and any `system:` origin are reserved: template create and rename, and bundle install, refuse them; no template route can read, edit, run, schedule or give a webhook to it; and an authored template may not name an internal step. `syncBuiltins` seeds it and never touches a row of the same name that lacks the system origin. See [agent runs](./4.6-agent-runs-and-implementer-runtimes.md#part-one-agent-runs).

**Agent version** — The integer `version` column on an Agent row; the active row at a scope is the highest version still marked active. At run start the resolved versions are snapshotted into `WorkflowRun.agentVersions`, so editing an Agent mid-flight cannot change a run already in progress. A node can also pin a version explicitly through the `key@version` form of an agent reference, which must carry a version of 1 or more.

**AgentTrace** — One recorded tool call, LLM response, or activity event captured during an agent activity. A row carries the Temporal activity type as `nodeId`, and separately the workflow-spec node it ran for (`specNodeId`), the interpreter's recording id for it (`recordingId`, prefixed with the fan-out branch path inside a branch) and the interpreter's own attempt number (`stepAttempt`), next to Temporal's retry `attempt`, so the run viewer can tie a trace to its node and group a retry's traces apart. `runId` is nullable: a [runless workflow](#r) writes traces keyed by `workflowId` and `temporalRunId`, and each row denormalizes the spending team and organization. Persistence is best-effort: failures are swallowed so tracing never breaks a run.

**Autonomy policy** — A governance row holding JSON rules keyed by risk class that decide whether an outcome publishes automatically or pauses for human approval. Resolution walks template-specific policy, then team default, then the seeded global default. Decisions taken under a policy are recorded as `AutonomyDecision` rows against the run.

## B

**Binding** — The unit that reads a value into a node's inputs. Exactly one of three forms is used: `from` reads a dot-path out of the run context with an optional default, `literal` supplies a constant, and `expr` evaluates an expression capped at 2,000 characters. The union is deliberately non-strict so specs stored with incidental extra keys still parse when re-read at run time.

**Budget tier** — One of `STANDARD`, `LARGE`, or `EPIC`, attached to a run and used to cap token spend. The built-in ceilings run from 2M input and 500K output tokens at standard up to 20M and 5M at epic. An operator can override the six numbers on the workflow-defaults singleton; with no override the resolver returns exactly the built-in constants. A workflow that keeps no run has no tier and is capped by the [runless](#r) settings instead.

**Bundle** — A versioned, self-describing export of a tagged set of library content: agents, skills, scanner patterns, and templates. Connection instances never travel in a bundle because they hold URLs and credentials; a bundle only declares the connection types its content requires. Schema version 2 hashes the whole manifest minus the three self-referential metadata fields, so a bundle's name and version are covered by its signature, and a version 1 bundle is rejected rather than reinterpreted.

## C

**Catalog price source** — Where a call's price came from, recorded as one of three `PriceSource` values: `catalog` (a `ModelCatalogEntry` row), `builtin` (the `BUILTIN_MODELS` table in code) or `unknown`. `getModelPrice` asks the catalog first, then the built-in table, and otherwise answers a zero price marked unknown; the lookup is exact, so a near-miss spelling is never priced as its neighbour. The value is written to the `llm.cost_price_source` span attribute. Separately, every built-in model row carries a `priceSourceUrl`, the provider's official pricing page its prices were read from. See [pricing in the worker](./4.7-model-catalog-and-pricing.md#pricing-in-the-worker).

**Claude Code runtime** — The second [implementer runtime](#i), chosen when the run-pinned `workspace.implementerRuntime` setting is `claude-code`. The Claude Agent SDK runs in the worker; the `claude` binary runs inside the workspace container, reached through `docker exec -i`. Every tool call the harness makes is decided in the worker by `decideToolCall` before it runs, so the scanners that guard the Mastra tools guard this loop too. It brings its own tools, so only six are allowed (`Read`, `Write`, `Edit`, `Bash`, `Glob`, `Grep`); the agent's model must be an Anthropic one, and the same credential the Mastra runtime would use is passed to the container. See [implementer runtimes](./4.6-agent-runs-and-implementer-runtimes.md#part-two-implementer-runtimes).

**cond node** — A branching node that evaluates an expression and transitions to `onTrue` or `onFalse`. Because a `cond` edge may point backwards, the workflow graph is intentionally not acyclic and can express retry loops. The transition ceiling is what stops a back-edge from looping forever.

**Connection** — The generic integration target. Its `type` discriminator defaults to `git_repo`; other types such as `mcp`, `http_api`, and `notion` stash their specifics in an opaque `config` JSON bag. Git-repository fields stay as typed columns, and a token-based connection stores its credential as an AES-256-GCM ciphertext with nonce and auth tag. A git repository additionally points at an optional `GitHubInstallation`, may be shared with further teams, and may carry per-user tokens and cached permission answers; see [Repository share](#r), [Installation](#i), and [Repo access](#r).

**Connection credential** — One user's own GitHub token for one repository, stored as a `ConnectionCredential` row. The token is held as an AES-256-GCM ciphertext with its nonce, auth tag, key version and last four characters, and the row records the API and web origins that were current when it was saved. It is unique per repository and user, and it is used only for runs that user launched; a run launched by anyone else, or by no one, never reads it. The feature is inert unless `github.userCredentialsEnabled` is on. The only way to obtain a token is `resolveUserCredential`, which is keyed by repository and user, so no path can pick whichever token a repository happens to have. It returns nothing, and the run falls back to the platform credential, when the user is inactive or no longer a member, a base URL is off the allowlist, or an origin no longer matches; a token that cannot be decrypted throws instead. See [per-user credentials](./3.4-repository-access-and-credentials.md#per-user-github-credentials).

**Consent and grant** — A user's consent to one OAuth client is an `OauthConsent` row holding the scopes (`mcp:read`, `mcp:write`) the user approved. The consent screen shows the app's registered name marked unverified, the redirect host and what the grant allows, and starts with write unchecked. A grant is that consent as it is used: the token verifier loads the latest consent for the user and client on every request, rejects a token when none exists or when a re-consent is newer than the token, and intersects the token's scopes with what was consented and what the operator allows. Settings lists a user's grants as connected apps; disconnecting one runs `revokeMcpGrants`, a single transaction that deletes the consent and revokes the stored refresh and access tokens and pending authorization codes, because deleting the consent alone would leave a refresh token alive. See [consent, connected apps and revocation](./3.5-mcp-server-and-oauth.md#consent-connected-apps-and-revocation).

**containerStep node** — A node that runs an image under the same locked-down ephemeral container as a shell node, but with a structured JSON contract: resolved inputs arrive on the `CONTAINER_STEP_INPUT` environment variable and the container's JSON output binds at `nodes.<id>.output.result`. Three transports exist — a single stdout object, a newline-delimited event stream, or a detached loopback HTTP sidecar. It is how a bundle ships coded capabilities without untrusted code entering the worker process.

**Context snapshot** — A per-work-request row capturing raw ticket data, raw documentation, an optional Figma design summary, and the extracted success criteria. It is seeded server-side at submission time by the tracker, knowledge-base, and Figma connectors. Population is best-effort, so a connector failure never blocks a submission.

## E

**Epic** — A cross-repository request fanned out into one child workflow per repository, with a dependency graph between them. Each `EpicRepoEntry` names the repositories that must complete before it starts, and the orchestrator collects a per-repository `WorkflowResult` into `EpicResult.childResults`. When the entry list is empty the planner activity proposes repositories from the candidate ids. A child starts only once every repository it depends on has succeeded; one blocked by a failed upstream is recorded as skipped. The result's status is `SUCCESS`, `FAILED`, `TIMED_OUT` or `CANCELLED`. The pair is a workflow-input and result type with no table of its own. The epic's `launchedById`, when present, is copied onto every child request, so each child runs as the person who launched the epic.

**Eval case** — One frozen benchmark case: a pinned fixture repository at an exact commit, the input payload the candidate agent runs on, and the in-scope golden test command used as the execution floor. `flakeScreened` gates promotion, requiring the reference to pass consistently. A case that stops passing against current repository state is quarantined and excluded from the gate rather than counted as an agent failure.

**Eval run** — One harness run: a candidate agent, model, or prompt reference scored against a baseline over a dataset, with the paired-statistics verdict stored in `summary`. Its status is one of `RUNNING`, `SUCCESS`, `FAILED`, or `REGRESSION`. Individual scores land as `EvalResult` rows linked back to the run and the case.

**Eval scorer** — One entry in an eval node's scorer list. Six kinds exist: `gate` and `assert` are floor scorers that run first and short-circuit the rest on failure, while `trajectory`, `judge`, `policy`, and `pii` are the remaining kinds, with judge and trajectory advisory by default (`judgeAdvisory: false` lets a calibrated judge axis block). The recorded signal source enum is broader still, nine values in all, adding review, merge, and human-audit origins for scores captured outside a node.

**Expression** — The tiny grammar evaluated on `cond` nodes and `expr` bindings, over the run context: path lookups, literals, arithmetic, comparisons, boolean logic, `??` and parentheses, with no function calls and no assignment. Source length is capped at 2,000 characters because a binding that long is a payload rather than a condition. `evalBoolean` is the entry point the interpreter uses for branching.

## F

**fanOut node** — A node that evaluates `over` to an array and runs a named subgraph once per element, then resumes at `join`. ## I

**Implementer runtime** — The loop that drives one model turn of the implementer, the CI, review and gate fixers, and the merge-conflict resolver. It is an `ImplementerRuntime` with a single `runTurn` method that only runs the loop; usage, scanning and tracing belong to [`runImplementerTurn`](#r). Two exist: the Mastra tool loop, which is the default, and the [Claude Code runtime](#c). `selectImplementerRuntime` chooses between them from the run-pinned `workspace.implementerRuntime` setting (`mastra` or `claude-code`), so a run that began on one runtime cannot finish a later iteration on the other. **Installation** — A `GitHubInstallation` row naming one GitHub App installation: a numeric `installationId`, a display-only `accountLogin`, `isActive`, and a `host` that is empty for the instance's own host and otherwise names the GitHub host the installation lives on. It caps total node transitions at 500 by default so a spec with back-edges cannot loop forever; the cap and the default fan-out width come from run-pinned settings that `readInterpreterLimits` reads out of the run's snapshot. It runs the same way in the worker and in unit tests, because its dispatcher is an interface rather than a direct activity call.

## M

**MCP node** — A node that calls one tool on a Model Context Protocol (MCP) connection as a workflow step. `connectionRef` names an `mcp`-type Connection, `tool` names the tool on that server, and the node's inputs map to the tool's arguments. The tool result binds at `nodes.<id>.output.result` like any other step output. This is the outbound direction: the platform is the client. The platform's own endpoint is the [MCP server](#m).

**MCP server** — The MCP endpoint the platform itself exposes at `/api/v1/mcp`, so an external MCP client can act as a signed-in user. It is an OAuth resource server: stateless, with the tool list decided per request from the verified access token, and it answers 404 from every route while the `mcp.enabled` setting, which defaults to off, is off. Its authorization server is better-auth's `jwt` and `oauthProvider` plugins, which issue short-lived JWT access tokens to dynamically registered public clients. MCP code never touches the database: a tool reaches data only by calling an ordinary REST route in-process, so the route's role check, visibility filter and audit apply. See [MCP Server and OAuth](./3.5-mcp-server-and-oauth.md).

**MCP tool** — One of the seven tools the MCP server exposes. Five are reads: `list_repositories`, `list_work_requests`, `list_runs`, `get_run` and `list_pending_human_steps`. Two are writes: `submit_work_request` and `cancel_run`, which exist only for a token that holds `mcp:write`, which in turn requires `mcp.writeToolsEnabled`. A tool makes one in-process call to a REST route that declares a matching `mcpScope`, then reduces the response to an allowlisted projection, because a result enters a model's context and anything another person wrote is an injection channel. No tool can approve, merge or answer a human step. Not to be confused with the `mcp` pseudo-key in an agent's `toolKeys`, which binds an outbound server's tools. See [tools](./3.5-mcp-server-and-oauth.md#tools).

**Memory item** — The generic semantic-memory row, carrying a 1536-dimension pgvector embedding plus scope, entity, channel, team, and organization keys for retrieval. `scope` is the partition key, so one domain's memories stay isolated from another's. The vector dimension is fixed in the column, so an embedding model returning a different shape is rejected rather than stored.

**Model catalog entry** — A `ModelCatalogEntry` row: the per-million-token USD input and output prices LLM calls are costed at, for one `<provider>/<model-id>` spec, with a `kind` (`CHAT` or `EMBEDDING`) and a `status` (`ACTIVE`, `DEPRECATED`, `RETIRED`). Status drives the model pickers and never pricing, so a retired model stays priced for the agent versions pinned to it. Rows are global and unique per provider and model id. Built-in rows are seeded from `BUILTIN_MODELS` by `syncModelCatalog`, which keeps an untouched one in step with code and never overwrites one an admin customized (`isCustomized`); nothing is deleted, and a row of `0/0` is a known free model rather than an unknown one. See [the catalog table](./4.7-model-catalog-and-pricing.md#the-catalog-table-its-enums-and-the-uniqueness-rule).

**Model discovery suggestion** — A `ModelSuggestion` row raised by asking each provider, through its GLOBAL credential, which models it lists. A `NEW` suggestion means a provider lists a model nothing prices; a `RETIREMENT_CANDIDATE` means a model the catalog prices is no longer listed by a provider whose listing succeeded. Suggestions are stored apart from the catalog, so discovery can never make a model known at zero cost and the pricing path never reads one; an admin supplies each price and can only dismiss a suggestion, and nothing here retires a model. A provider whose listing failed leaves its suggestions as they were, and its `ModelDiscoveryProviderStatus` row records the failure. Discovery runs on demand from the gateway and on a schedule in a worker workflow. See [on-demand discovery](./4.7-model-catalog-and-pricing.md#on-demand-discovery).

**Model spec** — The `<provider>/<model-id>` string that binds an agent to a model, stored in `Agent.modelSpec`. The provider is lowercased when parsed and the model id may itself contain slashes. When the spec is null and `inheritsModelFrom` names a parent agent key, the model resolves from that parent instead, which is how sub-role personas avoid needing their own model row. Provider names outside the built-in set (`anthropic`, `openai`, `google`) route through the OpenAI-compatible adapter and require an `apiBase` on the credential.

## N

**Node type** — One of the fifteen members of the discriminated union a workflow spec's nodes may take: `step`, `agent`, `mcp`, `eval`, `set`, `cond`, `signal`, `terminate`, `fanOut`, `shell`, `containerStep`, `humanApproval`, `humanDecision`, `humanInput`, and `humanReview`. ## O

**OAuth client** — A registered application that may ask for tokens from the platform's authorization server, stored as an `OauthClient` row. Registration is dynamic and unauthenticated, and the gateway hardens it into the narrowest shape: every client is public (`token_endpoint_auth_method` is `none`), may request only the `mcp:read`, `mcp:write` and `offline_access` scopes, and is linked by default to the one MCP resource. There is no surface for creating, editing or deleting clients; the only per-client switch is the `disabled` flag, which the token verifier reads on every request. The authorization-code and refresh-token grants are the only ones enabled. See [the authorization server](./3.5-mcp-server-and-oauth.md#the-authorization-server).

**onFail** — The per-step workflow-level failure policy. `block` terminates the run as failed and is the default, `warn` records the failure and continues to `next`, and `{ retry: N }` re-runs the step up to N more times before falling back to block semantics. A node's own `retry`, `startToCloseTimeout` and `heartbeatTimeout` fields still parse so stored specs load, but nothing reads them: the worker applies fixed activity retry and timeout groups by step kind.

**Organization** — The outermost tenant. Every team nests under exactly one organization, and an organization may carry a monthly spend cap in USD cents plus a warning threshold percentage. It owns agents, provider credentials, skills, memory items, config settings, and permission grants at the `ORGANIZATION` scope.

## P

**Personal access token** — A long-lived API token for command-line and CI use, issued once in plaintext as `ats_<random>` with only its SHA-256 hash stored. A non-secret twelve-character prefix is retained so the admin interface can disambiguate listed tokens without re-issuing them. `lastUsedAt` updates best-effort on each successful authentication so stale tokens can be pruned. A personal access token is refused on the MCP bridge: an MCP access token is a different credential.

**Provider credential** — An AES-256-GCM encrypted API key for one large-language-model provider, scoped `GLOBAL`, `ORGANIZATION`, or `TEAM` and resolved team-first. Template scope is deliberately unsupported: a template may reference an existing credential but cannot create its own. `lastFour` holds the trailing plaintext characters for display only, and `keyVersion` supports rotation.

## Q

**Quality gate** — One of six commands run inside the work-request workspace: `runLint`, `runTypecheck`, `runTests`, `runBuild`, `runVulnScan`, and `runPerfBench`. Each captures stdout, stderr, and exit code without throwing, stores the full output as a workflow artifact, and returns a small `{ passed, summary, exitCode, artifactId?, signal?, command? }` payload. ## R

**Repo access** — A `RepoAccess` row: what the source-control host last said about one user's permission on one repository, as a `RepoPermissionLevel` plus a `checkedAt` time. It is a cache, not a grant table. Every row is an answer GitHub gave, written only by the launch path, the webhook refresh and the scheduled sweep, so editing one by hand grants access GitHub does not back until the next sweep takes it away. Rows exist only for pairs that team membership already allows, and a failed lookup leaves the row alone so it grows stale instead of recording an outage as a denial. See [caching and refresh](./3.4-repository-access-and-credentials.md#github-permission-gating).

**Repo access gate** — The deployment-wide switch that decides whether GitHub's answer narrows team membership. `repoAccess.mode` is `off` (the default, membership alone), `advisory` (log what would be refused, change nothing) or `enforce`; `repoAccess.viewStaleAfterHours` bounds how old a cached answer may be for listings. Administrators bypass it. At launch the gate asks GitHub live and requires the `write` level, because a run pushes a branch; listings read the cached `RepoAccess` rows and are narrowed only under `enforce`. A launch is refused as `no-github-identity`, `insufficient-permission`, `lookup-unavailable`, `host-mismatch` (no platform credential applies to the repository's host) or `user-credential-rejected`; failures to ask (rate limit, outage, rejected credential) are refusals under `enforce`, not verdicts of no access. The decision function that also checks membership and installation retirement is `decideRepoAccess`. See [GitHub-permission gating](./3.4-repository-access-and-credentials.md#github-permission-gating).

**Repo permission level** — The `RepoPermissionLevel` enum: `NONE`, `READ`, `WRITE`, `ADMIN`, weakest first, mirroring GitHub's collaborator permission levels. It is the type of the cached `RepoAccess.permission` value and what the launch gate compares against `write`.

**Repository host allowlist** — The rule that stops a credential being sent to a host an administrator has not approved. A repository's `githubUrl` and `githubApiUrl` are base URLs and every credential is sent to them, so an override must match the GitHub integration's own hosts or `github.repositoryHosts`; a user's own token must additionally match `github.userCredentialHosts`. `credentialHostAllowed` accepts only HTTPS URLs in canonical form with no userinfo, query or fragment, and matches the host exactly. Both settings are `ADMIN`-only and `sensitive`. A platform credential is further confined to its own host family; see [GitHub host credential](#g). See [host allowlist and verified-origin binding](./3.4-repository-access-and-credentials.md#host-allowlist-and-verified-origin-binding).

**Repository share** — A `ConnectionTeamShare` row giving one further team access to a repository. Members of a shared team may see the repository and launch runs on it exactly like owning-team members, but cannot edit, re-share, schedule or add dependency edges, and runs keep the owning team's budget and settings. A share is unique per repository and team, and is limited to teams in the owning team's organization. "May this user reach this repository" is answered only through `repoMembersSelect`, `isRepoMember` and `repoMemberWhere`; reading the owning team's memberships alone locks shared members out. See [one definition of membership](./3.4-repository-access-and-credentials.md#one-definition-of-membership).

**Review network** — Three reviewer personas — security, domain logic, and performance — each given the whole diff and each returning a structured verdict with an approval flag, a severity of `PASS`, `INFO`, `WARNING`, or `CRITICAL`, and a list of findings. Each persona runs as its own Agent row (`securityReviewer`, `domainLogicReviewer`, `performanceReviewer`), binding the `reviewer` model through `inheritsModelFrom` unless its row sets one. The verdicts aggregate into an `AggregatedReviewResult` that fixed workflow code branches on. This is distinct from the post-diff security gate, which scans the diff alone and fails the activity outright.

**Run context** — The mutable record the interpreter walks with, seeded with four top-level keys: `request` (the run request), `workflow` (the Temporal workflow id), `context` (writable scratch, pre-populated with the resolved workspace) and `nodes` (per-node outputs). Bindings read dot-paths out of it and `set` nodes write into it. A fan-out branch gets a sealed child copy so its writes do not leak back to the parent.

**Run identity** — Which GitHub identity a launched run will act as, `'caller'` or `'platform'`, passed into the launch gate. `'caller'` is used on a path that records the caller as the run's launcher, so the gate judges the caller's own saved token; work-request submission, epics, PRD runs, Slack (as the linked platform user) and creating, rebinding or firing a schedule pass it. `'platform'` is the default, so a call site that does not think about it keeps the login-based behaviour. See [per-user credentials](./3.4-repository-access-and-credentials.md#per-user-github-credentials).

**Run pinning** — Freezing a value into `WorkflowRun.pinnedSettings` at run start so a mid-run configuration change cannot make the second half of a run disagree with the first. A setting declares this with `runPinned: true`; it is used for structural decisions such as fan-out width, the transition ceiling and the implementer runtime, none of which the workflow isolate could read from the database anyway. Everything not pinned re-resolves per call, which is what lets a model or credential edit land inside an in-flight workflow.

**runImplementerTurn** — The one function every implementer-driven caller goes through for a model turn. It runs the turn on the given [implementer runtime](#i), then does the bookkeeping every caller owes it: accrues usage against the run's budget (one record per model when a turn spans several, each priced at its own spec), runs the advisory output scan, and records the LLM call on the tracer. The TDD loop, the CI, review and gate fix sessions, the eval harness and the merge-conflict resolver all call it, so every runtime is governed the same way. The caller keeps the pre-call budget check and any failure row. See [implementer runtimes](./4.6-agent-runs-and-implementer-runtimes.md#part-two-implementer-runtimes).

**Runless workflow** — A workflow that keeps no `WorkflowRun` row: workflow authoring and explaining, scheduled evals, lesson consolidation and repository-dependency inference. No budget tier applies to one. Instead the `workflow.runlessMaxInputTokens` (20M by default) and `workflow.runlessMaxOutputTokens` (5M) settings cap what one execution may spend, summed from its `AgentTrace` rows, and an execution that passes a cap fails with `BUDGET_EXCEEDED`. Both settings are `ADMIN`-only and resolve against the team or organization the spend is attributed to.

## S

**Scanner pattern** — A labeled regular expression row with a type of `INJECTION`, `EXFILTRATION`, `SHELL_COMMAND`, `CODE_SECURITY`, `SENSITIVE_FILE`, or `PII`. Sixty-three built-in patterns ship in source (13, 11, 18, 10, 7 and 4 across those six types) and sync idempotently at gateway startup; admins add more through the scanner admin page. Patterns are data whose execution is bounded rather than analysed, so they run in a pooled worker thread under a wall-clock budget.

**Scope cascade** — The five configuration levels, most specific first: `WORKFLOW_TEMPLATE`, `CHANNEL`, `TEAM`, `ORGANIZATION`, `GLOBAL`. Channel applies only to channel-resident runs and organization only when the run's team belongs to one, so a deployment using neither behaves like a three-level cascade. Agent and credential resolution stops at the first match and has no fallback past global.

**set node** — A node that writes a map of bindings into the run context and continues to `next`. It is the shaping primitive: it is how a spec moves a value from one node's output into the position a later node's binding expects.

**Setting registry** — One declaration per operator-tunable knob, carrying its Zod schema, default, the scopes it may be overridden at, the required role, and whether it pins to a run. That single declaration validates a write, resolves a read, drives the admin form, and gates permission, so adding a knob is a definition rather than a migration plus a route plus a form field. Thirty-one settings are declared across eight groups (`channel`, `github`, `mcp`, `memory`, `repoAccess`, `repoDependency`, `workflow`, `workspace`). A setting's identity is the property name it is stored under, and its default is always the constant it replaced, so an unconfigured deployment behaves as it did before the knob existed. A definition may be marked `sensitive`, which redacts its stored and resolved values for anyone below the required role; the host allowlists use it. What a process needs at start-up, such as workspace sizing and the default workspace image, is read from the environment by `resolveWorkspaceInfra` and is not a setting.

**shell node** — A node that runs an author-supplied command in an ephemeral, locked-down container separate from the long-lived workspace. The image must be on the team's effective allowlist, networking is `none` unless the node opts into `egress`, and the container is read-only with a tmpfs, a process limit, and memory and CPU caps. Authoring one requires a team-admin permission and every save is recorded in a shell audit row.

**signal node** — A node that waits for a named Temporal signal with a timeout, transitioning to `onReceive` or `onTimeout` and optionally storing the payload under `storeAs`. It is the generic wait primitive; the human-in-the-loop node types are the specialized forms.

**Skill** — A named prompt fragment injected into an agent's system message; it controls how an agent reasons, not what it can do. Thirty-five built-ins ship one per file and seed as built-in and verified, while custom skills seed unverified and reset to unverified whenever their prompt text is edited. Custom text is scanned for injection and exfiltration patterns on save, advisory rather than blocking.

**Step key** — The `step` string on a step node, naming an entry in the built-in step catalog. The catalog holds thirty-eight names (`BUILTIN_STEPS`), spanning agent, gate, control, version-control, and shell categories; one of them, `runAgentTask`, is internal to the Agent Run template and is left out of the authoring palette, so thirty-seven are offered to authors. The worker asserts at boot that every `BUILTIN_STEPS` name has a registry entry, and a test checks that the list and the `STEP_EXECUTORS` table name the same steps, so a step missing from either fails before it ships.

**Subtask** — A feature-level unit produced by decomposition, carrying a stable kebab-case slug of at most forty characters, a title, a description, and optional file-scope hints. Each subtask is implemented in its own workspace and branch, and the resulting branches merge into the work-request branch before the pull request opens. The decomposer is prompted to generate the slug and the activity validates it.

## T

**Team** — The tenancy unit that owns connections, workflow templates, agents, credentials, skills, and configuration overrides. It carries a slug, per-team additions to the shell-step image allowlist and the egress allowlist, and optional Slack notification settings. Every team nests under exactly one organization, with the foreign key set to restrict so an organization holding teams cannot be deleted out from under them.

**terminate node** — A node that ends a run with a status of `SUCCESS`, `FAILED`, `TIMED_OUT`, or `SKIPPED`, optionally binding a result map. `CANCELLED` is deliberately absent: Temporal sets it out of band on a cancellation signal, so a spec can never declare it. Inside a fan-out branch, reaching a terminate node ends that branch rather than the whole run.

**Tool** — An executable Mastra tool function, as opposed to a skill's prompt text. The implementer has four configurable workspace tools — read file, write file, list directory, and run a shell command — gated by the resolved agent's `toolKeys`, where null means all four. A fifth skill-loading tool is added automatically when skills are present and is not configurable, and an `mcp` pseudo-key gates binding an outbound MCP server's tools at run time. The [Claude Code runtime](#c) has its own tool set and does not use these.

## W

**Work request** — The submitted unit of work, stored in the `run_inputs` table as a `RunInput` row. It carries a correlation key, a description, an optional structured payload validated against the template's input schema, an optional target connection, and an optional template and version override snapshotted at run start. The relation field names on related models remain `workRequest` across the model rename, so the public API shape does not churn. Its `requestedById` is whoever first submitted it, which is not the run's launcher: a re-run reuses the request. An `Idempotency-Key` supplied on `POST /work-requests` is stored on the row and is unique per requester.

**Workflow ID** — The deterministic Temporal workflow identifier, formed as `eng-<organization>-<repo>-<ticketId>` with the organization and repository lowercased and the ticket id keeping its case. A repository with a `githubUrl` override also carries that URL's lowercased host (`eng-<host>-<organization>-<repo>-<ticketId>`), because the same organization and repository name on two hosts are different repositories; a repository on the instance's own host keeps the original form. The format is not unique on its own, since every part may contain hyphens, so `chooseWorkflowId` checks which repository an existing row belongs to: a string held by a different repository moves the new one to an `-x<repo-id-prefix>` family, a rerun of a finished ticket takes `-r<N>`, and a still-running execution of the same ticket is a conflict. The matching branch name is `<prefix>/<ticketId>`, where the prefix defaults to `auto`. Agent runs use their own `agent-` workflow ids.

**Workflow run** — One execution of a template. It stores the parsed spec as `specSnapshot`, the resolved agent versions, and the pinned settings at start time, so live edits to the template or its agents do not affect the run. It records who started the execution as `launchedById` and the Temporal run id that created the row, which together decide whose saved GitHub credential the run may use (see [Launcher](#l)). It also denormalizes the run's total cost and input and output token counts at finalization, so analytics need not re-join through the work-request graph.

**Workflow spec** — The serializable, versioned graph the interpreter executes, stored as JSON on a template version. It holds a name, a description, an entry node id, and a node map, at schema version 1. The schema validates that the entry node exists and that every outgoing edge on every node points at a node that exists, so a dangling reference is a parse error rather than a run-time surprise.

**Workflow step** — A per-node execution record for a run, holding the node id, the attempt number, a status of `PENDING`, `RUNNING`, `PASSED`, `FAILED`, or `SKIPPED`, plus inputs, outputs, and any error. It is unique on run, node, and attempt, so a retry produces a new row rather than overwriting the first.

**Workflow template** — A named, team-owned container for spec versions, carrying an optional declarative input schema, a workspace provider, a status of `DRAFT`, `ACTIVE`, or `ARCHIVED`, and pointers to the active version. It supports an A/B experiment by routing a percentage of incoming requests to an alternate version, and an optional webhook token for public triggering. Template names are unique per team.

**Workflow template version** — An immutable snapshot of a template's spec at version N, validated against the spec schema on insert. A version produced by the workflow-author agent records that provenance in `generatedBy` and must carry a human review timestamp and reviewer before it can be promoted to active. Shell nodes introduced in a version are recorded as audit rows against it.

**Workspace container** — The long-lived Docker container an agent works in, named `workspace-<random-hex>`. It exposes exec, capturing exec, stdin-streaming exec, and an authenticated git helper that injects the clone credential per call rather than persisting it in the repository's git config. Unlike the ephemeral shell-node runner it keeps default bridge networking and a writable layer, because the implementer needs outbound git and package installs, but it still drops all Linux capabilities and bounds memory, CPU, and process count. Those caps and the default base image come from environment variables (`WORKSPACE_MEMORY`, `WORKSPACE_CPUS`, `WORKSPACE_PIDS_LIMIT`, `WORKSPACE_IMAGE`), and an image passed by the caller wins.

**Workspace provider** — The registry entry naming what kind of context a run works in: `git_repo`, `document`, `issue_tracker`, `record`, or `api_only`. Each provider declares the connection types it can consume. A template names the provider it expects; a null value falls back to `git_repo`.
