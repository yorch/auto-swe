## Overview

The gateway exposes one versioned REST surface under `/api/v1`. Forty-three non-test modules live in
[packages/gateway/src/routes/](https://github.com/yorch/auto-swe/tree/ae416937/packages/gateway/src/routes);
forty-two of them register routes, and `workflowProjections.ts` holds only shared schemas and
projections. Together they declare 263 handlers, as `FastifyPluginAsync` plugins mounted with a URL
prefix in [packages/gateway/src/index.ts:L290-L370](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/index.ts#L290-L370); the two `GET` metadata handlers in `mcp.ts`, a plain async function,
are among the 263. A route file therefore
declares paths relative to its prefix, and the same file can be mounted more than once. `mcp.ts` is
the exception: it declares absolute paths and is registered at the root.

Counts on this page come from the source, not from a generated manifest. Modules are the `*.ts` files
in `routes/` that are not `*.test.ts`. Handlers are lines in those files that open a route declaration
on the Fastify instance, that is `app.`, `f.` or `fastify.` followed by `get`, `post`, `put`, `patch`
or `delete` at the start of a line, which leaves out Prisma `delete` calls. A declaration that loops
over two paths counts once (`modelCatalog.ts` registers `dismiss` and `undismiss` from one), and an
`app.route(...)` call is not counted at all; those are the better-auth routes and the MCP endpoint,
listed separately below. Mounts are the `app.register(<plugin>, { prefix: '/api/v1…' })` calls in
`index.ts`: 62 mounts of 44 distinct plugins. A module can export more than one plugin:
`workflowRuns.ts` exports `workflowRunRoutes` and `stepRegistryRoutes`, `skills.ts` and
`agentLibrary.ts` each export an admin plugin and a team-scoped one, and `modelConfig.ts` exports a
team-scoped plugin that `teamRoutes` registers as a child.

Eighteen plugins are mounted twice. Seventeen are mounted under both `/api/v1/platform` and
`/api/v1/admin`, the latter an alias kept for one release: thirteen plugins at the bare prefixes,
three at `/organizations`, and `slackChannelRoutes` at `/slack-channels`. `humanStepRoutes` is the
eighteenth, mounted at both `/api/v1/human-steps` and `/api/v1/inbox`. Seventeen `Deprecated alias`
comments mark the second mounts; `githubInstallationRoutes` is the one doubled mount without one.
Four plugins are mounted at `/api/v1/platform` only, with no alias: `modelCatalogRoutes`,
`githubWebhookSecretRoutes`, `githubHostCredentialRoutes` and `usageRoutes`. The tables below give
the canonical prefix; the alias column notes the second mount where one exists.

## Endpoints outside the plugin tree

Four routes are declared inline on the Fastify instance, ten are registered by the better-auth
handler module, and the MCP endpoint is registered by its own module.

| Method | Path | Purpose | Auth |
| --- | --- | --- | --- |
| `GET` | `/health` | Liveness probe; returns `{ status: 'ok' }` | none |
| `GET` | `/api/v1/auth/providers` | Which social providers are configured, so the login page can hide absent buttons | none |
| `POST` | `/api/v1/auth/session-token` | Exchanges a better-auth session cookie for a short-lived JWT | session cookie |
| `GET` | `/api/v1/auth/me` | Current user row, used by the web server for server-side admin guards | any authenticated |
| `POST` | `/api/auth/sign-in/email` and seven sibling credential paths | better-auth handler under a tightened 20/min per-IP rate limit | none |
| `POST` | `/api/auth/oauth2/register` | better-auth anonymous Dynamic Client Registration, capped at 10/min per IP | none |
| `GET`, `POST` | `/api/auth/*` | better-auth catch-all handler | none |
| `GET`, `POST`, `DELETE` | `/api/v1/mcp` | The MCP endpoint, an OAuth resource server; answers `404` unless `mcp.enabled` is on | OAuth bearer token |
| `GET` | `/.well-known/oauth-protected-resource` and the same path suffixed with `/api/v1/mcp` | RFC 9728 protected-resource metadata | none, `404` unless MCP is enabled |

The eight credential paths are sign-in, magic-link sign-in, sign-up, forget-password,
request-password-reset, reset-password, change-password and send-verification-email; each is
registered as its own `POST` route so it can carry the 20-requests-per-minute limit while
`/get-session` stays under the global 200. The handler refuses any path that URL resolution would
rewrite (`.` or `..` segments, encoded or not, and backslashes) with `400` and `NON_CANONICAL_PATH`,
because Fastify chose the route and its rate limit on the raw path while better-auth dispatches on
the resolved one. The endpoint mechanics, the consent flow and the tool list are covered on
[MCP Server and OAuth](./3.5-mcp-server-and-oauth.md); session and token handling is on
[Authentication and RBAC](./3.2-authentication-and-rbac.md).

## Work requests, runs, and scheduling

### `/api/v1/work-requests`

| Method | Path | Purpose | Role |
| --- | --- | --- | --- |
| `GET` | `/` | List and search work requests; `ticket` is a case-insensitive substring match, results paginated and limited to repositories the caller can reach | `ENGINEER` |
| `POST` | `/` | Submit a work request; takes the launch decision (repository access, org membership, monthly cap), then launches a `RunnableWorkflow` as the caller; honours `Idempotency-Key` | `ENGINEER` |
| `POST` | `/:id/retry` | Re-run a finished request with an `-rN` workflow-ID suffix against the same ticket, repo, and recorded template snapshot; takes the same launch decision as a fresh submit and launches as whoever retried | `ENGINEER` |

Submission and retry both call `authorizeLaunch`, which weighs team membership (owning or shared
team) and the cached GitHub permission together through `decideRepoAccess`, then org membership and
the org cap, and refuse with `403` (or `402` for the cap) and a reason body. The mechanism is covered
on [Repository Access and Credentials](./3.4-repository-access-and-credentials.md). Workflow-id
allocation also accounts for the pre-host id form of a ticket, so an execution still in flight under
the old id blocks a second one. `GET /` and `POST /` both declare `config.mcpScope`, which is what
lets an MCP tool reach them (see [MCP-reachable routes](#mcp-reachable-routes)).

### `/api/v1/agent-runs`

A launch runs one library agent against one repository without a workflow of the caller's choosing;
the run is a `WorkflowRun` of a hidden system template. How the run executes, and its limits, are on
[Agent Runs and Implementer Runtimes](./4.6-agent-runs-and-implementer-runtimes.md) and in
[docs/agent-runs.md](https://github.com/yorch/auto-swe/blob/ae416937/docs/agent-runs.md).

| Method | Path | Purpose | Role |
| --- | --- | --- | --- |
| `GET` | `/agents` | The launchable agents as a launch would resolve them: `GLOBAL`, plus the repository's `ORGANIZATION` scope when `repoId` is given, never `TEAM`; each row lists the versions a `key@version` pin can select | `ENGINEER` |
| `GET` | `/limits` | The step and wall-clock ceilings, the concurrency settings and whether runs are enabled, resolved at the repository's scope when `repoId` is given | `ENGINEER` |
| `POST` | `/` | Launch a run: body names `agent`, `repoId`, `prompt` and optionally `deliver` (`none`, `branch` or `draft_pr`), `budgetTier`, `maxSteps`, `maxWallClockSeconds`; answers `201` with the effective caps; honours `Idempotency-Key` | `ENGINEER` |
| `POST` | `/:workRequestId/rerun` | Re-run an earlier agent run as a new run at the default budget tier; every check is taken again, and anything that is not an agent run answers `404` and `AGENT_RUN_NOT_FOUND`; honours `Idempotency-Key` | `ENGINEER` |

The launch refuses an agent that backs a platform mechanism (`400` and `AGENT_NOT_LAUNCHABLE`), then
takes `validateRunConnection` (repository reach, org membership, the cap). It then refuses a
repository that is not a git repository (`400`) or sits on an unapproved host (`422`), a missing
agent (`404` and `AGENT_NOT_FOUND`), a version pin shadowed by an organization override (`400` and
`AGENT_PIN_SHADOWED`), a cap above the ceiling (`400` and `CAP_EXCEEDS_CEILING`), a missing system
template (`503`), a team with runs disabled (`403` and `AGENT_RUNS_DISABLED`) and a reached
concurrency limit (`429` and `AGENT_RUN_CONCURRENCY_EXCEEDED`). The worker re-checks the bounds that
matter.

`configSettings.ts` is the one config module that is deliberately **not** behind a blanket admin

## Cross-cutting conventions

### Zod schemas and the type provider

Forty of the forty-two route-registering modules open with
`fastify.withTypeProvider<ZodTypeProvider>()`; `slack.ts` and `mcp.ts` are the exceptions. That call
makes `request.body`, `request.query`, `request.params`, and `request.headers` typed from the Zod
schemas declared in the route options. The compilers are installed once at boot with
`setValidatorCompiler` and `setSerializerCompiler` from `fastify-type-provider-zod`.

Serialization has a guard rail. An `onRoute` hook gives any route that declares no `response` schema
a permissive `z.any()` for `200`, because `fast-json-stringify` otherwise silently strips fields the
schema does not declare. Routes that already declare response schemas are untouched.

```ts
app.addHook('onRoute', (routeOptions) => {
  if (!routeOptions.schema?.response) {
    routeOptions.schema = { ...routeOptions.schema, response: { 200: z.any() } };
  }
});
```

Most successful responses wrap the payload as `{ data }`, list responses add
`meta: { limit, offset, total }`, and failures return `{ error: { code, message } }`. `sendError` in
[packages/gateway/src/lib/httpErrors.ts:L1-L18](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/lib/httpErrors.ts#L1-L18) is the helper that writes that envelope, with optional structured
`details`. The MCP endpoint answers in OAuth's own error shapes instead.

### Boolean query parameters

`booleanQueryParam()` is the only sanctioned way to accept a boolean in a querystring, used by the
human-steps, workflow-runs, agent-library, Slack-channel, lesson, repository and model-catalog routes.
It accepts exactly `'true'` and `'false'` and transforms to a real boolean; anything else, including
`'1'`, `'0'`, mixed case, and a bare valueless flag that Fastify parses as `''`, fails validation
with `400`.

`z.coerce.boolean()` is banned because coercion is `Boolean(input)`, which is `true` for any
non-empty string. An explicit `?flag=false` would silently invert to `true`, so the parameter would
mean its opposite with no error anywhere.

### Idempotency

Two mechanisms share the `Idempotency-Key` header, which `IdempotencyHeaderSchema` bounds to 255
characters. Five generic run triggers hash the key into the workflow id: `POST
/workflow-templates/:id/runs`, `POST /webhooks/:token`, `POST /prd-runs`, `POST /agent-runs` and
`POST /agent-runs/:workRequestId/rerun`. They take arbitrary payloads, so there is nothing intrinsic
to derive a stable workflow id from, unlike a work request which has a ticket id. Without a key the
unique index on `ActiveWorkflow.temporalWorkflowId` never fires and a retried trigger starts a
second run.

`workflowIdFromIdempotencyKey(prefix, scopeId, key)` hashes rather than embeds the key, keeping
arbitrary client input out of the Temporal workflow id and bounding its length and charset. The
prefixes are `wf`, `wh`, `prd` and `agent`. The scope is length-prefixed rather than joined by a
separator, because any separator that can also occur inside `scopeId` lets two different pairs hash
to the same string. The digest is truncated to sixteen hex characters, and a collision surfaces as a
`409`, never as two runs merging. An agent run scopes the key by repository and caller, so two users
who pick the same key cannot collide and a `409` never reveals another user's run.

`POST /work-requests` stores the key instead. `RunInput` carries a unique `(requestedById,
idempotencyKey)` pair, so the key is scoped to the authenticated user, and a replay answers `200`
with `deduplicated: true` and the ids of the run the first request started, after re-checking that
the caller could still launch it. The same key with a different ticket, repository, description or
budget tier is `422` and `IDEMPOTENCY_KEY_MISMATCH`; a request whose first attempt has not finished
starting is `409` and `IDEMPOTENCY_KEY_IN_PROGRESS` with a `retry-after` header. A replay starts and
spends nothing, so the org's monthly cap is deliberately not re-applied.

Every mechanism is opt-in: a caller sending no key keeps one fresh run per request, which is what a
schedule or a manual retry wants.

### Launching a run: authorize, then ledger before start

Nine call sites in seven route modules start a run through `launchTrackedWorkflow`: work-request
submit and retry, epics, PRD runs, template runs, the `/:token` and `/jira` webhooks, agent runs, and
the Slack work-request modal. Nine call sites in seven files take the one launch decision, `authorizeLaunch`,
before that: repository access, then org membership, then the org's monthly cap, so a route cannot
ship without one of them. It decides without sending, so an HTTP route and a Slack view
submission render the same refusal in their own shape, and `kind` is `repo-access`, `org-access` or
`org-budget` with status `403` or `402`. Schedule fires, authoring jobs, and the eval and
maintenance triggers do not go through `launchTrackedWorkflow`; a schedule fire is started by its
Temporal Schedule.

`launchTrackedWorkflow` writes the `RunInput` and `ActiveWorkflow` rows first, starts the workflow
second, and deletes the rows if the start fails. The ordering is deliberate. Starting Temporal first
meant a failed DB write left a workflow burning budget, pushing branches, and opening pull requests
with no row to attribute it to, while the reverse orphan is inert, visible in the dashboard, and
operator-recoverable. Writing rows first also makes dedup atomic: the unique index on
`ActiveWorkflow.temporalWorkflowId` decides the winner of two concurrent submissions, where a
read-then-start sequence had a time-of-check-to-time-of-use gap. A lost race returns `409`, with
`RUN_CONFLICT` from template runs, the `/:token` webhook and agent runs, and
`WORKFLOW_ALREADY_EXISTS` from work requests.

### Error mapping

A global error handler converts thrown Fastify errors into the `{ error: { code, message } }`
envelope. Messages on `4xx` are intentional and pass through; `5xx` messages can leak database
constraint text or library internals, so the detail is logged server-side and the client gets a
generic `Internal server error`.

Handlers map domain outcomes to status codes explicitly rather than letting exceptions escape.
Counting literal `.status(N)` and `.code(N)` calls in the route modules, `404` appears 122 times,
`400` 74, `409` 56, `403` 34, `503` 18 and `422` 6. Responses sent through a helper such as
`sendError`, `sendConflict` or `sendLaunchRefusal` are not in those figures, which is why the `402`
count is zero there.

| Source of failure | Detection | Status |
| --- | --- | --- |
| Prisma unique-constraint violation | `isUniqueConstraintError` matches code `P2002` | `409` |
| Known resource collisions | `sendConflict(reply, code, message)` with `REPO_EXISTS`, `TEAM_EXISTS`, `MEMBER_EXISTS` | `409` |
| Launch refused | `authorizeLaunch` returns a refusal; epics and PRD runs collect one per repository | `403` with the reason, `402` for the org cap |
| Temporal execution missing or already closed | `isTerminalSignalError` matches `WorkflowNotFoundError` | write stands, response reports `signalSent: false` |
| Temporal transient failure | anything `isTerminalSignalError` rejects | write is undone so a retry can land the signal |
| Temporal or an integration unreachable | caught around the client call | `503` with a `*_UNAVAILABLE` code, or `502` for a failed schedule sync or cancel |
| Setting write refused by the registry | `denialStatus(code)` | `400` for `UNKNOWN_SETTING` and `SCOPE_NOT_ALLOWED`, else `403` |
| Regex fails the backtracking probe | `probeRegexBacktracking` overruns the budget | `400` with `REDOS_RISK` |
| Better-auth path that URL resolution would rewrite | `isCanonicalRequestPath` | `400` with `NON_CANONICAL_PATH` |

The terminal-versus-transient split matters wherever a signal is delivered after a database write
that describes the same decision. On a transient failure the write is undone so a retry, a GitHub
redelivery or a human pressing the button again, can land the signal and unblock the run. On a
terminal failure there is no run left to strand, so undoing the write would only leave the database
describing reality incorrectly and invite an unclearable retry loop. Webhooks, Slack thread steering,
run cancellation, and the inbox resolve path in `lib/hitlResolve.ts` share the helper so they cannot
disagree.

Four routes refuse to let an admin change shipped content, each with its own code so a client can
tell the guards apart: `DELETE /skills/:id` returns `403` and `BUILTIN_SKILL`,
`DELETE /scanner-patterns/:id` returns `403` and `BUILTIN_PATTERN`, `PUT /scanner-patterns/:id`
returns `400` and `BUILTIN_READONLY_FIELDS` for any field other than the `isActive` toggle, and
`DELETE /model-catalog/:id` returns `409` and `BUILT_IN_MODEL`. A bundle install guards the same
idea from the other side: replacing a seeded built-in or admin-authored global item needs
`overwriteProtected`, else `409` and `PROTECTED_CONTENT_OVERWRITE`, and a refused attempt is audited.
The other per-module guards are `LAST_ORG_ADMIN`, `LAST_TEAM_ADMIN`, `CANNOT_SELF_DEMOTE` and
`CANNOT_SELF_DEACTIVATE`, which stop the last holder of a role from removing it.

### Audit logging

Three helpers write `ConfigAuditLog` rows, 70 call sites in twenty-two route modules. `writeAuditLog`
has 56 calls in twenty modules; `auditConfigWrite` has 10, all in `systemConfig.ts`; and
`writeSystemConfigAudit` has 4, all in `configSettings.ts`. The MCP write hook in
`lib/mcpWriteGuard.ts` also calls `writeAuditLog`, once, to record a bridged write.
`writeAuditLog` inserts a row carrying the action, actor, entity type and id, and JSON snapshots of
the value before and after. `AuditEntityType` is a closed union of twenty-nine entity names, so a new
audited entity is a type change rather than a free-form string. The two config helpers take a
free-form entity type and are best-effort, so an audit failure never fails the config write.

```ts
await writeAuditLog(fastify, {
  action: 'UPDATE', actor, entityType: 'ScannerPattern',
  entityId: row.id, before, after,
});
```

The setting registry is the one entity whose rows are keyed by setting name rather than a UUID, so
its writes share a single sentinel `entityId` and carry the key and scope in the payload instead.
`systemConfig.ts` uses `auditConfigWrite` from the service layer for the same purpose on the
singleton config tables, and skips the write when nothing changed. Per-user credential saves and
removals are audited as `ConnectionCredential` with the last four characters only, and host
credentials and webhook secrets are audited with their last four characters rather than the secret.

### Visibility and scope filtering

Non-admin callers see a filtered slice of every listing, and the predicates are centralised so the
routes cannot drift apart. `requireAuth` resolves the repository permission gate once per request
and stores it on `request.repoAccessGate`, so the synchronous predicates can be called inside
`where` literals; the gate argument to each predicate is required, and may be `undefined`, so a new
call site has to say what it passes.

| Helper | Applies to | Rule |
| --- | --- | --- |
| `memberTeams`, `memberOrgs` | any listing keyed by team or organization | The one definition of "teams or organizations the actor belongs to"; nested under a relation key, never spread |
| `ledTeams` | the repository listing's inactive view | Teams where the actor is `LEAD` or `ADMIN`; the team-scoped write bar |
| `reachableConnections` | repository, work-request, schedule, lesson, workflow, epic and dependency listings | Owning-team or shared-team membership (`memberOrSharedTeams`), ANDed with a fresh enough GitHub permission row when the gate is in `enforce` mode, for git repositories only |
| `buildWorkflowRunVisibilityFilter` | run lists, template lists | Admins see everything; others see global templates, templates owned by one of their teams, or runs whose work request touches a repo they can reach |
| `buildWorkflowRunControlFilter` | cancel, and human-step answers | Narrower than visibility: owning-team members of the repository, members of the template's team, or whoever launched the run; a shared team can see and start runs but not stop or steer the owner's |
| `buildWorkflowHumanStepVisibilityFilter`, `buildWorkflowHumanStepControlFilter` | inbox, Slack actions | Delegate to the run filters through the step's `run` relation |
| `asPlatformAdmin` | any admin-branch cross-tenant read | Runs the query under `runUnscoped` only for admins, keeping the tenant guard live for everyone else |
| `assertOrgAccess`, `authorizeLaunch` | launches | Membership check where the org is derived inside the handler, not from a path parameter, as part of the one launch decision |
| `redactConnection` | every route returning a `Connection` | Strips the AES-GCM envelope columns and exposes only `hasApiToken` |

`asPlatformAdmin` exists because the common shape `user.role === 'ADMIN' ? {} : tenantFilter` makes a
deliberate cross-tenant read indistinguishable from a forgotten filter, which is exactly the bug the
tenant guard is meant to catch. Wrapping the whole call site in `runUnscoped` would disable the guard
for non-admins too, hiding a genuinely missing filter on the path that matters.

The membership predicates are nested rather than spread because the tenant-guard coverage test reads
the source through the TypeScript parser and drops spreads entirely, so a spread would turn a filtered
call site into an unaccounted one. The mechanism behind sharing and the gate is on
[Repository Access and Credentials](./3.4-repository-access-and-credentials.md).

### Route ordering

Fastify matches static segments before parameters within a level, but several modules still declare
literals ahead of their sibling `/:id` route and say why in a comment: `/config/grants/preview`,
`/workspaces` under Slack channels, `/dependencies/unresolved`, and the template `/analytics` and
`/generate` paths. Keeping the declaration order explicit means a later refactor cannot turn a
literal into an accidental id lookup. `/credentials/mine` is the same shape, a literal beside the
`/:id/credential` routes in a module that shares its prefix with `repositories.ts`.
