## Overview

The gateway exposes one versioned REST surface under `/api/v1`. Thirty-five non-test modules live in
[packages/gateway/src/routes/](https://github.com/yorch/auto-swe/tree/b1d8930/packages/gateway/src/routes);
thirty-four of them register routes, and `workflowProjections.ts` holds only shared schemas and
projections. Together they declare 228 handlers as `FastifyPluginAsync` plugins, each mounted with a
URL prefix in
[packages/gateway/src/index.ts#L307-L399](https://github.com/yorch/auto-swe/blob/b1d8930/packages/gateway/src/index.ts#L307-L399).
A route file therefore declares paths relative to its prefix, and the same file can be mounted more
than once.

Sixteen plugins are mounted twice: once under `/api/v1/platform` and once under `/api/v1/admin`,
the latter labelled a deprecated alias kept for one release. `humanStepRoutes` is likewise mounted
at both `/api/v1/human-steps` and `/api/v1/inbox`. The tables below give the canonical prefix; the
alias column notes the second mount where one exists.

The SSE route hijacks the reply, so it caps concurrent streams per user and returns `429` with
`TOO_MANY_STREAMS` beyond the cap. Because hijacking bypasses Fastify's send path, it copies the
reply headers other plugins set, notably the CORS origin header, onto the raw socket.

## Cross-cutting conventions

### Zod schemas and the type provider

Thirty-three of the thirty-four route modules open with
`fastify.withTypeProvider<ZodTypeProvider>()`, `slack.ts` being the exception, which makes `request.body`,
`request.query`, `request.params`, and `request.headers` typed from the Zod schemas declared in the
route options. The compilers are installed once at boot with `setValidatorCompiler` and
`setSerializerCompiler` from `fastify-type-provider-zod`.

Serialization has a guard rail. An `onRoute` hook gives any route that declares no `response` schema
a permissive `z.any()` for `200`, because `fast-json-stringify` otherwise silently strips fields the
schema does not declare. Routes that already declare response schemas are untouched.

```ts
app.addHook('onRoute', (routeOptions) => {
  if (!routeOptions.schema?.response) {
    routeOptions.schema = { ...routeOptions.schema, response: { 200: z.any() } };
  }
});
```

Successful responses wrap the payload as `{ data }`, list responses add
`meta: { limit, offset, total }`, and failures return `{ error: { code, message } }`.

### Boolean query parameters

`booleanQueryParam()` is the only sanctioned way to accept a boolean in a querystring, used by the
human-steps, workflow-runs, agent-library, Slack-channel, and lesson routes. It accepts exactly
`'true'` and `'false'` and transforms to a real boolean; anything else, including `'1'`, `'0'`,
mixed case, and a bare valueless flag that Fastify parses as `''`, fails validation with `400`.

`z.coerce.boolean()` is banned because coercion is `Boolean(input)`, which is `true` for any
non-empty string. An explicit `?flag=false` would silently invert to `true`, so the parameter would
mean its opposite with no error anywhere.

### Idempotency

Three generic run triggers accept an `Idempotency-Key` header: `POST /workflow-templates/:id/runs`,
`POST /webhooks/:token`, and `POST /prd-runs`. They take arbitrary payloads, so there is nothing
intrinsic to derive a stable workflow id from, unlike a work request which has a ticket id. Without
a key the unique index on `ActiveWorkflow.temporalWorkflowId` never fires and a retried trigger
starts a second run.

`workflowIdFromIdempotencyKey(prefix, scopeId, key)` hashes rather than embeds the key, keeping
arbitrary client input out of the Temporal workflow id and bounding its length and charset. The
scope is length-prefixed rather than joined by a separator, because any separator that can also
occur inside `scopeId` lets two different pairs hash to the same string. The digest is truncated to
sixteen hex characters, and a collision surfaces as a `409`, never as two runs merging.

The mechanism is opt-in: a caller sending no key keeps one fresh run per request, which is what a
schedule or a manual retry wants.

Sources: [packages/gateway/src/lib/idempotency.ts:L1-L52](https://github.com/yorch/auto-swe/blob/b1d8930/packages/gateway/src/lib/idempotency.ts#L1-L52) [packages/gateway/src/routes/workflowTemplates.ts:L1655-L1716](https://github.com/yorch/auto-swe/blob/b1d8930/packages/gateway/src/routes/workflowTemplates.ts#L1655-L1716)

### Launching a run: ledger before start

Every route that starts a Temporal workflow goes through `launchTrackedWorkflow`, which writes the
`RunInput` and `ActiveWorkflow` rows first, starts the workflow second, and deletes the rows if the
start fails.

The ordering is deliberate. Starting Temporal first meant a failed DB write left a workflow burning
budget, pushing branches, and opening pull requests with no row to attribute it to, while the
reverse orphan is inert, visible in the dashboard, and operator-recoverable. Writing rows first also
makes dedup atomic: the unique index on `ActiveWorkflow.temporalWorkflowId` decides the winner of two
concurrent submissions, where a read-then-start sequence had a time-of-check-to-time-of-use gap. A
lost race returns `409` with `RUN_CONFLICT`.

### Error mapping

A global error handler converts thrown Fastify errors into the `{ error: { code, message } }`
envelope. Messages on `4xx` are intentional and pass through; `5xx` messages can leak database
constraint text or library internals, so the detail is logged server-side and the client gets a
generic `Internal server error`.

Handlers map domain outcomes to status codes explicitly rather than letting exceptions escape.
Across the route modules, `404` is used 106 times, `400` 62, `409` 41, `403` 32, and `503` 16.

| Source of failure | Detection | Status |
| --- | --- | --- |
| Prisma unique-constraint violation | `isUniqueConstraintError` matches code `P2002` | `409` |
| Known resource collisions | `sendConflict(reply, code, message)` with `REPO_EXISTS`, `TEAM_EXISTS`, `MEMBER_EXISTS` | `409` |
| Temporal execution missing or already closed | `isTerminalSignalError` matches `WorkflowNotFoundError` | write stands, response reports `signalSent: false` |
| Temporal transient failure | anything `isTerminalSignalError` rejects | write is undone so a retry can land the signal |
| Temporal or an integration unreachable | caught around the client call | `503` with a `*_UNAVAILABLE` code |
| Org over its monthly budget | `assertOrgBudget` under a per-org advisory lock | `402` |
| Setting write refused by the registry | `denialStatus(code)` | `400` for `UNKNOWN_SETTING` and `SCOPE_NOT_ALLOWED`, else `403` |
| Regex fails the backtracking probe | `probeRegexBacktracking` overruns the budget | `400` with `REDOS_RISK` |

The terminal-versus-transient split matters wherever a signal is delivered after a database write
that describes the same decision. On a transient failure the write is undone so a retry, a GitHub
redelivery or a human pressing the button again, can land the signal and unblock the run. On a
terminal failure there is no run left to strand, so undoing the write would only leave the database
describing reality incorrectly and invite an unclearable retry loop. Webhooks, Slack thread steering,
and the inbox resolve path share the helper so the three cannot disagree.

### Audit logging

Seventeen route modules write audit rows, 57 call sites in total. `writeAuditLog` inserts a
`ConfigAuditLog` row carrying the action, actor, entity type and id, and JSON snapshots of the value
before and after. `AuditEntityType` is a closed union of twenty-four entity names, so a new audited
entity is a type change rather than a free-form string.

await writeAuditLog(fastify, {
  action: 'UPDATE', actor, entityType: 'ScannerPattern',

});

The setting registry is the one entity whose rows are keyed by setting name rather than a UUID, so
its writes share a single sentinel `entityId` and carry the key and scope in the payload instead.
`systemConfig.ts` uses `auditConfigWrite` from the service layer for the same purpose on the
singleton config tables.

### Visibility and scope filtering

Non-admin callers see a filtered slice of every listing, and the predicates are centralised so the
routes cannot drift apart.

| Helper | Applies to | Rule |
| --- | --- | --- |
| `buildWorkflowRunVisibilityFilter` | run lists, template lists | Admins see everything; others see global templates, templates owned by one of their teams, or runs whose work request touches a repo on one of their teams |
| `buildWorkflowHumanStepVisibilityFilter` | inbox, Slack actions | Delegates to the run filter through the step's `run` relation |
| `asPlatformAdmin` | any admin-branch cross-tenant read | Runs the query under `runUnscoped` only for admins, keeping the tenant guard live for everyone else |
| `assertOrgAccess` | work-request submission | Membership check where the org is derived inside the handler, not from a path parameter |
| `redactConnection` | every route returning a `Connection` | Strips the AES-GCM envelope columns and exposes only `hasApiToken` |

`asPlatformAdmin` exists because the common shape `user.role === 'ADMIN' ? {} : tenantFilter` makes a
deliberate cross-tenant read indistinguishable from a forgotten filter, which is exactly the bug the
tenant guard is meant to catch. Wrapping the whole call site in `runUnscoped` would disable the guard
for non-admins too, hiding a genuinely missing filter on the path that matters.

Repository, work-request, and schedule listings additionally scope by team membership through the
`repository.team.memberships` relation, and dependency edges are filtered to the caller's
organization.
