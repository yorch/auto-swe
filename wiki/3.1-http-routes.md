## Overview

The gateway exposes one versioned REST surface under `/api/v1`. Thirty-eight non-test modules live in
[packages/gateway/src/routes/](https://github.com/yorch/auto-swe/tree/147d054a/packages/gateway/src/routes);
thirty-seven of them register routes, and `workflowProjections.ts` holds only shared schemas and
projections. Together they declare 239 handlers as `FastifyPluginAsync` plugins, each mounted with a
URL prefix in [packages/gateway/src/index.ts:L351-L427](https://github.com/yorch/auto-swe/blob/147d054a/packages/gateway/src/index.ts#L351-L427). A route file therefore declares paths relative to its prefix,
and the same file can be mounted more than once.

Counts on this page come from the source, not from a generated manifest. Modules are the `*.ts` files
in `routes/` that are not `*.test.ts`. Handlers are lines in those files that open a route declaration
on the Fastify instance, that is `app.`, `f.` or `fastify.` followed by `get`, `post`, `put`, `patch`
or `delete`, which leaves out Prisma `delete` calls. Mounts are the
`app.register(<plugin>, { prefix: '/api/v1…' })` calls in `index.ts`: 58 mounts of 40 distinct plugins.
A module can export more than one plugin: `workflowRuns.ts` exports `workflowRunRoutes` and
`stepRegistryRoutes`, `skills.ts` and `agentLibrary.ts` each export an admin plugin and a team-scoped
one, and `modelConfig.ts` exports a team-scoped plugin that `teamRoutes` registers as a child.

Eighteen plugins are mounted twice. Seventeen are mounted under both `/api/v1/platform` and
`/api/v1/admin`, the latter an alias kept for one release: thirteen plugins at the bare prefixes,
three at `/organizations`, and `slackChannelRoutes` at `/slack-channels`. `humanStepRoutes` is the
eighteenth, mounted at both `/api/v1/human-steps` and `/api/v1/inbox`. Two mounts
break the pattern in `index.ts`: `githubInstallationRoutes` is doubled without the deprecation
comment the others carry, and `usageRoutes` is mounted at `/api/v1/platform` only. The tables below give the canonical prefix; the alias column notes the second
mount where one exists.

## Endpoints outside the plugin tree

Six routes are declared inline on the Fastify instance rather than in a route module.

| Method | Path | Purpose | Auth |
| --- | --- | --- | --- |
| `GET` | `/health` | Liveness probe; returns `{ status: 'ok' }` | none |
| `POST` | `/api/auth/sign-in/email` and seven sibling credential paths | better-auth handler under a tightened 20/min rate limit | none |
| `GET`, `POST` | `/api/auth/*` | better-auth catch-all handler | none |
| `GET` | `/api/v1/auth/providers` | Which social providers are configured, so the login page can hide absent buttons | none |
| `POST` | `/api/v1/auth/session-token` | Exchanges a better-auth session cookie for a short-lived JWT | session cookie |
| `GET` | `/api/v1/auth/me` | Current user row, used by the web server for server-side admin guards | any authenticated |

The eight credential paths are the sign-in, magic-link, sign-up, password-reset,
password-change and verification-email endpoints; each is registered as its own `POST` route so it can carry the
20-requests-per-minute limit while `/get-session` stays under the global 200.

## Work requests, runs, and scheduling

### `/api/v1/work-requests`

| Method | Path | Purpose | Role |
| --- | --- | --- | --- |
| `GET` | `/` | List and search work requests; `ticket` is a case-insensitive substring match, results paginated and limited to repositories the caller can reach | `ENGINEER` |
| `POST` | `/` | Submit a work request; takes the repository access decision, checks org budget, then launches a `RunnableWorkflow` as the caller | `ENGINEER` |
| `POST` | `/:id/retry` | Re-run a finished request with an `-rN` workflow-ID suffix against the same ticket, repo, and recorded template snapshot; takes the same access decision as a fresh submit and launches as whoever retried | `ENGINEER` |

Submission and retry both call `decideRepoAccess`, which weighs team membership (owning or shared
team) and the cached GitHub permission together, and refuse with `403` and a reason body. The
mechanism is covered on [Repository Access and Credentials](./3.4-repository-access-and-credentials.md).
Workflow-id allocation also accounts for the pre-host id form of a ticket, so an execution still in
flight under the old id blocks a second one.

### `/api/v1/scheduled-work-requests`

| Method | Path | Purpose | Role |
| --- | --- | --- | --- |
| `GET` | `/` | List schedules visible to the caller; live next/last-fire info comes from the Temporal Schedule, DB columns are bookkeeping only; each row names the user it `actsAs` | `ENGINEER` |
| `POST` | `/` | Create a schedule and its Temporal Schedule; gated like a launch and bound to the creator as `actsAs` | `ENGINEER` |
| `PATCH` | `/:id` | Update a schedule and resync Temporal; an edit that changes what, how often, or whether it runs rebinds `actsAs` to the editor, after a launch decision on them | `ENGINEER` |
| `POST` | `/:id/fire` | Trigger the Temporal Schedule immediately; `SKIP` overlap policy drops the fire if a previous run is live; the firer is gated, but the run launches as the schedule's `actsAs` user | `ENGINEER` |
| `DELETE` | `/:id` | Delete the schedule and its Temporal Schedule; the standing work request and historical runs are kept as audit history; not gated | `ENGINEER` |

Management stays with the owning team: a member of a shared team can see and launch on a repository
but not schedule against it.

### `/api/v1/human-steps` (alias `/api/v1/inbox`) and `/api/v1/human-error-baselines`

| Method | Path | Purpose | Role |
| --- | --- | --- | --- |
| `GET` | `/api/v1/human-steps/` | Pending, or all, human-in-the-loop steps for the caller | `ENGINEER` |
| `GET` | `/api/v1/human-steps/stream` | Server-Sent Events (SSE) stream emitting `change` when the pending set changes | `ENGINEER` |
| `GET` | `/api/v1/human-steps/:id` | One step | `ENGINEER` |
| `POST` | `/api/v1/human-steps/:id/respond` | Resolve a pending step; the validate, atomic-resolve, signal-with-rollback core is shared with the Slack button handler and judges the caller by the run-control predicate | `ENGINEER` |

The SSE route hijacks the reply, so it caps concurrent streams per user and returns `429` with
`TOO_MANY_STREAMS` beyond the cap. Because hijacking bypasses Fastify's send path, it copies the
reply headers other plugins set, notably the CORS origin header, onto the raw socket.

## Workflow templates

All twenty endpoints live under `/api/v1/workflow-templates`. Reads are `ENGINEER`; every mutation
is `LEAD`.

`configSettings.ts` is the one config module that is deliberately **not** behind a blanket admin

write this key at this scope, which is what lets a team lead own their team's policy without an
admin in the loop.

## Cross-cutting conventions

### Zod schemas and the type provider

Thirty-six of the thirty-seven route-registering modules open with
`fastify.withTypeProvider<ZodTypeProvider>()`, `slack.ts` being the exception, which makes `request.body`,
`request.query`, `request.params`, and `request.headers` typed from the Zod schemas declared in the
route options. The compilers are installed once at boot with `setValidatorCompiler` and
`setSerializerCompiler` from `fastify-type-provider-zod`.

Serialization has a guard rail. An `onRoute` hook gives any route that declares no `response` schema
a permissive `z.any()` for `200`, because `fast-json-stringify` otherwise silently strips fields the
schema does not declare. Routes that already declare response schemas are untouched.

```ts
app.addHook('onRoute', (routeOptions) => {
  if (!routeOptions.schema?.response) {
    routeOptions.schema = { ...routeOptions.schema, response: { 200: z.any() } };
  }
});
```

Successful responses wrap the payload as `{ data }`, list responses add
`meta: { limit, offset, total }`, and failures return `{ error: { code, message } }`.

### Boolean query parameters

`booleanQueryParam()` is the only sanctioned way to accept a boolean in a querystring, used by the
human-steps, workflow-runs, agent-library, Slack-channel, and lesson routes. It accepts exactly
`'true'` and `'false'` and transforms to a real boolean; anything else, including `'1'`, `'0'`,
mixed case, and a bare valueless flag that Fastify parses as `''`, fails validation with `400`.

`z.coerce.boolean()` is banned because coercion is `Boolean(input)`, which is `true` for any
non-empty string. An explicit `?flag=false` would silently invert to `true`, so the parameter would
mean its opposite with no error anywhere.

### Idempotency

Three generic run triggers accept an `Idempotency-Key` header: `POST /workflow-templates/:id/runs`,
`POST /webhooks/:token`, and `POST /prd-runs`. They take arbitrary payloads, so there is nothing
intrinsic to derive a stable workflow id from, unlike a work request which has a ticket id. Without
a key the unique index on `ActiveWorkflow.temporalWorkflowId` never fires and a retried trigger
starts a second run.

`workflowIdFromIdempotencyKey(prefix, scopeId, key)` hashes rather than embeds the key, keeping
arbitrary client input out of the Temporal workflow id and bounding its length and charset. The
scope is length-prefixed rather than joined by a separator, because any separator that can also
occur inside `scopeId` lets two different pairs hash to the same string. The digest is truncated to
sixteen hex characters, and a collision surfaces as a `409`, never as two runs merging.

The mechanism is opt-in: a caller sending no key keeps one fresh run per request, which is what a
schedule or a manual retry wants.

### Launching a run: ledger before start

Eight call sites in six route modules start a run through `launchTrackedWorkflow`: work-request
submit and retry, epics, PRD runs, template runs, the `/:token` and `/jira` webhooks, and the Slack
work-request modal. It writes the `RunInput` and `ActiveWorkflow` rows first, starts the workflow
second, and deletes the rows if the start fails. Schedule fires, authoring jobs, and the eval and
maintenance triggers do not go through it; a schedule fire is started by its Temporal Schedule.

The ordering is deliberate. Starting Temporal first meant a failed DB write left a workflow burning
budget, pushing branches, and opening pull requests with no row to attribute it to, while the
reverse orphan is inert, visible in the dashboard, and operator-recoverable. Writing rows first also
makes dedup atomic: the unique index on `ActiveWorkflow.temporalWorkflowId` decides the winner of two
concurrent submissions, where a read-then-start sequence had a time-of-check-to-time-of-use gap. A
lost race returns `409` with `RUN_CONFLICT`.

### Error mapping

A global error handler converts thrown Fastify errors into the `{ error: { code, message } }`
envelope. Messages on `4xx` are intentional and pass through; `5xx` messages can leak database
constraint text or library internals, so the detail is logged server-side and the client gets a
generic `Internal server error`.

Handlers map domain outcomes to status codes explicitly rather than letting exceptions escape.
Counting literal `.status(N)` and `.code(N)` calls in the route modules, `404` appears 112 times,
`400` 68, `409` 45, `403` 38, and `503` 17. Responses sent through a helper such as `sendConflict`
or `repoAccessErrorBody` are not in those figures.

| Source of failure | Detection | Status |
| --- | --- | --- |
| Prisma unique-constraint violation | `isUniqueConstraintError` matches code `P2002` | `409` |
| Known resource collisions | `sendConflict(reply, code, message)` with `REPO_EXISTS`, `TEAM_EXISTS`, `MEMBER_EXISTS` | `409` |
| Repository launch refused | `decideRepoAccess` returns a refusal; epics and PRD runs collect one per repository | `403` with the reason |
| Temporal execution missing or already closed | `isTerminalSignalError` matches `WorkflowNotFoundError` | write stands, response reports `signalSent: false` |
| Temporal transient failure | anything `isTerminalSignalError` rejects | write is undone so a retry can land the signal |
| Temporal or an integration unreachable | caught around the client call | `503` with a `*_UNAVAILABLE` code |
| Org over its monthly budget | `assertOrgBudget` under a per-org advisory lock | `402` |
| Setting write refused by the registry | `denialStatus(code)` | `400` for `UNKNOWN_SETTING` and `SCOPE_NOT_ALLOWED`, else `403` |
| Regex fails the backtracking probe | `probeRegexBacktracking` overruns the budget | `400` with `REDOS_RISK` |

The terminal-versus-transient split matters wherever a signal is delivered after a database write
that describes the same decision. On a transient failure the write is undone so a retry, a GitHub
redelivery or a human pressing the button again, can land the signal and unblock the run. On a
terminal failure there is no run left to strand, so undoing the write would only leave the database
describing reality incorrectly and invite an unclearable retry loop. Webhooks, Slack thread steering,
and the inbox resolve path share the helper so the three cannot disagree.

### Audit logging

Three helpers write `ConfigAuditLog` rows, 60 call sites in nineteen route modules. `writeAuditLog`
has 43 calls in seventeen modules; `auditConfigWrite` has 13, all in `systemConfig.ts`; and
`writeSystemConfigAudit` has 4, all in `configSettings.ts`. `writeAuditLog` inserts a row carrying
the action, actor, entity type and id, and JSON snapshots of the value before and after.
`AuditEntityType` is a closed union of twenty-three entity names, so a new audited entity is a type
change rather than a free-form string. The two config helpers take a free-form entity type and are
best-effort, so an audit failure never fails the config write.

```ts
await writeAuditLog(fastify, {
  action: 'UPDATE', actor, entityType: 'ScannerPattern',
  entityId: row.id, before, after,
});
```

The setting registry is the one entity whose rows are keyed by setting name rather than a UUID, so
its writes share a single sentinel `entityId` and carry the key and scope in the payload instead.
`systemConfig.ts` uses `auditConfigWrite` from the service layer for the same purpose on the

### Visibility and scope filtering

Non-admin callers see a filtered slice of every listing, and the predicates are centralised so the
routes cannot drift apart. `requireAuth` resolves the repository permission gate once per request
and stores it on `request.repoAccessGate`, so the synchronous predicates can be called inside
`where` literals; the gate argument to each predicate is required, and may be `undefined`, so a new
call site has to say what it passes.

| Helper | Applies to | Rule |
| --- | --- | --- |
| `memberTeams`, `memberOrgs` | any listing keyed by team or organization | The one definition of "teams or organizations the actor belongs to"; nested under a relation key, never spread |
| `reachableConnections` | repository, work-request, schedule, lesson, workflow, epic and dependency listings | Owning-team or shared-team membership, ANDed with a fresh enough GitHub permission row when the gate is in `enforce` mode, for git repositories only |
| `buildWorkflowRunVisibilityFilter` | run lists, template lists | Admins see everything; others see global templates, templates owned by one of their teams, or runs whose work request touches a repo they can reach |
| `buildWorkflowRunControlFilter` | cancel, and human-step answers | Narrower than visibility: owning-team members of the repository, members of the template's team, or whoever launched the run; a shared team can see and start runs but not stop or steer the owner's |
| `buildWorkflowHumanStepVisibilityFilter`, `buildWorkflowHumanStepControlFilter` | inbox, Slack actions | Delegate to the run filters through the step's `run` relation |
| `asPlatformAdmin` | any admin-branch cross-tenant read | Runs the query under `runUnscoped` only for admins, keeping the tenant guard live for everyone else |
| `assertOrgAccess` | work-request submission | Membership check where the org is derived inside the handler, not from a path parameter |
| `redactConnection` | every route returning a `Connection` | Strips the AES-GCM envelope columns and exposes only `hasApiToken` |

`asPlatformAdmin` exists because the common shape `user.role === 'ADMIN' ? {} : tenantFilter` makes a
deliberate cross-tenant read indistinguishable from a forgotten filter, which is exactly the bug the
tenant guard is meant to catch. Wrapping the whole call site in `runUnscoped` would disable the guard
for non-admins too, hiding a genuinely missing filter on the path that matters.

The membership predicates are nested rather than spread because the tenant-guard coverage test reads
the source through the TypeScript parser and drops spreads entirely, so a spread would turn a filtered
call site into an unaccounted one. The mechanism behind sharing and the gate is on
[Repository Access and Credentials](./3.4-repository-access-and-credentials.md).

### Route ordering

Fastify matches static segments before parameters within a level, but several modules still declare
literals ahead of their sibling `/:id` route and say why in a comment: `/config/grants/preview`,
`/workspaces` under Slack channels, `/dependencies/unresolved`, and the template `/analytics` and
`/generate` paths. Keeping the declaration order explicit means a later refactor cannot turn a
literal into an accidental id lookup. `/credentials/mine` is the same shape, a literal beside the
`/:id/credential` routes in a module that shares its prefix with `repositories.ts`.
