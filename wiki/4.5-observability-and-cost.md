## Overview

Three concerns share one code path in the worker: what an agent did, what it cost, and whether the run may keep spending. `AgentTracer` collects a per-activity record of tool calls and model calls and writes them to the `agent_traces` table that backs the run viewer. `costTracking.ts` prices each model call, debits a per-run token and dollar ledger, and refuses further calls once a cap is breached. `telemetry.ts` boots the OpenTelemetry SDK so the same events also leave the process as spans, metrics, and log records. The three meet in `persistActivityTrace`, which stamps every trace row with a span's trace and span identifiers, with the spec node that dispatched the activity, and with the team and organization whose spend it is.

Three properties distinguish the design from a plain "log to the database" tracer.

- `agent_traces` is the one place spend is recorded for every workflow, including workflows that keep no `WorkflowRun` or `ActiveWorkflow` ledger row. Rows carry the Temporal workflow id and run id, so they stay attributable, and for such a workflow they are also the ledger its budget is measured against.
- Budgets are layered by what a workflow keeps. A workflow with a ledger row is held to a token tier; one with neither a ledger nor a run is held to a runless token cap; a call a USD cap could not count is refused before it is made. A channel and an organization carry their own monthly dollar caps.
- Every activity attempt is wrapped in an `activity.<type>` span parented on the trace of whoever started the workflow, and a small set of low-cardinality metrics (calls, tokens, cost, budget breaches, run outcomes, activity duration) is exported beside the spans.

Pricing mechanics, the model catalog, and the built-in price table are covered in [Model Catalog and Pricing](./4.7-model-catalog-and-pricing.md); this page keeps only the short summary needed to follow the budget code.

## Implementation

### The tracer pattern

Every activity that calls a model constructs an `AgentTracer`, appends entries as it works, and persists them once. The class holds an ordered in-memory array and a monotonic `seq` counter, plus optional OpenTelemetry identifiers set by `setSpanContext`; `hasSpanContext()` reports whether one has been attached, and `llmTokenTotals()` sums the tokens of the model calls recorded so far ([agentTracer.ts:L112-L132](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/agentTracer.ts#L112-L132), [agentTracer.ts:L183-L194](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/agentTracer.ts#L183-L194)).

A record carries a sequence number, one of three types, an optional name, request and response JSON, a duration, and an optional error string; `model`, `inputTokens`, `outputTokens`, and `costUsd` are populated only on model calls ([agentTracer.ts:L84-L101](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/agentTracer.ts#L84-L101)). The `toolName` column is overloaded by type: a tool name for a tool call, an agent key for a model call, an event name for an activity event. The `agent_traces` schema comment lists the same three kinds ([schema.prisma:L1630](https://github.com/yorch/auto-swe/blob/ae416937/packages/shared/src/prisma/schema.prisma#L1630)).

| Entry | Added by | Records |
| ----- | -------- | ------- |
| `tool_call` | `addToolCall` | Workspace tool invocations such as `bash`, `readFile`, `writeFile` |
| `llm_response` | `addLlmResponse` | One model round trip, with system prompt, user message, output, tokens, and cost; also one embedding call (see below) |
| `activity_event` | `addActivityEvent` | Non-model work such as git operations, test runs, and pull-request creation |

Both request and response payloads pass through `sanitizeJsonValues` before they are stored. Redaction rewrites credentials embedded in URLs, `Authorization` headers, and values that follow key-looking names, then blanks any property whose lowercased key is in `SENSITIVE_KEYS`: strings become `***`, other values `[REDACTED]` ([agentTracer.ts:L10-L58](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/agentTracer.ts#L10-L58)). Truncation then caps each string at 32,000 characters with an explicit `…[truncated N chars]` marker; the limit is sized so that a single bash output or file read rarely exceeds it ([agentTracer.ts:L5-L8](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/agentTracer.ts#L5-L8), [agentTracer.ts:L60-L82](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/agentTracer.ts#L60-L82)).

`persist` takes the ids `{ runId, workflowId, temporalRunId, teamId, orgId }`, the activity type as `nodeId`, the agent key, the attempt, an optional node tag, and a sequence offset. It returns `true` immediately when there are no records and otherwise writes one `createMany`. A missing `runId` does not drop the batch: workflows that keep no `WorkflowRun` row (workflow authoring, scheduled evals, lesson consolidation, repo-access sync, epic planning) have their traces written with `run_id` null and `workflow_id` set. The write's `try`/`catch` swallows every database error and returns `false`, because tracing is bookkeeping and must never fail a run that has already paid a provider ([agentTracer.ts:L215-L275](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/agentTracer.ts#L215-L275)). The boolean exists so the caller can undo its in-process accounting when the write failed (see the runless budget below).

Each row also carries its position in the workflow spec. `nodeTagColumns` maps the activity's node tag onto three columns: `specNodeId` (the key in `spec.nodes`), `recordingId` (the interpreter's recording id, prefixed with the fan-out branch path inside a branch, such as `fan[0]/impl`), and `stepAttempt` (the interpreter's 1-based attempt at that node, distinct from Temporal's own `attempt`) ([activityNodeTag.ts:L25-L36](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/activityNodeTag.ts#L25-L36), [schema.prisma:L1610-L1624](https://github.com/yorch/auto-swe/blob/ae416937/packages/shared/src/prisma/schema.prisma#L1610-L1624)). The `agent_traces` row set is `run_id` (nullable), `workflow_id`, `temporal_run_id`, `node_id`, the three node columns, `agent_key`, `attempt`, `seq`, the call attribution columns, the two OpenTelemetry columns, and `team_id` and `org_id` ([schema.prisma:L1594-L1669](https://github.com/yorch/auto-swe/blob/ae416937/packages/shared/src/prisma/schema.prisma#L1594-L1669)).

### Resolving run, node, attempt, and owner from Temporal

Activities never pass their own identity to the tracer. `activityContext.ts` reads it from the ambient Temporal activity context instead. `currentActivityType()` returns the activity function name and becomes the trace's `nodeId`; `currentAttempt()` returns the one-based retry attempt so the viewer can separate retries; `currentWorkflowId()` reads `Info.workflowExecution` and throws when it is absent, because every activity here is workflow-driven and a missing execution is a programmer error rather than a case to paper over ([activityContext.ts:L9-L43](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/activityContext.ts#L9-L43)). `currentTemporalRunId()` returns Temporal's per-execution run id, or null outside an activity; unlike the workflow id it is unique per execution, since an id can be started again once its earlier execution has closed ([activityContext.ts:L45-L56](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/activityContext.ts#L45-L56)). It is written on every trace row, which is what scopes a runless workflow's spend to one execution, and the run-creation activity stores it on the `WorkflowRun` ([templates.ts:L257](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/templates.ts#L257)).

The spec node is carried by a Temporal header. The interpreter records the node it is dispatching; a workflow interceptor stamps it on each scheduled activity as `x-auto-swe-node`, adding a header and nothing else, so the command stream is unchanged; an activity interceptor decodes it into an `AsyncLocalStorage` before the activity body runs, and `currentNodeTag()` reads it back. A header the worker cannot decode costs attribution, never the run, and an activity scheduled outside a dispatch gets no tag ([nodeTag.ts:L11-L36](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/workflows/nodeTag.ts#L11-L36), [nodeTagInterceptor.ts:L14-L29](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/workflows/nodeTagInterceptor.ts#L14-L29), [activityNodeTag.ts:L38-L63](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/activityNodeTag.ts#L38-L63)).

Whose spend a row is comes from `currentSpendOwner()`. It returns what the activity declared through `withSpendOwner`, else what the workflow's rows say (the run's own connection, the ledger row's repository, the work request's connection, the Slack channel, then the template), else nobody; the lookup is cached for one config window and never throws ([spendOwner.ts:L21-L37](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/spendOwner.ts#L21-L37), [spendOwner.ts:L79-L130](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/spendOwner.ts#L79-L130)). Workflows with no run have no row to derive it from, so their activities declare it: workflow authoring and explaining use the team, lesson consolidation and repo-dependency inference use the connection's team, and a scheduled eval uses the dataset's team, else its organization, else nobody ([generateWorkflowSpec.ts:L152](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/generateWorkflowSpec.ts#L152), [consolidateLessons.ts:L57](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/consolidateLessons.ts#L57), [inferRepoDependencies.ts:L162](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/inferRepoDependencies.ts#L162), [evalHarness.ts:L359-L366](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/evalHarness.ts#L359-L366), [spendOwner.ts:L58-L68](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/spendOwner.ts#L58-L68)).

`persistActivityTrace` composes all of it. It attaches the active span context to the tracer only if the tracer does not already carry one, so a more specific span set earlier wins. It then looks up the `WorkflowRun` id and the spend owner in parallel; a successful lookup stamps the rows with the run id and the owner, a failed lookup leaves them with neither, because a failed run lookup cannot tell a runless workflow from one with a run and stamping the owner on a run's rows would bill that run to its organization twice. Before writing it takes the batch's tokens out of the runless in-process sum and puts them back if the write fails ([activityContext.ts:L97-L138](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/activityContext.ts#L97-L138)). One activity can persist more than one tracer (its own and `runAgent`'s), and each tracer numbers its records from zero, so `reserveSeq` hands out a per-attempt offset, keyed by the attempt's own Temporal `Context`, that keeps the batches' `seq` values from colliding ([activityContext.ts:L81-L95](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/activityContext.ts#L81-L95)). The "set earlier" case matters for `runAgent`: its trace is persisted after its `llm.*` span has ended, so it captures that span's identifiers up front and the rows keep pointing at the span that did the work ([runAgent.ts:L130-L137](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/runAgent.ts#L130-L137)).

### Why persistence belongs in `finally`

The call must sit in a `finally` block, and the reason is concrete. Records accumulate only in process memory until `persist` runs, so a `persist` reachable solely on the success path is skipped entirely when the model call throws. The failed prompt, the tool calls that led to it, and the error string all vanish, and the run viewer shows an activity that produced nothing at exactly the moment an operator needs the transcript. Temporal then retries the activity with a fresh tracer, so nothing later recovers the lost attempt.

`runAgent` shows the canonical shape: the `catch` records a failed `llm_response` carrying the error message and re-raises, while the outer `finally` persists the batch regardless of outcome, unless the caller passed its own tracer and so owns the persist ([runAgent.ts:L273-L293](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/runAgent.ts#L273-L293)). The failed row is not blank: `failedCallAttribution` spreads the call's model, tokens, and cost into it. If usage was already recorded and something after it threw (missing structured output, a parse error), the call was paid for and the recorded attribution is used. If the post-call check raised `BUDGET_EXCEEDED`, the attribution rides on the failure's details. Anything else gets the configured model and no tokens ([llmAttribution.ts:L4-L38](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/llmAttribution.ts#L4-L38)). The helper is shared by the planner, decomposers, review network, memory passes, eval node, and security-review processor, so the usage report prices failed calls and blames the right model. With per-step accounting, steps already debited when a call fails are summed into the failed row too ([runAgent.ts:L273-L283](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/runAgent.ts#L273-L283)).

Activities holding a workspace order the teardown deliberately: `executeImplementation` closes any MCP connection, persists, then continues its cleanup ([executeImplementation.ts:L452-L455](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/executeImplementation.ts#L452-L455)), and `implementerSession` starts the persist, destroys the container, then awaits the write so container teardown and the database round trip overlap ([implementerSession.ts:L314-L319](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/implementerSession.ts#L314-L319)).

### Spend with no ledger: embeddings, trace totals, and the usage report

Not every workflow has an `ActiveWorkflow` ledger row. Channel tasks, PRD runs, authoring, and similar paths keep none, so the ledger cannot be the only record of spend. Three mechanisms close that gap.

**Embeddings.** After each successful `embed`, `generateEmbeddingWithSpec` calls `recordEmbeddingUsage`. It always counts the call in the `llm.*` metrics. Inside an activity it then writes one `llm_response` row with agent key `embedding`, tool name `embedding`, `seq` 0, the character count as input JSON, the token count, and the cost priced from the embedding spec rounded to micro-dollars; a provider that omits usage yields null tokens and cost. The row is stamped with the node tag, the spend owner, and the run id when there is one. Its cost, but deliberately not its tokens, is added to the ledger's `costUsdAccrued` when a ledger row exists, because the per-tier budgets are measured in chat tokens. Outside an activity nothing is written, and any database error is swallowed so a bookkeeping failure never fails the embedding ([embeddings.ts:L100-L125](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/embeddings.ts#L100-L125), [embeddings.ts:L127-L201](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/embeddings.ts#L127-L201)).

**Trace totals.** `sumRunTraceUsage(runId)` sums a run's `agent_traces` rows into cost and token totals, excluding the `embedding` key from tokens for the same reason. The run-finalizing activity uses it when a run has no ledger workflows, so `/runs` shows real cost rather than $0, and `finalizeChannelRun` uses it for channel runs ([traceTotals.ts:L4-L32](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/traceTotals.ts#L4-L32), [templates.ts:L475-L488](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/templates.ts#L475-L488), [channelRun.ts:L255-L263](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/channelRun.ts#L255-L263)).

**The usage report.** The same rows feed `GET /api/v1/platform/usage?window=7|30|90` (default 30), scoped by `teamId` or `orgId` or platform-wide. An ADMIN may read any scope, a team LEAD their team, an ORG_ADMIN their organization; the platform-wide report is ADMIN-only because it includes spend no team owns ([usage.ts:L9-L22](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/routes/usage.ts#L9-L22), [usage.ts:L122-L144](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/routes/usage.ts#L122-L144)). It aggregates `llm_response` rows over whole UTC days. One grouping by model, agent key, and activity serves the totals and the three breakdowns; a second grouping by team and organization serves `byTeam` and `byOrg`; the response also carries a per-day series, the ten most expensive runs, and an `unattributed` bucket for rows with no run. Latency means exclude failed calls, a null model marks a call whose spec could not be resolved, a null team or organization is spend no tenant is derivable for, and at most four window-wide queries run together, then the per-day aggregates three at a time, so a report never holds the gateway's ten-connection pool ([usage.ts:L24-L46](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/routes/usage.ts#L24-L46), [usage.ts:L152-L401](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/routes/usage.ts#L152-L401)). The per-run trace list on the run detail route is a separate read, ordered by creation time then `seq` ([workflowRuns.ts:L450-L470](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/routes/workflowRuns.ts#L450-L470)).

### Pricing a call

A call is priced from the resolved `<provider>/<model-id>` spec alone. `getModelPrice` reads the model catalog first (one read per config-cache window), falls back to the built-in table (`MODEL_PRICES`, a view over `BUILTIN_MODELS`), and otherwise returns a zero rate with `known: false`. It also reports the `source` (`catalog`, `builtin`, or `unknown`) and whether the catalog was readable at all ([costTracking.ts:L37-L47](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L37-L47), [costTracking.ts:L105-L132](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L105-L132)). The lookup is exact; a near-miss spelling is unknown, never priced as its neighbour. Pricing never throws: an unreadable catalog serves the last good read, else the built-in table, and is not queried again for one window ([costTracking.ts:L60-L98](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L60-L98)). `MODEL_PRICE_<SPEC>` environment overrides are not read; the worker names any it finds at startup so the price can be moved into the catalog ([costTracking.ts:L134-L143](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L134-L143), [index.ts:L53-L63](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/index.ts#L53-L63)).

The cost formula takes the provider's total input tokens, which include cached reads and writes, charges the cached portions at per-provider multiples of the input rate (`cacheMultipliers`), and clamps cache counts so a provider that reports them outside the total is costed at no less than plain input ([costTracking.ts:L189-L229](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L189-L229), [builtinModels.ts:L92-L98](https://github.com/yorch/auto-swe/blob/ae416937/packages/shared/src/lib/builtinModels.ts#L92-L98)).

`recordLlmUsage` prices the model that was actually bound for the call. When the caller passes `boundModelSpec`, it is priced as-is; re-resolving the role from the ambient activity context cannot see a channel-level override, an owning-team override the caller chose not to use, or an explicit `key@version` pin, and would price a different model than the one that was paid for. Only when no spec is given is the role re-resolved. If resolution fails, the code substitutes `unknown/unknown` and continues, because failing here would let a malformed configuration burn unlimited tokens: each retry would re-spend at the provider while the counter stayed still and the cap never fired ([costTracking.ts:L401-L429](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L401-L429)). An unpriced model logs a warning and sets `llm.cost_pricing_known=false` on the span; usage is still recorded, so no run is lost to a missing entry. The agent identity is used only for attribution, never as part of the price ([costTracking.ts:L430-L455](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L430-L455)). Embedding calls take the same path through `calculateCostUsd` ([costTracking.ts:L176-L187](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L176-L187)).

### The ledger and the token checks

Accounting for a workflow with a ledger lives on the `ActiveWorkflow` row keyed by `temporalWorkflowId`, which holds `budgetTier`, two BigInt token counters, and a float dollar total ([schema.prisma:L109-L133](https://github.com/yorch/auto-swe/blob/ae416937/packages/shared/src/prisma/schema.prisma#L109-L133)). `recordLlmUsage` updates it with Postgres-side `increment` operations rather than read-modify-write. Concurrency is the reason: the review network runs three reviewers under one settled promise and fan-out branches run in parallel, possibly on different workers, so interleaved read/write pairs would drop increments precisely when spend is highest. The returned row is the authoritative post-increment total, keyed on the `@unique` workflow id so no extra read is needed, and the dollar delta is rounded to micro-dollars so each increment is exactly representable in the float column ([costTracking.ts:L479-L521](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L479-L521)). The per-call metrics are recorded before the ledger is touched, so a call with no ledger row is still counted ([costTracking.ts:L447-L455](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L447-L455)).

A missing ledger row surfaces as Prisma error `P2025`, which is treated as non-fatal: the span gets `llm.workflow_found=false`, and the call is handed to the runless accounting below, which applies only if the workflow also has no `WorkflowRun` ([costTracking.ts:L522-L544](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L522-L544)).

Enforcement happens twice around each call, and `resolveTierLimits` is the single definition both use. It defaults a null tier to `STANDARD`, reads the database-backed tier table, falls back to `BUDGET_LIMITS`, and throws on a tier it cannot find, so a misconfigured tier cannot quietly disable the gate at one site ([costTracking.ts:L277-L297](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L277-L297)).

`assertBudgetAvailable(label)` runs before `generate()`. It reads the workflow identifier from activity context rather than accepting it as a parameter, since a caller-supplied string that matched no row would turn the gate into a permanent no-op. With a ledger row it throws a non-retryable `BUDGET_EXCEEDED` failure when either counter is already at or above its cap; with none it defers to the runless check ([costTracking.ts:L299-L336](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L299-L336)). The comparison is `>=` here and `>` after the call, deliberately: a call landing exactly on the cap is allowed, the next one is not.

`recordLlmUsage` runs after. It writes the increment first and checks the limits second, so the dashboard shows the real overage rather than the last value under the cap. On a breach it counts `workflow.budget_exceeded` for the tier and throws the same non-retryable `BUDGET_EXCEEDED`, carrying the call's own attribution in the failure details so the caller can price the failed trace row ([costTracking.ts:L546-L586](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L546-L586)). Non-retryable is what makes the failure terminal: Temporal does not retry the activity, and the workflow fails instead of re-spending. The post-call check alone cannot prevent overshoot, because a call's cost is unknown until it returns; the pre-call gate turns one overshooting call per concurrent branch into one overshooting call total. It is a gate, not a reservation, and a workflow sitting just under its cap is still allowed one more call of unknown size ([costTracking.ts:L258-L277](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L258-L277)).

A long tool loop would otherwise be checked once, before its first step. `createStepAccounting` (used by agent runs) takes Mastra's `onStepFinish` and debits each finished step through `recordLlmUsage` immediately, then re-runs `assertBudgetAvailable`, so a loop of hundreds of steps cannot overshoot its tier by an unbounded amount, and an aborted call has already recorded every step that completed. A step that exhausts the budget aborts the loop through a merged abort signal (cancellation, the caller's deadline, and the budget stop); the failure is surfaced after `generate` settles, because an aborted generate may resolve rather than throw ([stepAccounting.ts:L10-L113](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/stepAccounting.ts#L10-L113)). `runAgent` runs the gates in a fixed order, the unpriced-model check first and the token gate second ([runAgent.ts:L155-L157](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/runAgent.ts#L155-L157)).

One advisory check rides along. `flagUnregisteredAgentUsage` compares the executing activity against `STEP_REQUIRED_AGENTS` and flags a step that spent tokens on an agent the boot gate never validated, since a missing entry means a deployment boots clean and dies mid-run on a missing model or credential. It only judges activities the gate actually walked, skips steps whose agent comes from the spec (a `null` entry), sets `llm.step_agent_unregistered` on the span unconditionally, and logs once per step-and-agent pair per process ([costTracking.ts:L338-L399](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L338-L399), [stepRequiredAgents.ts:L40-L50](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/config/stepRequiredAgents.ts#L40-L50)).

### Budgets for spend with no ledger

A workflow execution that keeps neither an `ActiveWorkflow` ledger nor a `WorkflowRun` (workflow authoring and explaining, scheduled evals, lesson consolidation, repo-dependency inference) is held to a runless token cap. The ledger here is `agent_traces` itself: an execution's spend is the sum of its persisted `llm_response` rows for that workflow id and Temporal run id (embedding rows excluded), plus the tokens this process has recorded that are not persisted yet, because an activity writes its rows only when it finishes and one eval case can make many calls before then ([runlessBudget.ts:L11-L28](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/runlessBudget.ts#L11-L28), [runlessBudget.ts:L117-L162](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/runlessBudget.ts#L117-L162)).

The in-process sum is a map keyed by `workflowId/temporalRunId`, capped at 1,000 executions with the oldest evicted first. When an activity persists its rows, `takePersistingUsage` removes those tokens from the map before the write, so a budget check running while the write commits never counts them twice, and returns an undo function that `persistActivityTrace` calls if the write failed ([runlessBudget.ts:L30-L87](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/runlessBudget.ts#L30-L87)). The check is a no-op outside an activity and for any execution that has a `WorkflowRun`, which is judged by its own budget, or none. It pairs `>=` before a call with `>` after one, like the tier checks, and a breach is a non-retryable `BUDGET_EXCEEDED` whose details carry `runless: true` and the paid call's attribution ([runlessBudget.ts:L179-L231](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/runlessBudget.ts#L179-L231)). A runless breach does not increment the `workflow.budget_exceeded` metric, which is recorded only on the tier check.

The cap is two registry settings, `workflow.runlessMaxInputTokens` (default 20,000,000) and `workflow.runlessMaxOutputTokens` (default 5,000,000), ADMIN-only, overridable at TEAM and ORGANIZATION, not run-pinned, and resolved against the spend owner of the execution ([registry.ts:L344-L369](https://github.com/yorch/auto-swe/blob/ae416937/packages/shared/src/config/registry.ts#L344-L369), [runlessBudget.ts:L136-L153](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/runlessBudget.ts#L136-L153)). An eval execution runs every case of its dataset under one cap, so `runEvalHarness` wraps the run in `withRunlessCapScale(cases.length, …)` and the setting reads as a per-case allowance ([runlessBudget.ts:L89-L100](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/runlessBudget.ts#L89-L100), [evalHarness.ts:L295](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/evalHarness.ts#L295)).

The bound is approximate by construction. Calls in flight on another worker are invisible until their activity persists, an activity's own tokens are invisible for the moment its write is committing, and the rows of a failed write count only on the worker that made the calls. An unreadable state fails open: the call is not capped and a warning is logged, because a failed read never fails a call that has already been paid for ([runlessBudget.ts:L163-L177](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/runlessBudget.ts#L163-L177)). A run that has a `WorkflowRun` row but no ledger row (a channel task, a PRD run) is checked against neither token cap; its spend is recorded in `agent_traces` and summed at finalize.

#### Dollar caps and the unpriced-model guard

Token caps bind at any price, but a dollar cap cannot count spend on a model with no price. `assertModelPricedForUsdCap` refuses such a call before it is made, and only when a dollar cap is watching it: the channel's monthly cap (`SlackChannel.monthlyBudgetUsdCents`), or the organization's monthly cap, reached through the ledger row's repository for a run or through the trace owner for a runless workflow. On an uncapped path the call proceeds at $0 with `llm.cost_pricing_known=false`. A priced model returns after one cached catalog read; the cap lookups run only for an unpriced one ([usdCapGuard.ts:L17-L93](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/usdCapGuard.ts#L17-L93), [usdCapGuard.ts:L95-L144](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/usdCapGuard.ts#L95-L144)).

The refusal has two typed forms. `MODEL_UNPRICED` is non-retryable and names the model and where to price it (the catalog API or the Catalog tab). `MODEL_PRICE_UNAVAILABLE` is retryable and applies when the catalog could not be read and none was ever read, so "no price" cannot be told from "price not loaded yet": it fails closed, since the cap cannot be trusted to count the call, but retryably, so a database blip does not become a permanent failure ([usdCapGuard.ts:L123-L143](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/usdCapGuard.ts#L123-L143)). `assertRolePricedForUsdCap(role)` resolves the role's model and asks the same question; the implementer and its fix sessions, the reviewers, planner, decomposers, security gate, and memory passes all call it, and the generic agent node, the agent-run activity, and the channel assistant call `assertModelPricedForUsdCap` with the model they bound ([usdCapGuard.ts:L146-L155](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/usdCapGuard.ts#L146-L155), [executeImplementation.ts:L112](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/executeImplementation.ts#L112), [reviewNetwork.ts:L230](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/agents/reviewNetwork.ts#L230), [runAgentTask.ts:L195](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/runAgentTask.ts#L195), [channelAssistant.ts:L439](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/channelAssistant.ts#L439)).

The two dollar caps themselves are enforced outside the per-call path:

- **Channel.** A turn first bails cheaply if the channel's month-to-date accrued spend already meets its cap (`isChannelOverBudgetNow`, which sweeps expired holds before it answers "over"). The cap is then enforced by `reserveChannelTurn`, which atomically increments the accrued total by an estimated cost and decides on the value before its own increment, so at most `headroom / estimate` turns can be in flight whatever the concurrency; `settle` swaps the hold for the real cost. The estimate is derived from the bound model's price over an 8,000-input and 1,500-output token envelope, falling back to a flat $0.05, and an abandoned hold expires after 30 minutes. An over-budget channel gets a friendly refusal rather than a failure ([channelAssistant.ts:L328-L381](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/channelAssistant.ts#L328-L381), [channelAssistant.ts:L386-L447](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/channelAssistant.ts#L386-L447), [channelAssistant.ts:L489-L516](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/channelAssistant.ts#L489-L516), [channelAssistant.ts:L876-L880](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/channelAssistant.ts#L876-L880)). A delegated task run is gated at launch by `isChannelOverBudgetForTask`, since its spend lands on its own ledger at finalize and there is nothing in flight to hold ([channelTask.ts:L72-L84](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/channelTask.ts#L72-L84)).
- **Organization.** The gateway rejects a submission with `ORG_BUDGET_EXCEEDED` and HTTP 402 when `orgMonthSpend` meets the cap. That spend is finalized runs, plus what runs still in flight have accrued so far (a run's ledger row, or its trace rows when it has none), plus runless workflows attributed to the org on their trace rows, read in one `REPEATABLE READ` snapshot. It is best-effort under concurrency, because spend is recorded after the launch returns: it stops new work and is not a hard ceiling ([orgAccess.ts:L29-L35](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/lib/orgAccess.ts#L29-L35), [orgAccess.ts:L51-L76](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/lib/orgAccess.ts#L51-L76), [billing.ts:L26-L63](https://github.com/yorch/auto-swe/blob/ae416937/packages/shared/src/lib/billing.ts#L26-L63)).

### OpenTelemetry wiring

The SDK starts from a preload, not from the entry point. `instrument.ts` calls `initTelemetry('auto-swe-worker')` and is loaded with `node --import` (`tsx --import` in dev), so the SDK and its module hooks are in place before `index.ts`'s import graph loads; called from the entry body it would run after `http` was already bound and patch nothing ([instrument.ts:L1-L13](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/instrument.ts#L1-L13)). The worker-local `initTelemetry` supplies HTTP and Undici instrumentation (Undici covers global `fetch`, which the AI SDK providers and Octokit use), an OTLP gRPC trace exporter, a periodic metric reader over an OTLP gRPC metric exporter, and a batch log-record processor over an OTLP gRPC log exporter, each conditional on the endpoint being set ([telemetry.ts:L14-L36](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/telemetry.ts#L14-L36)). The gateway boots the same shared helper from its own preload under the service name `auto-swe-gateway` with Fastify, HTTP, and Undici instrumentation and the same metric reader, but no log exporter ([gateway instrument.ts:L13](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/instrument.ts#L13), [gateway telemetry.ts:L13-L34](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/lib/telemetry.ts#L13-L34)).

The metric export interval comment still disagrees with the code. The inline comment in the worker's `initTelemetry` says the interval "defaults to 30s when unset/invalid", and the commented sample in `.env.example` says 30000; the resolver both call returns 60,000 milliseconds for an unset, non-finite, or non-positive value ([telemetry.ts:L29-L30](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/telemetry.ts#L29-L30), [.env.example:L358-L359](https://github.com/yorch/auto-swe/blob/ae416937/.env.example#L358-L359), [systemConfig.ts:L692-L695](https://github.com/yorch/auto-swe/blob/ae416937/packages/shared/src/lib/systemConfig.ts#L692-L695)). The code value is the one in force.

The shared helper builds the resource from a service name and package version and starts a `NodeSDK`. With no endpoint configured it logs once and returns a no-op shutdown, so a development machine needs no telemetry infrastructure ([shared/telemetry.ts:L35-L71](https://github.com/yorch/auto-swe/blob/ae416937/packages/shared/src/lib/telemetry.ts#L35-L71)). In `run()`, the worker calls `initMetrics()` right after the encryption-key check, then, when the endpoint is present, installs the Temporal runtime with its own OTel metrics pointed at the same collector (which surfaces task-queue and activity metrics) and with `OtelForwardingLogger` as its logger ([index.ts:L22-L38](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/index.ts#L22-L38)). That logger forwards every SDK log line and every activity `log` call to the normal logger and also emits it as an OpenTelemetry log record exported to Loki; inside an activity the record picks up the active `activity.<type>` span, so Grafana links the line to the trace, Temporal's metadata becomes the record's attributes minus the per-attempt `taskToken`, and an `Error` is exported with its message and stack rather than as `{}` ([otelLogger.ts:L78-L130](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/otelLogger.ts#L78-L130), [otelLogger.ts:L14-L76](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/otelLogger.ts#L14-L76)). Locally the collector is the Grafana LGTM container in the application compose overlay. `activityLog.ts` exposes `logError` and `logWarn`, which forward to the Temporal activity logger only when an activity context is present, so the helpers are inert outside one; pricing code uses them because embedding usage is priced outside an activity too ([activityLog.ts:L1-L13](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/activityLog.ts#L1-L13)).

`Worker.create` registers `activitySpanInterceptor` and `activityNodeTagInterceptor` as activity interceptors, and the node-tag and trace-context workflow modules as workflow interceptors ([index.ts:L87-L107](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/index.ts#L87-L107)).

#### Activity spans

`activitySpanInterceptor` wraps every activity attempt in an `activity.<type>` span from the tracer named `auto-swe-worker`. Without it the `llm.*` spans an activity opens are roots with nothing tying them to one another or to the workflow, and trace rows persisted outside an LLM span carry no trace id at all. Under it, everything an attempt does shares one trace, and the workflow id on the span finds it in Tempo.

The span's parent is the trace context of whoever started the workflow. A client interceptor, installed on the gateway's Temporal client and on the worker's own, writes the caller's W3C context into an `x-auto-swe-trace` header when it starts a workflow; a workflow interceptor copies the header, undecoded, onto every activity and child workflow the workflow schedules; the activity interceptor reads it back with `traceContextFromHeaders`. Every activity of a run therefore shares the starter's trace (a gateway request's, say), and a workflow started without one, such as a schedule, gives each activity its own trace ([temporalTracing.ts:L8-L61](https://github.com/yorch/auto-swe/blob/ae416937/packages/shared/src/lib/temporalTracing.ts#L8-L61), [plugins/temporal.ts:L279](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/plugins/temporal.ts#L279), [temporalClient.ts:L20](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/temporalClient.ts#L20), [traceContextInterceptor.ts:L16-L33](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/workflows/traceContextInterceptor.ts#L16-L33)). A cancelled attempt (`CancelledFailure` or an `AbortError`) is marked `temporal.cancelled` and recorded as outcome `cancelled`, not as an error; any other throw records the exception and sets error status. The official `@temporalio/interceptors-opentelemetry` package is not used, because it pins the 1.x OpenTelemetry SDK beside this repository's 2.x one and runs OpenTelemetry inside the isolate ([activitySpans.ts:L9-L79](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/activitySpans.ts#L9-L79)).

#### Metrics

`metrics.ts` owns six instruments under the meter `auto-swe-worker`. Attributes are low-cardinality on purpose (model spec, agent key, activity type, status, source, tier), never a run, workflow, or ticket id. Instruments are created lazily on first use and again explicitly by `initMetrics()`, because the metrics API has no proxy provider: instruments built at import time, before the preload ran, would be no-ops for the life of the process. `initMetrics()` also seeds zero samples for every `(source, status)` pair and every budget tier, then forces one export without awaiting it, so Prometheus `increase()` has a baseline before the first real event ([metrics.ts:L19-L117](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/metrics.ts#L19-L117)).

| Instrument | Kind | Attributes | Recorded by |
| ---------- | ---- | ---------- | ----------- |
| `llm.calls` | counter | `agent`, `model` | `recordLlmUsage` and each embedding call |
| `llm.tokens` | counter | `agent`, `model`, `direction` (`input` or `output`) | same |
| `llm.cost_usd` | counter | `agent`, `model` | same |
| `workflow.budget_exceeded` | counter | `tier` | post-call tier breach; concurrent breaching calls each count; a runless breach is not counted |
| `workflow.runs.finalized` | counter | `source` (`worker`, `channel`, `eval`, `gateway`), `status` | `finalizeWorkflowRun` (`worker`), `finalizeChannelRun` (`channel`), an eval verdict (`eval`); the gateway adds a dashboard cancel (`gateway`) and an eval that failed to start (`eval`) |
| `activity.duration` | histogram, seconds | `activity`, `outcome` (`success`, `failure`, `cancelled`) | `activitySpanInterceptor` |

The valid `(source, status)` pairs are `worker` with `SUCCESS`, `FAILED`, `TIMED_OUT`, `SKIPPED`, `CANCELLED`; `channel` with `SUCCESS`, `FAILED`; `eval` with `SUCCESS`, `REGRESSION`, `FAILED`; and, from the gateway's own copy of the instrument under the meter `auto-swe-gateway`, `gateway` with `CANCELLED` and `eval` with `FAILED`. A run is counted only by the attempt that actually ended it, so a retry cannot count it twice ([metrics.ts:L19-L32](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/metrics.ts#L19-L32), [metrics.ts:L139-L142](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/metrics.ts#L139-L142), [gateway metrics.ts:L1-L65](https://github.com/yorch/auto-swe/blob/ae416937/packages/gateway/src/lib/metrics.ts#L1-L65), [templates.ts:L592-L598](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/templates.ts#L592-L598), [channelRun.ts:L274-L277](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/channelRun.ts#L274-L277), [evalHarness.ts:L115](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/evalHarness.ts#L115)).

## Usage

More than twenty call sites across the activities and agents follow the pattern, including `executeImplementation`, `runReviewNetwork`, `commitToMemory`, `channelAssistant`, `evalHarness`, and the generic `runAgent` node. The agent key passed to `persistActivityTrace` is the attribution label on every row in the batch, and it need not be a model-backed agent: `createOrUpdatePullRequest` persists under `pr` and `mcpCallTool` under `mcp`, so tool-only activities still produce a viewable transcript ([createOrUpdatePullRequest.ts:L38](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/createOrUpdatePullRequest.ts#L38), [mcpCallTool.ts:L79](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/mcpCallTool.ts#L79)).

Callers should read cost from the `LlmAttribution` that `recordLlmUsage` returns rather than re-pricing the provider's usage object, which keeps the value shown per call identical to the amount debited to the run ledger. `pricingKnown` on it is false when a recorded $0 is an unpriced model rather than a measured zero. Callers that bind their own model pass it as `boundModelSpec`, so the price matches the model that was paid for. On failure, spread `failedCallAttribution(err, modelSpec, recorded)` into the failed `addLlmResponse` so the usage report still prices the call ([costTracking.ts:L246-L256](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/lib/costTracking.ts#L246-L256), [runAgent.ts:L273-L283](https://github.com/yorch/auto-swe/blob/ae416937/packages/worker/src/activities/runAgent.ts#L273-L283)).

A new workflow that keeps no run and calls a model is budgeted without further wiring, because the runless check keys on the workflow and Temporal run ids that every trace row already carries. To have its spend attributed to a team or organization, its activity wraps its body in `withSpendOwner`.
