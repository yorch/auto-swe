## Overview

The dashboard's shared front end sits in four directories under `packages/web/src`: `components/` holds the presentational library, `hooks/` holds the TanStack Query bindings for the gateway REST API (about forty files, one per resource area), `stores/` holds the two Zustand stores, and `lib/` holds the fetch wrapper, formatters, design tokens, graph layout and the pure helpers that sit behind forms and viewers. Route files under `app/` compose these; they own no fetching or styling logic of their own. How those routes are organised is covered in [App Routes and Pages](./5.1-app-routes-and-pages.md).

The organising rule is that server data never lives in a store. Every remote read is a `useQuery` keyed by resource, every write is a `useMutation` that invalidates the keys it touched, and Zustand holds only the two facts that have no server representation: who is signed in, and which team the chrome is filtered to.

A second rule governs the presentation layer: a treatment that appears on more than one page is a primitive, not a class string. Headers, modal action rows, table headers, segmented choices, dropdowns, the run rail and the auth screens each have one component, and a source-reading test (see [Styling](#styling)) fails the build when a colour class names a token the theme does not define.

A feature component reads data through a hook and renders through the primitives; the primitives import `lib/utils`, one another and, for the two dropdowns, React Aria. Every JSON read and write against the `/api/v1` surface goes through `ApiClient`, so bearer-token refresh and error shaping exist in exactly one place. Three call sites deliberately bypass it because the thing they talk to does not speak the gateway's envelope: `authStore` posts to better-auth's `/api/auth/*`, `useOAuthConsent` posts to the OAuth provider's `/api/auth/oauth2/*` and parses `{ error_description }` rather than `{ error: { message } }`, and `useGatewayStatus` probes the unauthenticated `/health`. The approvals inbox's `EventSource` is the fourth, since the browser owns that connection.

`AppShell` picks one of three frames per route. Chromeless routes (`/login`, `/reset-password`) render bare and take their ground from `AuthLayout`; the run detail and template diff pages render inside the chrome but with a full-height `<main>` that manages its own scrolling; every other route sits in a `max-w-[1280px]` column. The chromed branch is a separate `Chrome` component so that `useApprovalsStream` can mount only there, since a hook cannot sit behind the early return for chromeless routes ([AppShell.tsx#L11-L68](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/layout/AppShell.tsx#L11-L68)). Below the `md` breakpoint the sidebar is a modal drawer: `Chrome` marks the page behind it `inert`, and `useNavDrawer` closes it on navigation, Escape and growth past `md`, moves focus into it on open and back to the menu button on close, and traps Tab inside it ([AppShell.tsx#L51-L54](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/layout/AppShell.tsx#L51-L54), [AppShell.tsx#L70-L170](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/layout/AppShell.tsx#L70-L170)).

What the sidebar offers, who sees it and what each page is called is one list, `NAV_GROUPS` in `lib/navigation.ts`. `visibleNavGroups(role)` narrows it with the same `hasRole` the rest of the dashboard uses, `pageTitle` gives the `TopBar` its heading, and `navLabel(href)` returns the string a page must use as its H1, so the sidebar label, the top-bar title and the page heading cannot drift ([navigation.ts#L1-L30](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/navigation.ts#L1-L30), [navigation.ts#L139-L203](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/navigation.ts#L139-L203)).

## Shared Primitives and Conventions

Five conventions carry most of the consistency across pages.

- **One page header.** `PageHeader` takes a `chapter` kicker, a `title`, an optional `subtitle` and a right-aligned `actions` slot, and renders the `<h1>` a route should own; `SectionHeader` is its `<h2>` counterpart with an optional ordinal and hint ([PageHeader.tsx#L3-L77](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/PageHeader.tsx#L3-L77)). The `<h1>` elements in `app/` and `components/` are this one, the run detail page's own heading and the auth screens' `AuthHeading`; forty-eight route files render `<PageHeader`. The run detail page is the exception among routes: it manages its own full-height layout and writes its own heading. A page reachable from the sidebar titles itself with its nav label verbatim, through `navLabel` ([navigation.ts#L5-L14](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/navigation.ts#L5-L14)).
- **One modal action row.** `ModalFooter` is the row every modal ends with: a `ghost` Cancel beside a primary action, right-aligned. Without `onSubmit` the primary button is `type="submit"`, so a modal whose body is a `<form>` submits on Enter; with it, the button is a plain click target. A `submitHref` renders the primary action as a link for an action that navigates. Omitting `submitLabel` yields a read-only modal with a single `secondary` Close, because a lone ghost button reads as disabled ([Modal.tsx#L8-L71](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/Modal.tsx#L8-L71)).
- **Two ways to choose among a few things.** `TabBar` swaps a page's content section, and when its tabs carry an `href` they render as `next/link`s with `aria-current="page"`, so sub-pages stay linkable and prefetched ([TabBar.tsx#L11-L58](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/TabBar.tsx#L11-L58)). `SegmentedControl` is for a time range or view mode: a `<fieldset>` of toggle buttons carrying `aria-pressed`, so the selection is announced rather than conveyed by colour alone ([SegmentedControl.tsx#L10-L60](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/SegmentedControl.tsx#L10-L60)). The workflow viewer's Graph and Outline switch is one.
- **Two dropdowns, one skin.** `Select` is a single-choice dropdown and `Combobox` the searchable one for long, data-driven lists; both are covered under [Dropdowns](#dropdowns).
- **Shared feature chrome.** Where two or more features repeated the same markup it has been extracted next to them: `Rail` for the run detail's right-hand column, `IntegrationFormFooter` for the saved/error outcome and submit button that end every integration tab, `scheduleControls` for the enabled toggle and "Run now" footer of the schedule forms, `VersionTags` and `templateNav` for template pages, `EntityMetaBadges` for scanner patterns and skills, and `AuthLayout` for the sign-in screens.

## Dropdowns

Both dropdowns are built on React Aria Components (`react-aria-components` 1.21.1) rather than a native `<select>`, because Firefox has no customisable native select and a themed list that differs per browser is not a design system. No `<select>` element remains in `app/` or `components/`; thirty-nine files import `Select` and twenty import `Combobox`.

`dropdown.tsx` holds what the two share so they cannot drift: the `DropdownOption` shape (`value`, a `ReactNode` `label`, optional `textValue` for typeahead when the label is not a string, a muted `description` line and `disabled`), the field label, hint and error lines styled like `FieldWrapper`, the popover (as wide as its trigger, scrolling past about eight rows) and the option row with its selected tick ([dropdown.tsx#L14-L37](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/dropdown.tsx#L14-L37), [dropdown.tsx#L117-L157](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/dropdown.tsx#L117-L157)). Three decisions in it are easy to get wrong:

- **The empty string is a real value.** `""` stands for "All", "None" or "inherit" in many call sites, so it is used as the React Aria key unchanged and only `null` means no selection; the hidden native input submits `""`, and a `required` dropdown whose value is `""` counts as missing, as a native select does. `Select.test.tsx` pins both the round trip and the required case ([dropdown.tsx#L24-L30](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/dropdown.tsx#L24-L30), [Select.test.tsx#L32-L38](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/Select.test.tsx#L32-L38), [Select.test.tsx#L81-L97](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/Select.test.tsx#L81-L97)).
- **Native validation, unless the caller supplies an error.** Without an `error` prop the control validates natively, so an empty `required` dropdown blocks its form's submit and `FieldError` explains why ("Choose an option"), since React Aria suppresses the browser's own bubble. With an `error` the control switches to `aria` validation: the error is shown and announced but is never a validity flag, otherwise displaying an error would make the form unsubmittable and the caller could never clear it ([dropdown.tsx#L68-L107](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/dropdown.tsx#L68-L107)).
- **Overlays portal into the open dialog.** A shown `<dialog>` sits in the browser's top layer, above anything portalled to `<body>`, so a dropdown opened inside a modal would render behind it. `Modal` wraps its content in React Aria's `UNSAFE_PortalProvider` with the dialog as the container, and a test asserts the list opens inside the dialog ([Modal.tsx#L181-L187](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/Modal.tsx#L181-L187), [Modal.test.tsx#L68-L80](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/Modal.test.tsx#L68-L80)).

`Select` takes `options`, a string `value` and `onChange`, plus `label`, `hint`, `error`, `compact` (an `h-8` mono control for dense rails and inline editors), `required`, `placeholder`, `name` and an `aria-label` for when there is no visible label. A `value` that matches no option shows the placeholder. The trigger shows the selected option's plain text, not its listbox row, since the tick and description line do not fit one line. `appearance="pill"` renders an inline toolbar chip with an optional `prefix` and no label, hint or error, which is what the `TopBar` team picker uses ([Select.tsx#L20-L47](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/Select.tsx#L20-L47), [Select.tsx#L77-L131](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/Select.tsx#L77-L131), [TopBar.tsx#L85-L97](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/layout/TopBar.tsx#L85-L97)). A hidden native select keeps `name` and `required` working inside an enclosing `<form>`.

`Combobox` is for lists a user would rather type into: users, repositories, templates, teams, agents. It passes the options as `defaultItems`, which React Aria re-reads on every render, so options that arrive after mount still appear and typed text filters by `textValue` (or a string `label`). When nothing matches it shows `emptyMessage` rather than closing silently. The value can only be one of the options, unless `allowsCustomValue` is set, in which case the input text is the value and each option's text must equal its `value`. Its field box is a React Aria `Group`, which carries `data-focus-within`, so focus and disabled state draw on the box the same way they do on the `Select` trigger ([Combobox.tsx#L38-L119](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/Combobox.tsx#L38-L119), [Combobox.test.tsx#L58-L79](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/Combobox.test.tsx#L58-L79)).

The model-spec fields show the custom-value mode in use. `ModelSpecPicker` wraps `Combobox` with `allowsCustomValue`, suggesting the catalog's models of one kind, each with its price as the second line, and still accepting a spec the catalog lacks, such as a model released today or a self-hosted endpoint; saving one yields an advisory warning from the gateway, never a refusal. The empty-state text says the model is not in the catalog and its calls would be recorded at $0. It backs the agent editor's model field and the embeddings tab ([ModelSpecPicker.tsx#L7-L48](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/modelConfig/ModelSpecPicker.tsx#L7-L48), [modelCatalog.ts#L50-L69](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/modelCatalog.ts#L50-L69)). ## The Workflow Graph Renderer

`WorkflowDag` is the read-only viewer used by the template detail, diff and run pages. It wraps React Flow with a `FlowChrome` child (dotted background, minimap and zoom controls) and per-node multi-port handles, and it re-keys its memo on the serialized spec, statuses and diff markers rather than object identity so a 3-second poll that returns unchanged content does not tear down and rebuild every node ([WorkflowDag.tsx#L139-L156](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/WorkflowDag.tsx#L139-L156)). Nodes are non-draggable and non-connectable here; a click selects a node and a second click on the same node clears the selection, while a click on a collapsed group card expands it instead ([WorkflowDag.tsx#L372-L392](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/WorkflowDag.tsx#L372-L392)).

Positions come from `layoutSpec`, which delegates to dagre's network-simplex layered layout rather than a hand-rolled rank assignment; the file records that the previous BFS ranking flattened a 35-node workflow into a single strip ([workflowLayout.ts#L1-L13](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/workflowLayout.ts#L1-L13)). Which fields of which node types count as edges is not re-derived here: `collectEdges` calls `nodeEdges` from the shared spec module, the same function that backs schema ref validation and the interpreter's reachability analysis. `layoutSpec` also accepts `extraEdges`, edges that exist only in the picture, which is how a collapsed group's exits are routed ([workflowLayout.ts#L83-L108](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/workflowLayout.ts#L83-L108)).

**Two display-only folds.** Large templates are mostly bookkeeping, so the viewer can reduce them without ever touching the spec. `foldBookkeeping` hides `set` nodes and `updateDomainState` steps, which have one exit and no effect, by routing every edge that pointed at one straight through to where it leads; a chain that loops back on itself has no destination and is left alone ([foldBookkeeping.ts#L1-L78](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/foldBookkeeping.ts#L1-L78)). It defaults on for graphs past `AUTO_FOLD_NODE_COUNT` (20) nodes, and the viewer can flip it. `foldGroups` then collapses each `group` label into one synthetic card standing where the group's first member stood, with one exit port per distinct outside target so a group with two ways out draws two edges. Only a group that can be collapsed honestly is offered: two or more members and one connected piece, since a group split by a node outside it would fold into a card whose edges appear to skip that node ([foldGroups.ts#L1-L77](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/foldGroups.ts#L1-L77), [foldGroups.ts#L79-L176](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/foldGroups.ts#L79-L176)). Both folds take a `keep` set so the thing the viewer is looking for is never folded away: a node whose status is `FAILED`, `RUNNING` or `PENDING`, one carrying a diff marker, and the selected node; a group holding any of them stays open ([WorkflowDag.tsx#L76-L138](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/WorkflowDag.tsx#L76-L138)). Neither fold runs in the editor, where a hidden node is a node the author cannot change.

`specToFlow` translates the folded spec into React Flow arrays, colouring each edge by kind through `TOKEN` literals and building a descriptive `ariaLabel` per node. A node is named by `nodeDisplayName`, its `title` when it has one and its id otherwise, and the label also announces the group and status; every surface that names a node (card, outline, label) goes through `nodeDisplay.ts` so they agree ([nodeDisplay.ts#L1-L30](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/nodeDisplay.ts#L1-L30), [specToFlow.ts#L138-L152](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/specToFlow.ts#L138-L152)). ## The Outline View

The canvas answers "how is it wired"; the outline answers "what happens, in what order", at any size, with nothing to pan. `WorkflowOutline` lists the same spec as rows in flow order, gathered into sections by `group`, with a status beside each row. It is read-only and view-only: selecting a row only calls `onSelect`, exactly like clicking a node, so the inspector, trace filter and diff marks follow either view ([WorkflowOutline.tsx#L1-L41](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/WorkflowOutline.tsx#L1-L41)).

The ordering is pure logic in `outline.ts`. `flowOrder` walks depth-first from the entry node, following each node's edges in the order `nodeEdges` lists them, so a `cond`'s true branch is read before its false branch and a loop's back-edge adds nothing; nodes the walk never reaches (a half-edited spec) follow in map order instead of vanishing. `buildOutline` places a group's whole membership at the point the walk first meets it and gives each ungrouped node a section with no heading, so the list reads top to bottom as the flow and a group is never split ([outline.ts#L1-L77](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/outline.ts#L1-L77)). Rows are numbered by flow position across the whole spec, so a folded group leaves a visible gap rather than renumbering what follows ([WorkflowOutline.tsx#L89-L100](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/WorkflowOutline.tsx#L89-L100)).

A group heading is a button with `aria-expanded` that folds its rows, and the count beside it reads `ran/total` when a run overlay is present. A group holding the selected row, a `FAILED`, `RUNNING` or `PENDING` step or a diff mark cannot be folded, the same rule the canvas applies, and its heading says why in a tooltip ([WorkflowOutline.tsx#L43-L87](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/WorkflowOutline.tsx#L43-L87), [WorkflowOutline.tsx#L164-L194](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/WorkflowOutline.tsx#L164-L194)). ## The Template Editor

`TemplateEditor` adds authoring to the same canvas: a `NodePalette` rail on the left, drag-to-create and drag-to-connect on the canvas, and a `NodeInspector` rail on the right. It renders the same `FlowChrome` and `FIT_VIEW_OPTIONS` as the viewer, with nodes draggable and connectable and `Delete` bound to node removal. The `spec` prop is the single source of truth and every edit emits through `onChange`; the parent owns validation, saving and version management. Node positions are session-local and are never written into the spec ([TemplateEditor.tsx#L3-L16](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/TemplateEditor.tsx#L3-L16)).

When the parent's spec changes, the editor tells a change in the graph's shape from an edit inside one node. `structureSig` is the entry, each node's id and type and every edge target; if it is unchanged, only each node's label and data are refreshed and positions are kept, so typing in the inspector does not discard every manual drag. If it changed (a node added, removed, retyped or rewired), the nodes are reseeded from the layout ([TemplateEditor.tsx#L109-L139](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/TemplateEditor.tsx#L109-L139)). A live lint runs `validateSpec` on every edit and lists errors and warnings in a collapsible strip above the canvas, each a button that selects the offending node, so an author learns a spec is broken before saving rather than after ([TemplateEditor.tsx#L141-L144](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/TemplateEditor.tsx#L141-L144), [TemplateEditor.tsx#L452-L487](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/TemplateEditor.tsx#L452-L487)).

Palette items carry a Zod-validated payload on a private MIME type, so a drop from anything else is ignored ([NodePalette.tsx#L19-L26](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/NodePalette.tsx#L19-L26)). The primitive table is a `Record` over the node-type union rather than an array, because as an array it once omitted `eval` entirely and there was no way to create that node from the editor ([NodePalette.tsx#L44-L52](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/NodePalette.tsx#L44-L52)). Primitives are grouped Execution, Control flow, Human-in-loop and Advanced, and the ones that require team-admin authoring carry a warning mark.

Structural edits live in `specEdits`, and its central problem is that most edge fields are schema-required. Deleting a node that a `cond` branches to cannot simply clear the field, because the resulting node fails `parseWorkflowSpec` and the user sees a schema error about a node they never touched. Instead a required edge is retargeted to a shared `terminate` placeholder named `unresolved_branch`, created on demand and reused, so the delete succeeds and every orphaned branch is drawn into one obvious node ([specEdits.ts#L1-L37](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/specEdits.ts#L1-L37)). Whether a field is required is asked of `NodeSchema` by trial-clearing it rather than read from a table, since a table is what drifts ([specEdits.ts#L43-L65](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/specEdits.ts#L43-L65)).

`NodeInspector` dispatches per node type to the ten sections in `inspectorSections`, offers a `Select` for each outgoing edge alongside the canvas drag (omitting `— none —` for an edge the schema requires), and exposes a raw-JSON escape hatch. ## Run Detail Components

The run detail route composes its trace viewer itself; the reusable parts live in `components/runs/`. `Rail` supplies the two layout atoms of the right-hand column: `RailSection` (a hairline divider, an ember kicker, then content) and `RailRow` (a label/value line with the rail's row divider) ([Rail.tsx#L8-L42](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/runs/Rail.tsx#L8-L42)). `RunMetaRail` assembles a fixed 270px aside from them (start, end, duration, a Temporal deep link for the workflow id, trace-event count, cost, token totals and the template), then mounts the request block, the eval and autonomy panels, the outcome card and, when a step failed, the failure card ([RunMetaRail.tsx#L39-L185](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/runs/RunMetaRail.tsx#L39-L185)). For a run of the hidden agent-run template the template name renders as plain text rather than a link, because that template's route answers 404.

**Traces are tied to their node and branch.** A trace carries `specNodeId`, the node's key in `spec.nodes`, and `recordingId`, that key prefixed with the fan-out branch path when the step ran inside one (`fan[0]/impl`, `fan[0]/inner[1]/impl`). `traceLinkage.ts` reads those exactly. Traces recorded before those columns existed carry only the Temporal activity name, so the linker falls back to the spec nodes that run that activity (`step.step` for a step, a fixed activity per `agent`, `shell`, `mcp`, `eval` and `containerStep` node), reports every candidate and flags the result ambiguous rather than guessing one ([traceLinkage.ts#L1-L60](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/traceLinkage.ts#L1-L60), [traceLinkage.ts#L127-L159](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/traceLinkage.ts#L127-L159)). Because node ids are free-form, recording ids are never split on `/`: the longest spec key a recording id ends with, as a whole segment, wins, and `fan[n]` segments are matched against the spec's ids the same way ([traceLinkage.ts#L62-L125](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/traceLinkage.ts#L62-L125)).

Selection is a single string, either a spec node id (a graph click) or a recording id (a step row). A spec id selects every execution of that node across all branches, and a fan-out's id selects everything that ran inside it; a recording id selects exactly one branch's execution ([traceLinkage.ts#L161-L200](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/traceLinkage.ts#L161-L200)). `TracesTab` applies the filter, groups the matching traces by recording and attempt, adds a `Branch <path>` header per branch and badges an inferred match `ambiguous`, with a note explaining that such traces were matched by activity name ([TracesTab.tsx#L528-L672](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/app/runs/%5Bid%5D/TracesTab.tsx#L528-L672)). The graph's per-node status comes from `buildDagOverlay`, which folds a run's step records two ways: within one recording id the latest attempt wins, and across branches the worst status wins, because letting the last branch to report win would let a passing sibling paint a failed branch green ([dagOverlay.ts#L1-L60](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/dagOverlay.ts#L1-L60), [page.tsx#L741-L756](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/app/runs/%5Bid%5D/page.tsx#L741-L756)). The observability side of this linkage is in [Observability and Cost](./4.5-observability-and-cost.md).

**Agent runs.** `RunOutcomeCard` branches on the gateway's `isAgentRun` flag, not on the template name, and hands an agent run's result to `AgentRunOutcomeCard`. That card shows the gate verdict (security gate passed, no changes, not published), whether the diff was verified or is the agent's own unverified view of its container, any step or time limit it stopped at, the agent's text, the branch and draft PR when it was published, the changed files with their line deltas, and the diff behind a disclosure with a truncation note. Everything in it is agent-influenced text rendered as text, never HTML, and the one link is the pull request URL, rendered only when it is `https:` ([AgentRunOutcomeCard.tsx#L12-L135](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/runs/AgentRunOutcomeCard.tsx#L12-L135), [RunOutcomeCard.tsx#L28-L35](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/runs/RunOutcomeCard.tsx#L28-L35)). `RunMetaRail` puts an `AgentRunFailureNote` above the generic `FailureCard` when an agent run failed, naming the cause from the error type ([RunMetaRail.tsx#L49-L50](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/runs/RunMetaRail.tsx#L49-L50), [RunMetaRail.tsx#L167-L183](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/runs/RunMetaRail.tsx#L167-L183)). `useRunReRun` picks the endpoint: an agent run is re-run through its own route, since the generic retry answers `409 USE_AGENT_RUN_RERUN`, and one that delivered or whose delivery is unknown asks for confirmation first, naming what it will create ([useRunReRun.ts#L9-L66](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useRunReRun.ts#L9-L66)). ## Reused Form and Table Abstractions

Four abstractions carry most of the repetition out of the pages.

- **`FieldWrapper`** owns the label, hint and error markup for `Input` and `Textarea` (and `Slider`), and exports `fieldDescribedBy` so they compute the same `aria-describedby` value from the same ids, plus `RequiredMark`, which `Select` and `Combobox` reuse so a required dropdown looks like a required input ([FieldWrapper.tsx#L13-L71](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/FieldWrapper.tsx#L13-L71)). `Checkbox` is the standalone counterpart for choices inside a form: a `<label>` wrapping the native input, so the pair is associated without an id. Its `marked` prop shows only the `*`, not the native `required`, which on a checkbox would mean "must be ticked" ([Checkbox.tsx#L5-L43](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/Checkbox.tsx#L5-L43)).
- **`QueryBoundary`** renders the loading, error and settled states of a list query, with a `compact` mode for a section inside a card. Pages that checked only `isLoading` rendered their empty state on a 403 or 500, since `data` is merely undefined then ([QueryBoundary.tsx#L19-L43](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ui/QueryBoundary.tsx#L19-L43)).
- **`Table`** exposes `THead`, `Th`, `TRow` and `Td` with four named header treatments (`mono`, `plain`, `compact`, `dense`), so density is a variant rather than a per-page class string, and an optional sortable header. `TableStatusRow` is a full-width body row for a loading, empty or error state so the header stays in place while the body explains itself. ## Data Fetching

`Providers` creates one `QueryClient` with a 30-second `staleTime` and a single retry, and triggers the auth probe on mount ([Providers.tsx#L7-L27](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/Providers.tsx#L7-L27)). Every remote read goes through a hook in `hooks/`, one file per resource area, exporting query hooks and the mutations that invalidate them.

Query keys are arrays whose first element names the resource, plural for a collection and singular for one entity, with the identifying arguments appended: `['workflows', opts]`, `['workflow', id]`, `['workflow-runs', filters]`, `['workflow-templates', teamId]`, `['workflow-template-version', id, version]`. A run detail is `['workflow-run', id, includeTraces, fullTraces]`, so the trimmed and untrimmed views are distinct cache entries. Nesting a literal segment marks a scoped variant, as in `['workflow-runs', 'by-work-request', workRequestId, limit]`, and `['model-catalog', 'role-pricing']` sits under the `['model-catalog']` prefix its writes invalidate. A mutation invalidates every key its write can affect, and invalidating a shorter prefix covers the longer keys beneath it: cancelling a run invalidates the run, the run list and the workflow list ([useRuns.ts#L268-L278](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useRuns.ts#L268-L278)). Launching or re-running an agent run invalidates `['workflows']` and `['workflow-runs']`, and a catalog write invalidates both the catalog and its unpriced report ([useAgentRuns.ts#L44-L68](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useAgentRuns.ts#L44-L68), [useModelCatalog.ts#L49-L53](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useModelCatalog.ts#L49-L53)). Repository sharing and per-user credentials follow the same pattern: `useSetRepoShares` invalidates `['repositories']`, and the signed-in user's own credentials sit under `['my-repo-credentials']` ([useRepositories.ts#L59-L172](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useRepositories.ts#L59-L172)). The GitHub App installations and the per-host platform credentials each use a single module-level key constant for the list and all three mutations; a host credential row exposes only whether each secret is set and its last four characters ([useGithubInstallations.ts#L42-L75](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useGithubInstallations.ts#L42-L75), [useGithubHostCredentials.ts#L38-L72](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useGithubHostCredentials.ts#L38-L72)). A query that depends on a selection is disabled until there is one: the agent list for the launch form is not fetched without a repository ([useAgentRuns.ts#L17-L32](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useAgentRuns.ts#L17-L32)).

The admin config hooks go further and derive both the path and the key from one slug, through the `sourcedConfigQuery`, `unwrappedConfigQuery` and `configMutation` factories. `configPath` yields `/api/v1/platform/config/<slug>` and `configKey` yields `admin-config-<slug>`. Deriving both from the same string is what keeps a resource from reading one cache entry and invalidating another; the two GET shapes exist because integration configs return `{ data, sources }` so each field can be badged as database- or environment-sourced, while schedule and tuning configs unwrap to `data` alone ([useAdminConfig.ts#L24-L78](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useAdminConfig.ts#L24-L78)). The factories cover GitHub, Slack, issue tracker, knowledge base, Figma, workflow defaults and the consolidation, revalidation and canary schedules; credentials that moved to deployment environment variables have no hook here.

The run viewer's two modes are encoded in `useWorkflowRun`. By default it loads the trimmed trace view (`?includeTraces=true`) once and caches it. Each later poll, every 3 seconds while the run is not terminal and every 30 once it is, reads the run without traces plus only the traces created since a cursor, and merges the new ones into the cached run. The cursor is the server time of the previous tail read minus a 10-second overlap, because a trace's `createdAt` is the writing worker's clock at insert, not commit, so a slow insert can land older than a row already read. No cursor can promise every row behind it has been read, so the tail also reports the run's trace count: when the merged set does not match, or the run has just turned terminal, the poll re-reads every trimmed trace ([useRuns.ts#L36-L151](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useRuns.ts#L36-L151)). With `fullTraces` it fetches the server's untrimmed payloads exactly once and never polls, because full prompts run to tens of kilobytes each. `placeholderData` keeps the previous data on screen while switching modes, but only for the same run id, so navigating between runs never flashes the previous one. `useRunDetail` owns the mode toggle and falls back to the trimmed view, during render rather than in an effect, if a full-payload response fails ([useRuns.ts#L153-L184](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useRuns.ts#L153-L184)); `useRuns.test.tsx` covers the intervals, the cursor and the merge.

Freshness is mostly polling. Run and workflow lists refetch every 10 seconds, a single workflow every 5, per-run eval and autonomy panels every 10, and the admin lists that poll at all every 30. The template-generation job polls at 1.5 seconds until it reaches a terminal state and then stops ([useTemplates.ts#L108-L122](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useTemplates.ts#L108-L122)). A re-run's new `WorkflowRun` row does not exist yet when the retry call returns, so `useRetriedRun` polls the work request's runs every 2 seconds for the one keyed by the Temporal workflow id, for at most 60 seconds, and reports `timedOut` so the caller can fall back to a generic link ([useRuns.ts#L292-L327](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useRuns.ts#L292-L327)). The gateway's own reachability is a 30-second poll with refetch on window focus ([useGatewayStatus.ts#L48-L74](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useGatewayStatus.ts#L48-L74)). The approvals inbox is the one live-refresh surface and the only `EventSource` in the dashboard: `useApprovalsStream` is mounted once in `Chrome` and invalidates the `['approvals']` keys on a `change` event, with the 30-second poll on pending approvals kept as a fallback. Mounting it in the shell replaced three long-lived connections per page, one per consumer of `useApprovals` ([useApprovals.ts#L44-L65](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useApprovals.ts#L44-L65)).

Paginated lists share `useListQuery`, which returns rows as `data` and the pagination block as `meta`; a hook that unwrapped `data` alone dropped the total and made every page report its own length as the row count ([useListQuery.ts#L35-L49](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useListQuery.ts#L35-L49)). Server-side filtered lists (the audit log, security events and eval results) put their filters and offset in the query key and pass `keepPreviousData` as `placeholderData`, so paging or filtering does not blank the table while the next page loads. ## The API Client

`ApiClient` is a class with one instance exported as `api`. It holds the bearer token in memory, mirrors it into a middleware-visible cookie, and sends `credentials: 'include'` on every request so the gateway can authenticate from either the `Authorization` header or the better-auth session cookie without per-call branching ([api.ts#L40-L103](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/api.ts#L40-L103)). It exposes `get`, `post`, `patch`, `put` and `delete` over a general `fetch(path, options)`, which is what a call that needs its own headers uses: an agent-run launch passes an `Idempotency-Key` that way.

Four behaviours are worth naming. A `Content-Type` header is attached only when a body exists, because Fastify rejects a JSON content type with an empty body and that made every dashboard `DELETE` fail against the real gateway ([api.ts#L80-L91](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/api.ts#L80-L91)). A 401 on a request that carried a token triggers one refresh through the session-token bridge and one retry, and a second 401 expires the session; a 401 without a token, such as a wrong password, surfaces as a normal error rather than a redirect loop ([api.ts#L114-L139](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/api.ts#L114-L139)). Expiring the session redirects to `/login?redirect=<here>` only for a caller that had one, a bearer or the better-auth marker cookie, and never from a public auth page, so an anonymous visitor to `/reset-password` is not bounced ([api.ts#L14-L21](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/api.ts#L14-L21), [api.ts#L161-L173](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/api.ts#L161-L173)). Concurrent refreshes share one promise, and a generation counter discards a refresh whose token was superseded by a logout or a fresh login mid-flight ([api.ts#L186-L230](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/api.ts#L186-L230)). A `204` or zero-length response resolves to `undefined` instead of throwing on `.json()`, which would reject a mutation after the server had already applied it and skip the caller's invalidation ([api.ts#L148-L159](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/api.ts#L148-L159)).

Errors are unwrapped from the gateway's `{ error: { message, code } }` envelope into an `ApiError`, which extends `Error` with the message (falling back to `HTTP <status>`), the HTTP `status` and the machine-readable `code`. Existing `errMsg(err)` callers are unchanged, and callers that branch on the outcome read `status` and `code`; `describeLaunchError` is one, mapping `AGENT_RUN_CONCURRENCY_EXCEEDED` and `AGENT_RUNS_DISABLED` to different guidance ([api.ts#L23-L38](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/api.ts#L23-L38), [api.ts#L175-L184](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/api.ts#L175-L184)). A network-level failure is separated from an HTTP error by `isNetworkError`, which matches the `TypeError` messages Chrome, Firefox and Safari produce, and is rewrapped by `gatewayUnreachableMessage` into copy naming the actual API base URL and the CORS setting to check ([networkErrors.ts#L14-L32](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/networkErrors.ts#L14-L32)). The same helper serves the calls that bypass the client, so the OAuth consent screen and the login page say the same thing when the gateway is down. Component-level `catch` blocks narrow the unknown through `errMsg`, and the shared surfaces that display a failure (`QueryBoundary`, `ConfirmModal`, the run-rail panels) all route it through the same helper.

## Client State

Two Zustand stores exist, `authStore` and `teamStore`, and both hold state the server has no per-request representation of.

| Store | Holds | Why it is client state |
| ----- | ----- | ---------------------- |
| `useAuthStore` | The signed-in user, an `isAuthenticated` flag, and the sign-in, sign-out, social-link, magic-link and password-reset actions | The gateway's session lives in a cookie on its own origin. The dashboard needs a synchronous answer to "who is signed in" for chrome, role gating and redirects, before and between queries |
| `useTeamStore` | `selectedTeamId` | A view filter applied across the top bar, the library page and the new-request modal. It is a UI preference with no server row and no URL segment |

`useAuthStore` is where the auth flows live rather than a hook, because they are imperative and cross-cutting: `login` posts to better-auth, probes the resulting session and mints a bearer, while `signInWithProvider` and `linkProvider` post to the OAuth endpoints and navigate the browser to the returned URL, since better-auth answers with JSON rather than a 302 ([authStore.ts#L155-L176](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/stores/authStore.ts#L155-L176), [authStore.ts#L277-L313](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/stores/authStore.ts#L277-L313)). Both sign-in actions take an optional `oauthQuery`, the signed query of an MCP client's pending authorization read from the page's address by `signedOAuthQuery`, which includes only the parameters the authorization server signed because adding any other would invalidate the signature. With one, `login` returns where the authorization continues (the consent page, or the app's own redirect when consent already exists), validated by `resumeUrl`; otherwise it returns `null` ([authStore.ts#L360-L367](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/stores/authStore.ts#L360-L367), [oauthQuery.ts#L1-L36](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/oauthQuery.ts#L1-L36)). A post-sign-in `?redirect=` is passed through `safeRedirectPath`, which resolves it against the real origin and rejects backslashes and control characters, raw or percent-encoded, because a prefix check alone lets `/\evil.com` through ([safeRedirect.ts#L1-L45](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/safeRedirect.ts#L1-L45)).

The session probe returns a three-valued result and this distinction is load-bearing. Only `anonymous`, meaning a 401 or 403 or a 2xx with no user, may clear the local auth cookies. A network failure, a 429 or a 5xx returns `unknown` and says nothing about whether the session is still valid, so a transient gateway hiccup must not sign the user out ([authStore.ts#L178-L226](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/stores/authStore.ts#L178-L226), [authStore.ts#L229-L253](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/stores/authStore.ts#L229-L253)). `hydrateFromSession` reports the same three values to its caller rather than a boolean, so the consent screen does not tell a user their session expired when nobody could check ([authStore.ts#L255-L267](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/stores/authStore.ts#L255-L267)). Session responses are parsed with Zod before being trusted, and the cookie names shared with the Next.js proxy middleware are centralised in `lib/config.ts` so a rename cannot silently break auth in one of the three places that read them.

Role checks do not live in the store. `lib/roles.ts` defers to the shared `roleMeets`, the seniority order the gateway's `requireAuth` applies, and an unknown or missing role meets nothing; `useHasRole(required)` is the hook form, and `teamPermissions` derives what a team detail page may offer from the same rules the team routes enforce ([roles.ts#L1-L25](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/roles.ts#L1-L25), [useHasRole.ts#L1-L8](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useHasRole.ts#L1-L8), [teamPermissions.ts#L1-L40](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/teamPermissions.ts#L1-L40)).

Everything else that looks like state is either query cache or component-local. `useTransientFlag` backs the "saved" and "copied" confirmations, clearing its timer on unmount and on re-trigger so a dismissed modal cannot set state on an unmounted component ([useTransientFlag.ts#L5-L38](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useTransientFlag.ts#L5-L38)). The one durable per-user preference, the run detail layout, is stored on the server rather than in a store, and its union type lives in `@auto-swe/shared` so the gateway schema, the toggle and the hook cannot disagree. The gateway's reachability is likewise a query (`['gateway-status']`) behind `useGatewayStatus`, not store state; the login page and the top bar share one `probeGateway` so "reachable" means the same in both, and the top bar badge reads checking, online, offline or status unknown ([useGatewayStatus.ts#L16-L74](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/hooks/useGatewayStatus.ts#L16-L74), [TopBar.tsx#L115-L124](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/layout/TopBar.tsx#L115-L124)).

## Styling

Tailwind CSS 4 is configured entirely in `app/globals.css` — there is no `tailwind.config`. The file imports `tailwindcss`, declares two explicit `@source` globs so the scanner picks up the app and components trees regardless of the monorepo working directory, and defines the design tokens in an `@theme` block ([globals.css#L1-L20](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/app/globals.css#L1-L20)). PostCSS loads `@tailwindcss/postcss` from `postcss.config.mjs`.

The palette is a single dark theme: an eight-step `ink` surface ramp, a seven-step `paper` text scale, a violet `ember` accent, and five status hues named `moss`, `amber`, `brick`, `dust` and `violet`. Type is three families — Inter for display and body, IBM Plex Mono for labels and numerals. A `@layer base` block keeps legacy semantic aliases such as `--background` pointing at the ramp, and a `@layer utilities` block defines the recurring treatments: `kicker` for the mono small-caps section labels, `label-mono` for field labels, `num` and `tabular` for tabular numerals, and `pulse-dot` for live-status indicators.

Two surfaces cannot use CSS custom properties. Recharts passes `tick={{ fill }}` straight onto an SVG `<text>` as a presentation attribute, and React Flow does the same with an edge marker's colour, and presentation attributes do not resolve `var()`. Rather than inline hex per call site, `lib/palette.ts` holds one copy of the affected tokens as 17 literals, plus a `TOKEN_CSS_VAR` map naming the custom property each mirrors, and `palette.test.ts` parses `globals.css` and fails if any entry stops matching ([palette.ts#L1-L54](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/palette.ts#L1-L54), [palette.test.ts#L12-L32](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/palette.test.ts#L12-L32)). Chart colours in `components/charts/colors.ts` and axis chrome in `chartChrome.tsx` both draw from that one copy, and `STATUS_CHART_COLORS` mirrors the text colour of each `STATUS_META` entry so a pie slice matches the `StatusBadge` beside it. Status pill styling is centralised in `STATUS_META` in `lib/utils.ts`, keyed by every status enum the API returns.

Two further source-reading tests guard against a class of silent failure: a colour class that compiles to nothing. `palette.test.ts` also fails on any default Tailwind colour scale (`gray`, `red`, `indigo`, and so on) in a component, since a default-scale class is valid Tailwind and renders light-theme colours on a dark ground; `amber` and `violet` are excluded there because the project defines its own `amber-400` and `violet-400` ([palette.test.ts#L34-L89](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/palette.test.ts#L34-L89)). `themeClasses.test.ts` fails on any `family-shade` utility that `@theme` does not declare: the status families define only the 400 and 600 shades, so `bg-brick-900` or `text-moss-300` emit no rule and render as bare, uncoloured pills, and `amber` and `violet` are worse, because Tailwind's defaults fill their other shades and `violet-300` would render purple beside a theme `violet-400` that is teal. It scans `app`, `components`, `hooks`, `lib` and `stores`, and reports each offender with its line ([themeClasses.test.ts#L5-L53](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/lib/themeClasses.test.ts#L5-L53)).

## Accessibility

The graph canvas carries the most deliberate work. `dagKeyboardNav` holds the traversal logic as pure functions over node and edge lists, free of React Flow runtime imports so it is unit-testable without a canvas ([dagKeyboardNav.ts#L1-L14](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/dagKeyboardNav.ts#L1-L14)). Right and Left follow edges forward and back, Down and Up step between the other branches of a `cond`, `fanOut` or human gate (`nextSibling` and `prevSibling`), because Right alone only ever reaches the topmost target and left every other branch unreachable from the keyboard, `Home` jumps to the entry node (the one with no incoming edges, topmost when several) and `Enter` opens the anchored node in the inspector. Candidate targets are ordered by vertical position then id, so traversal across a multi-output node is deterministic ([dagKeyboardNav.ts#L16-L40](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/dagKeyboardNav.ts#L16-L40), [dagKeyboardNav.ts#L42-L85](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/dagKeyboardNav.ts#L42-L85)).

Both canvases use `role="application"` with an instructional `aria-label`, chosen so arrow keys deliver raw key events instead of the roving-tabindex behaviour a list role would impose ([WorkflowDag.tsx#L359-L371](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/WorkflowDag.tsx#L359-L371)). Each node gets a descriptive `ariaLabel` built by `specToFlow` announcing type, name, id when titled, group, sublabel and status, a collapsed group card announces its step count and that Enter expands it, and `globals.css` draws a visible focus ring on the React Flow node wrapper so keyboard traversal is visible before selection lands. The viewer treats `Enter` and `Space` alike, either opening the node or expanding a collapsed group, and moves focus to the first expanded member so it is not dropped to `<body>` when the card unmounts ([WorkflowDag.tsx#L192-L296](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/WorkflowDag.tsx#L192-L296)). In the editor the handler is attached in the capture phase so it preempts React Flow's native arrow-key nudge, skips events from inputs, textareas and selects, and opens a node on `Enter` only when a node holds focus so `Enter` on a Controls button still works; `Space` is left to React Flow as its pan-activation key ([TemplateEditor.tsx#L326-L386](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/TemplateEditor.tsx#L326-L386)). The outline is the other route through a graph: a `<nav>` of buttons in one tab stop, which suits screen-reader and keyboard users better than panning a canvas ([WorkflowOutline.tsx#L155-L162](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/WorkflowOutline.tsx#L155-L162)).

Elsewhere the affordances are conventional but centralised in primitives. Form controls get `aria-describedby` and `aria-invalid` from `FieldWrapper`'s shared helper; `Select` and `Combobox` get listbox semantics, arrow-key navigation, typeahead and a described-by hint or error from React Aria; `Modal` derives `aria-labelledby` from its own title so callers cannot forget it, and its close button carries `aria-label="Close"`; `ToggleSwitch` renders `role="switch"` with `aria-checked`; `SegmentedControl` options carry `aria-pressed` inside a labelled `<fieldset>`; a sortable `Th` carries `aria-sort`; `Pagination` is a labelled `<nav>` whose buttons are named Previous and Next page; `TabBar` links carry `aria-current="page"`; `Alert` is `role="alert"` for errors and `role="status"` for success and warning, which is the dashboard's one live-region mechanism; decorative dots and inline icons are `aria-hidden`. The mobile navigation drawer makes the page behind it `inert` and traps Tab, as described under [Architecture](#architecture). Palette items are the one deliberate role override: a `<div role="button">` with `aria-roledescription="draggable palette item"` that also activates on `Enter` and `Space`, because `<button draggable>` does not fire drag events reliably across browsers, and the file carries a Biome suppression recording why ([NodePalette.tsx#L294-L325](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/workflow/NodePalette.tsx#L294-L325)).

## Limitations

- There is no design-system documentation page or component playground; the primitives are discovered by reading `components/ui/`.
- The dashboard ships a single dark theme. There is no light mode and no `prefers-color-scheme` handling, and `globals.css` defines no `prefers-reduced-motion` override for the animated utilities.
- Accessibility coverage is uneven. The graph canvases, the outline, the dropdowns and the form primitives are deliberately handled; most list pages and tabs rely on native semantics alone, the app has no skip link, and the only live regions are the `role` attributes on `Alert`, so a status change that does not render an `Alert` is not announced.
- `ErrorBoundary` logs to the console because the app has no client-side error sink, so a render crash in a user's browser is not reported anywhere the team can see ([ErrorBoundary.tsx#L24-L32](https://github.com/yorch/auto-swe/blob/ae416937/packages/web/src/components/ErrorBoundary.tsx#L24-L32)).
- Live refresh is polling everywhere except the approvals inbox, so a long-open dashboard issues steady background traffic and a run's status can lag by up to its poll interval. The run viewer's trace tail narrows what each poll downloads but not how often it asks.
- The full, untrimmed trace payloads are fetched once and never refreshed, so a run still in progress shows stale full payloads until the viewer switches back to the trimmed view.
- A trace recorded before traces named their node can only be matched by activity name, so it can be attributed to the wrong node or never to a fan-out branch; the viewer flags it `ambiguous` rather than resolving it.
- Editor node positions are session-local and are not persisted with the spec, so a hand-arranged graph reverts to the dagre layout on reload. The bookkeeping and group folds exist only in the viewer; the editor always shows every node.
- A model spec typed into a `ModelSpecPicker` that the catalog does not list is accepted, and its calls are recorded at $0 until an admin prices it. The picker hides retired models but cannot stop a spec typed by hand.
