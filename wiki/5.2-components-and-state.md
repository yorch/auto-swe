## Overview

The dashboard's shared front end sits in four directories under `packages/web/src`: `components/` holds the presentational library, `hooks/` holds the TanStack Query bindings for the gateway REST API, `stores/` holds the two Zustand stores, and `lib/` holds the fetch wrapper, formatters, design tokens and graph layout. Route files under `app/` compose these; they own no fetching or styling logic of their own.

The organising rule is that server data never lives in a store. Every remote read is a `useQuery` keyed by resource, every write is a `useMutation` that invalidates the keys it touched, and Zustand holds only the two facts that have no server representation: who is signed in, and which team the chrome is filtered to.

A second rule governs the presentation layer: a treatment that appears on more than one page is a primitive, not a class string. Headers, modal action rows, table headers, segmented choices, the run rail and the auth screens each have one component, and a source-reading test (see [Styling](#styling)) fails the build when a colour class names a token the theme does not define.

A feature component reads data through a hook and renders through the primitives; the primitives import nothing but `lib/utils` and one another. The `ApiClient` is the only module that calls the gateway's `/api/v1` surface from a hook, so bearer-token refresh and error shaping exist in exactly one place.

`AppShell` picks one of three frames per route. Chromeless routes (`/login`, `/reset-password`) render bare and take their ground from `AuthLayout`; the run detail and template diff pages render inside the chrome but with a full-height `<main>` that manages its own scrolling; every other route sits in a `max-w-[1280px]` column. The chromed branch is a separate `Chrome` component so that `useApprovalsStream` can mount only there, since a hook cannot sit behind the early return for chromeless routes ([AppShell.tsx#L15-L36](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/layout/AppShell.tsx#L15-L36)).

## Shared Primitives and Conventions

Four conventions carry most of the consistency across pages.

- **One page header.** `PageHeader` takes a `chapter` kicker, a `title`, an optional `subtitle` and a right-aligned `actions` slot, and renders the only `<h1>` a route should own; `SectionHeader` is its `<h2>` counterpart with an optional ordinal and hint ([PageHeader.tsx#L3-L72](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/ui/PageHeader.tsx#L3-L72)). Forty-five route files render it. The run detail page is the exception: it manages its own full-height layout and writes its own heading.
- **One modal action row.** `ModalFooter` is the row every modal ends with: a `ghost` Cancel beside a primary action, right-aligned. Without `onSubmit` the primary button is `type="submit"`, so a modal whose body is a `<form>` submits on Enter; with it, the button is a plain click target. Omitting `submitLabel` yields a read-only modal with a single `secondary` Close, because a lone ghost button reads as disabled ([Modal.tsx#L7-L58](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/ui/Modal.tsx#L7-L58)).
- **Two ways to choose among a few things.** `TabBar` swaps a page's content section, and when its tabs carry an `href` they render as `next/link`s with `aria-current="page"`, so sub-pages stay linkable and prefetched ([TabBar.tsx#L11-L58](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/ui/TabBar.tsx#L11-L58)). `SegmentedControl` is for a time range or view mode: a `<fieldset>` of toggle buttons carrying `aria-pressed`, so the selection is announced rather than conveyed by colour alone ([SegmentedControl.tsx#L10-L60](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/ui/SegmentedControl.tsx#L10-L60)).
- **Shared feature chrome.** Where two or more features repeated the same markup it has been extracted next to them: `Rail` for the run detail's right-hand column, `IntegrationFormFooter` for the restart warning, outcome alert and submit button that end every integration tab, `scheduleControls` for the enabled toggle and "Run now" footer of the schedule forms, `VersionTags` and `templateNav` for template pages, `EntityMetaBadges` for scanner patterns and skills, and `AuthLayout` for the sign-in screens.

## The Workflow Graph Renderer

`WorkflowDag` is the read-only viewer used by the template detail, diff and run pages. It wraps React Flow with a `FlowChrome` child (dotted background, minimap and zoom controls) and per-node multi-port handles, and it re-keys its memo on the serialized spec, statuses and diff markers rather than object identity so a 3-second poll that returns unchanged content does not tear down and rebuild every node ([WorkflowDag.tsx#L60-L75](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/WorkflowDag.tsx#L60-L75)). Nodes are non-draggable and non-connectable here; a click selects a node and a second click on the same node clears the selection.

Positions come from `layoutSpec`, which delegates to dagre's network-simplex layered layout rather than a hand-rolled rank assignment; the file records that the previous BFS ranking flattened a 35-node workflow into a single strip ([workflowLayout.ts#L1-L13](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/lib/workflowLayout.ts#L1-L13)). Which fields of which node types count as edges is not re-derived here: `collectEdges` calls `nodeEdges` from the shared spec module, the same function that backs schema ref validation and the interpreter's reachability analysis.

`specToFlow` translates that layout into React Flow arrays, colouring each edge by kind through `TOKEN` literals and building a descriptive `ariaLabel` per node. Its `subLabelFor` switch ends in a `never` assignment, so adding a node type to the spec without giving it a sublabel fails the build instead of silently rendering an unidentifiable card ([specToFlow.ts#L51-L94](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/specToFlow.ts#L51-L94)). It also owns `FIT_VIEW_OPTIONS` (zoom clamped to 0.55 to 1.2). React Flow's `fitViewOptions` prop covers only the initial fit, while `<Controls>` takes its own options and defaults to the canvas `minZoom` of 0.15, at which a wide graph's labels are unreadable; `FlowChrome` therefore passes the same constant to both, so the toolbar's fit button no longer undoes the view the canvas opened with ([specToFlow.ts#L16-L23](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/specToFlow.ts#L16-L23), [flowChrome.tsx#L14-L28](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/flowChrome.tsx#L14-L28)).

`dagNode` draws one source handle per outgoing edge, with `handlePortsFor` expanding a `humanDecision` into one port per option; the comment records that exposing only `onTimeout` made React Flow silently drop every decision branch ([dagNode.tsx#L70-L101](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/dagNode.tsx#L70-L101)). The left-stripe colour for each node type lives in `nodeTypeTone`, a `Record` over the node-type union shared by the canvas node and the palette swatch so the two cannot drift, written as full literal class strings so Tailwind's scanner sees each one ([nodeTypeTone.ts#L1-L24](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/nodeTypeTone.ts#L1-L24)).

Theming React Flow is split across two files for a reason. Its stylesheet is imported by the canvas components after `globals.css`, so a property override in `globals.css` loses at equal specificity and the controls rendered white on the dark canvas. The overrides therefore set React Flow's own `--xy-controls-*` and `--xy-minimap-*` variables on `.react-flow`, and the properties that must be set inline (edge markers, the minimap mask, the dot background) take `TOKEN` literals ([globals.css#L335-L389](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/app/globals.css#L335-L389), [flowChrome.tsx#L7-L28](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/flowChrome.tsx#L7-L28)).

## The Template Editor

`TemplateEditor` adds authoring to the same canvas: a `NodePalette` rail on the left, drag-to-create and drag-to-connect on the canvas, and a `NodeInspector` rail on the right. It renders the same `FlowChrome` and `FIT_VIEW_OPTIONS` as the viewer, with nodes draggable and connectable and `Delete` bound to node removal. The `spec` prop is the single source of truth and every edit emits through `onChange`; the parent owns validation, saving and version management. Node positions are session-local and are never written into the spec ([TemplateEditor.tsx#L1-L16](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/TemplateEditor.tsx#L1-L16)).

Palette items carry a Zod-validated payload on a private MIME type, so a drop from anything else is ignored ([NodePalette.tsx#L16-L26](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/NodePalette.tsx#L16-L26)). The primitive table is a `Record` over the node-type union rather than an array, because as an array it once omitted `eval` entirely and there was no way to create that node from the editor ([NodePalette.tsx#L41-L52](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/NodePalette.tsx#L41-L52)). Primitives are grouped Execution, Control flow, Human-in-loop and Advanced.

Structural edits live in `specEdits`, and its central problem is that most edge fields are schema-required. Deleting a node that a `cond` branches to cannot simply clear the field, because the resulting node fails `parseWorkflowSpec` and the user sees a schema error about a node they never touched. Instead a required edge is retargeted to a shared `terminate` placeholder named `unresolved_branch`, created on demand and reused, so the delete succeeds and every orphaned branch is drawn into one obvious node ([specEdits.ts#L15-L36](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/specEdits.ts#L15-L36)). Whether a field is required is asked of `NodeSchema` by trial-clearing it rather than read from a table, since a table is what drifts ([specEdits.ts#L51-L65](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/specEdits.ts#L51-L65)).

`NodeInspector` dispatches per node type to the ten sections in `inspectorSections`, offers dropdowns for each outgoing edge alongside the canvas drag, and exposes a raw-JSON escape hatch. Its `HAS_CONFIG_SECTION` map is a `Record` over the node-type union so a new type is a compile error rather than an inspector with no fields; `eval` and the four `human*` types map to `false` and render a pointer to JSON mode instead of blank space ([NodeInspector.tsx#L58-L82](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/NodeInspector.tsx#L58-L82)).

## Data Fetching

`Providers` creates one `QueryClient` with a 30-second `staleTime` and a single retry, and triggers the auth probe on mount ([Providers.tsx#L7-L26](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/Providers.tsx#L7-L26)). Every remote read goes through a hook in `hooks/`, one file per resource area, exporting query hooks and the mutations that invalidate them.

Query keys are arrays whose first element names the resource, plural for a collection and singular for one entity, with the identifying arguments appended: `['workflows', opts]`, `['workflow', id]`, `['workflow-runs', filters]`, `['workflow-templates', teamId]`, `['workflow-template-version', id, version]`. A run detail is `['workflow-run', id, includeTraces, fullTraces]`, so the trimmed and untrimmed views are distinct cache entries. Nesting a literal segment marks a scoped variant, as in `['workflow-runs', 'by-work-request', workRequestId]`. A mutation invalidates every key its write can affect, and invalidating a shorter prefix covers the longer keys beneath it: cancelling a run invalidates the run, the run list and the workflow list ([useRuns.ts#L139-L149](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/hooks/useRuns.ts#L139-L149)). Repository sharing and per-user credentials follow the same pattern: `useSetRepoShares` invalidates `['repositories']`, and the signed-in user's own credentials sit under `['my-repo-credentials']` ([useRepositories.ts#L84-L154](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/hooks/useRepositories.ts#L84-L154)). GitHub App installations use a single module-level key constant for the list and all three mutations ([useGithubInstallations.ts#L37-L71](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/hooks/useGithubInstallations.ts#L37-L71)).

The admin config hooks go further and derive both the path and the key from one slug, through the `sourcedConfigQuery`, `unwrappedConfigQuery` and `configMutation` factories. `configPath` yields `/api/v1/platform/config/<slug>` and `configKey` yields `admin-config-<slug>` (with `oauth/google` flattened to `oauth-google`). Deriving both from the same string is what keeps a resource from reading one cache entry and invalidating another; the two GET shapes exist because integration configs return `{ data, sources }` so each field can be badged as database- or environment-sourced, while schedule and tuning configs unwrap to `data` alone ([useAdminConfig.ts#L30-L70](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/hooks/useAdminConfig.ts#L30-L70)).

The run viewer's two modes are encoded in `useWorkflowRun`. By default it fetches the trimmed trace view (`?includeTraces=true`) and polls every 3 seconds while the run is `RUNNING` and every 30 seconds once it is not. With `fullTraces` it fetches the server's untrimmed payloads exactly once and never polls, because full prompts run to tens of kilobytes each and re-downloading them every few seconds is the cost the trim exists to avoid. `placeholderData` keeps the previous data on screen while switching modes, but only for the same run id, so navigating between runs never flashes the previous one ([useRuns.ts#L33-L59](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/hooks/useRuns.ts#L33-L59)); `useRuns.test.tsx` asserts both intervals.

Freshness is mostly polling. Run and workflow lists refetch every 10 seconds, a single workflow every 5, per-run eval and autonomy panels every 10, and admin lists every 30. The template-generation job polls at 1.5 seconds until it reaches a terminal state and then stops ([useTemplates.ts#L112-L122](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/hooks/useTemplates.ts#L112-L122)). The approvals inbox is the one live-refresh surface and the only `EventSource` in the dashboard: `useApprovalsStream` is mounted once in `Chrome` and invalidates the `['approvals']` keys on a `change` event, with the 30-second poll on pending approvals kept as a fallback. Mounting it in the shell replaced three long-lived connections per page, one per consumer of `useApprovals` ([useApprovals.ts#L44-L65](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/hooks/useApprovals.ts#L44-L65)).

Paginated lists share `useListQuery`, which returns rows as `data` and the pagination block as `meta`; a hook that unwrapped `data` alone dropped the total and made every page report its own length as the row count ([useListQuery.ts#L35-L49](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/hooks/useListQuery.ts#L35-L49)). Only `useUserPreferences` updates optimistically, snapshotting the previous value in `onMutate`, restoring it in `onError` and reconciling in `onSettled` ([useUserPreferences.ts#L40-L57](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/hooks/useUserPreferences.ts#L40-L57)).

## The API Client

`ApiClient` is a class with one instance exported as `api`. It holds the bearer token in memory, mirrors it into a middleware-visible cookie, and sends `credentials: 'include'` on every request so the gateway can authenticate from either the `Authorization` header or the better-auth session cookie without per-call branching ([api.ts#L61-L71](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/lib/api.ts#L61-L71)).

Four behaviours are worth naming. A `Content-Type` header is attached only when a body exists, because Fastify rejects a JSON content type with an empty body and that made every dashboard `DELETE` fail against the real gateway ([api.ts#L50-L59](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/lib/api.ts#L50-L59)). A 401 on a request that carried a token triggers one refresh through the session-token bridge and one retry, and a second 401 expires the session; a 401 without a token, such as a wrong password, surfaces as a normal error rather than a redirect loop ([api.ts#L82-L107](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/lib/api.ts#L82-L107)). Concurrent refreshes share one promise, and a generation counter discards a refresh whose token was superseded by a logout or a fresh login mid-flight ([api.ts#L150-L194](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/lib/api.ts#L150-L194)). A `204` or zero-length response resolves to `undefined` instead of throwing on `.json()`, which would reject a mutation after the server had already applied it and skip the caller's invalidation ([api.ts#L116-L127](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/lib/api.ts#L116-L127)).

Errors are unwrapped from the gateway's `{ error: { message } }` envelope, falling back to `HTTP <status>`. A network-level failure is separated from an HTTP error by `isNetworkError`, which matches the `TypeError` messages Chrome, Firefox and Safari produce, and is rewrapped by `gatewayUnreachableMessage` into copy naming the actual API base URL and the CORS setting to check ([networkErrors.ts#L1-L32](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/lib/networkErrors.ts#L1-L32)). Component-level `catch` blocks narrow the unknown through `errMsg`, and the shared surfaces that display a failure (`QueryBoundary`, `ConfirmModal`, the run-rail panels) all route it through the same helper.

## Client State

Two Zustand stores exist, `authStore` and `teamStore`, and both hold state the server has no per-request representation of.

| Store | Holds | Why it is client state |
| ----- | ----- | ---------------------- |
| `useAuthStore` | The signed-in user, an `isAuthenticated` flag, and the sign-in, sign-out, social-link, magic-link and password-reset actions | The gateway's session lives in a cookie on its own origin. The dashboard needs a synchronous answer to "who is signed in" for chrome, role gating and redirects, before and between queries |
| `useTeamStore` | `selectedTeamId` | A view filter applied across the top bar, the library page and the new-request modal. It is a UI preference with no server row and no URL segment |

`useAuthStore` is where the auth flows live rather than a hook, because they are imperative and cross-cutting: `login` posts to better-auth, probes the resulting session and mints a bearer, while `signInWithProvider` and `linkProvider` post to the OAuth endpoints and navigate the browser to the returned URL, since better-auth answers with JSON rather than a 302 ([authStore.ts#L254-L292](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/stores/authStore.ts#L254-L292)).

The session probe returns a three-valued result and this distinction is load-bearing. Only `anonymous`, meaning a 401 or 403 or a 2xx with no user, may clear the local auth cookies. A network failure, a 429 or a 5xx returns `unknown` and says nothing about whether the session is still valid, so a transient gateway hiccup must not sign the user out ([authStore.ts#L167-L240](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/stores/authStore.ts#L167-L240)). Session responses are parsed with Zod before being trusted, and the cookie names shared with the Next.js proxy middleware are centralised in `lib/config.ts` so a rename cannot silently break auth in one of the three places that read them.

Everything else that looks like state is either query cache or component-local. `useTransientFlag` backs the "saved" and "copied" confirmations, clearing its timer on unmount and on re-trigger so a dismissed modal cannot set state on an unmounted component ([useTransientFlag.ts#L5-L38](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/hooks/useTransientFlag.ts#L5-L38)). The one durable per-user preference, the run detail layout, is stored on the server rather than in a store, and its union type lives in `@auto-swe/shared` so the gateway schema, the toggle and the hook cannot disagree.

## Styling

Tailwind CSS 4 is configured entirely in `app/globals.css` — there is no `tailwind.config`. The file imports `tailwindcss`, declares two explicit `@source` globs so the scanner picks up the app and components trees regardless of the monorepo working directory, and defines the design tokens in an `@theme` block ([globals.css#L1-L20](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/app/globals.css#L1-L20)). PostCSS loads `@tailwindcss/postcss` from `postcss.config.mjs`.

The palette is a single dark theme: an eight-step `ink` surface ramp, a seven-step `paper` text scale, a violet `ember` accent, and five status hues named `moss`, `amber`, `brick`, `dust` and `violet`. Type is three families — Inter for display and body, IBM Plex Mono for labels and numerals. A `@layer base` block keeps legacy semantic aliases such as `--background` pointing at the ramp, and a `@layer utilities` block defines the recurring treatments: `kicker` for the mono small-caps section labels, `label-mono` for field labels, `num` and `tabular` for tabular numerals, and `pulse-dot` for live-status indicators.

Two surfaces cannot use CSS custom properties. Recharts passes `tick={{ fill }}` straight onto an SVG `<text>` as a presentation attribute, and React Flow does the same with an edge marker's colour, and presentation attributes do not resolve `var()`. Rather than inline hex per call site, `lib/palette.ts` holds one copy of the affected tokens as 17 literals, plus a `TOKEN_CSS_VAR` map naming the custom property each mirrors, and `palette.test.ts` parses `globals.css` and fails if any entry stops matching ([palette.ts#L1-L54](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/lib/palette.ts#L1-L54)). Chart colours in `components/charts/colors.ts` and axis chrome in `chartChrome.tsx` both draw from that one copy, and `STATUS_CHART_COLORS` mirrors the text colour of each `STATUS_META` entry so a pie slice matches the `StatusBadge` beside it. Status pill styling is centralised in `STATUS_META` in `lib/utils.ts`, keyed by every status enum the API returns.

Two further source-reading tests guard against a class of silent failure: a colour class that compiles to nothing. `palette.test.ts` also fails on any default Tailwind colour scale (`gray`, `red`, `indigo`, and so on) in a component, since a default-scale class is valid Tailwind and renders light-theme colours on a dark ground. `themeClasses.test.ts` fails on any `family-shade` utility that `@theme` does not declare: the status families define only the 400 and 600 shades, so `bg-brick-900` or `text-moss-300` emit no rule and render as bare, uncoloured pills, and `amber` and `violet` are worse, because Tailwind's defaults fill their other shades and `violet-300` would render purple beside a theme `violet-400` that is teal ([themeClasses.test.ts#L3-L53](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/lib/themeClasses.test.ts#L3-L53)).

## Accessibility

The graph canvas carries the most deliberate work. `dagKeyboardNav` holds the traversal logic as pure functions over node and edge lists, free of React Flow runtime imports so it is unit-testable without a canvas ([dagKeyboardNav.ts#L1-L8](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/dagKeyboardNav.ts#L1-L8)). Arrow keys walk edges, `Home` jumps to the entry node (the one with no incoming edges, topmost when several) and `Enter` opens the anchored node in the inspector. Candidate targets are ordered by vertical position then id, so traversal across a multi-output `cond` or `fanOut` is deterministic ([dagKeyboardNav.ts#L16-L40](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/dagKeyboardNav.ts#L16-L40)).

Both canvases use `role="application"` with an instructional `aria-label`, chosen so arrow keys deliver raw key events instead of the roving-tabindex behaviour a list role would impose ([WorkflowDag.tsx#L150-L162](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/WorkflowDag.tsx#L150-L162)). Each node gets a descriptive `ariaLabel` built by `specToFlow` announcing type, id, sublabel and status, and `globals.css` draws a visible focus ring on the React Flow node wrapper so keyboard traversal is visible before selection lands. The viewer treats `Enter` and `Space` alike. In the editor the handler is attached in the capture phase so it preempts React Flow's native arrow-key nudge, skips events from inputs, textareas and selects, and opens a node on `Enter` only when a node holds focus so `Enter` on a Controls button still works; `Space` is left to React Flow as its pan-activation key ([TemplateEditor.tsx#L285-L338](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/TemplateEditor.tsx#L285-L338)).

Elsewhere the affordances are conventional but now centralised in primitives. Form controls get `aria-describedby` and `aria-invalid` from `FieldWrapper`'s shared helper; `Modal` derives `aria-labelledby` from its own title so callers cannot forget it, and its close button carries `aria-label="Close"`; `ToggleSwitch` renders `role="switch"` with `aria-checked`; `SegmentedControl` options carry `aria-pressed` inside a labelled `<fieldset>`; `TabBar` links carry `aria-current="page"`; `Alert` is `role="alert"` for errors and `role="status"` for success and warning, which is the dashboard's one live-region mechanism; decorative dots and inline icons are `aria-hidden`. Palette items are the one deliberate role override: a `<div role="button">` with `aria-roledescription="draggable palette item"` that also activates on `Enter` and `Space`, because `<button draggable>` does not fire drag events reliably across browsers, and the file carries a Biome suppression recording why ([NodePalette.tsx#L294-L325](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/workflow/NodePalette.tsx#L294-L325)).

## Limitations

- There is no design-system documentation page or component playground; the primitives are discovered by reading `components/ui/`.
- The dashboard ships a single dark theme. There is no light mode and no `prefers-color-scheme` handling, and `globals.css` defines no `prefers-reduced-motion` override for the animated utilities.
- Accessibility coverage is uneven. The graph canvases and the form primitives are deliberately handled; most list pages and tabs rely on native semantics alone, the app has no skip link, and the only live regions are the `role` attributes on `Alert`, so a status change that does not render an `Alert` is not announced.
- `ErrorBoundary` logs to the console because the app has no client-side error sink, so a render crash in a user's browser is not reported anywhere the team can see ([ErrorBoundary.tsx#L24-L32](https://github.com/yorch/auto-swe/blob/147d054a/packages/web/src/components/ErrorBoundary.tsx#L24-L32)).
- Live refresh is polling everywhere except the approvals inbox, so a long-open dashboard issues steady background traffic and a run's status can lag by up to its poll interval.
- The full, untrimmed trace payloads are fetched once and never refreshed, so a run still in progress shows stale full payloads until the viewer switches back to the trimmed view.
- Editor node positions are session-local and are not persisted with the spec, so a hand-arranged graph reverts to the dagre layout on reload.
