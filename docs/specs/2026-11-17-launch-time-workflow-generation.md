# Launch-time workflow generation (design)

Goal: at launch a user states what they want done; the platform proposes existing templates and a
generated workflow (a deterministic skeleton plus agentic nodes), shows the plan, and starts the run
only after the launcher approves exactly that plan.

## Decisions

Made with the product owner:

1. A human approves every generated plan before the run starts. No auto-start path.
2. Scope: repo-bound runs for engineering and for any launchable library agent.
3. Entry points: dashboard `/start`, REST API + CLI, Slack channel assistant.
4. Routing: a router ranks existing templates; the user chooses between them and "generate new".
5. Freedom: a mandatory core and free ends (see Decision 8). No shell, container, MCP or
   authored-command nodes.
6. Library-agent plans (anything other than the implementer path) are output-only in v1.
7. An approved plan runs through one hidden system template, not through per-plan templates.
8. Canonical core, free ends. For a delivering plan the mandatory region is not described by rules
   over an arbitrary graph; it must equal the shipped `ticket-to-merge` core node for node. The
   generator writes only the nodes before the core and, optionally, after the human merge wait.

Defaults taken after adversarial review (changeable):

- Service principals cannot create or approve plans.
- A Slack plan is approved only by the user whose message created it, in the same channel.
- Pull requests opened by a generated plan are excluded from PR-evaluation `auto` mode.
- Plan creation is rate-limited per user (registry settings).

## Facts this design rests on

- A run launches only from an ACTIVE template version (`launchableTemplateWhere`); DRAFT is not
  launchable. `createWorkflowRun` reads `WorkflowTemplateVersion` and writes `WorkflowRun.specSnapshot`,
  `agentVersions`, `pinnedSettings`, `skillRevisions`.
- Template writes need LEAD on the owning team. A generated version cannot be promoted or activated
  without a review by someone other than its generator (`SELF_REVIEW_FORBIDDEN`).
- The hidden-template mechanism is `isSystemTemplate` / `EXCLUDE_SYSTEM_TEMPLATES`: null team, a
  `system:` origin, `404` on every template route. Agent runs use it.
- `generateWorkflowSpec` returns `{ spec, summary, attempts }`; its catalog is narrowed only by
  `teamId` and `allowShell`, and it lists agents on `NON_LAUNCHABLE_AGENT_KEYS`.
- The LLM security gate runs inside `executeImplementation`, the fix paths, decomposition and agent-run
  finalize, not as a node. `applyRecipe` and other steps push without it.
- `runReviewNetwork` and the implementation steps accept step-level `systemPrompt`, `tools`,
  `allowedPaths` and `testIntegrity`; `onFail: 'warn'`, `onFailure` and `cond` edges can route around any
  node. Existence of a node therefore proves nothing about what it does.
- Agent-run ceilings and admission (`wouldAdmitNewRun`, `clampToCeiling`) apply only to the Agent Run
  template.
- `WorkflowRun.template` is `onDelete: Restrict`; templates with runs cannot be deleted.

## Design

### 1. The plan

A `RunPlan` row holds: the owning user (never a service principal), team, repository, agent (for
library-agent plans), intent text, router candidates, the generated `WorkflowSpec`, the `validateSpec`
and skeleton reports, a cost estimate, the catalog hash and model, the resolved `key@version` of every
agent the spec names, a status (`PENDING`, `APPROVED`, `LAUNCHED`, `REJECTED`, `EXPIRED`) and an
expiry. Approval is an atomic `updateMany where status = PENDING`, so a second approval launches
nothing. Approval re-checks the owner, repository reach under the access gate, role, quotas and
budget, and refuses (it never regenerates or re-injects) when any pinned agent version, the setting
snapshot or the catalog hash no longer matches. A refused plan is regenerated by the user.

### 2. Running an approved plan

One hidden GLOBAL system template, "Planned Run" (reserved `system:planned-run` origin, null team,
guarded like Agent Run: absent from lists, pickers, schedules, bundles; `404` on template routes; not
creatable by name). Launch parameters carry only the plan id. The worker, when it creates the run for
that template, loads the approved plan and pins **its** spec as `WorkflowRun.specSnapshot` instead of
the template's placeholder version, and refuses if the plan is not `APPROVED`, was not approved by the
launcher, or belongs to another repository. No per-plan template rows exist, so there is nothing to
re-run by id, schedule, attach a webhook to, export or accumulate. Retry of a planned run is refused
(`USE_PLAN_RERUN`): the user creates a new plan. Run provenance records the plan id, the intent and the
model.

"Save to library" creates an ordinary DRAFT template from the plan's spec for a LEAD, which then needs
an independent review like any generated draft. Choosing an existing template in the preview skips the
plan spec and launches that template through the normal path, with that path's own checks.

Planned runs charge the owning team's budget and concurrency like any run, and additionally take the
agent-run admission (`wouldAdmitNewRun`) and step/wall-clock ceilings when the plan is built on a
library agent, so a generated spec cannot exceed what an agent run could.

### 3. Skeleton policy (a canonical core and free ends)

`applySkeletonPolicy(spec, mode)` in shared runs at generation, and its **check** half
(`checkSkeletonPolicy`) runs again at approval and in the worker before pinning. It never silently
rewrites an approved spec.

**Delivering plans.** The mandatory region is the **canonical core**: the part of `ticket-to-merge`
from `implement` to the end of the run, i.e. the implementation (with the preview check), the review
loop, the pull request, the CI loop, the failure lessons, the human merge wait and the merge lesson.
`buildCanonicalCore()` constructs it with the template's own builders (`ticketToMergeCore`), so the
shipped template and the pinned core cannot drift; a test proves the two equal. The core contains no
quality-gate step: CI is the check, as in the template, and a gate step is refused outside the core.

- **Core nodes are exact.** Every core id is reserved. A node with a core id must deep-equal its
  canonical node (id, type, step, config, inputs, edges, status and presentation), after the spec
  parser's defaults. Nothing is repaired: a missing or edited core node is `CORE_MISMATCH`.
- **Two mutable points, both named.** The hook edge `waitForHumanMerge.onReceive` is `commitLesson`
  in the core and may name a post-region node. The guidance slot `implement.inputs.guidance` is
  absent in the template and may be exactly `{ from: 'context.planNotes' }`.
- **Free ends.** The **pre-region** is every free node reachable from the entry without passing a
  core node; it hands over by pointing at `implement`, the one core node a free node may name. In
  `ticket-to-merge` it is the validate phase. The **post-region** is every other free node, reached
  through the hook; it may point back only at `commitLesson`. An edge from a free node to any other
  core node is `CORE_ENTERED_MIDWAY`, an edge from a core node to a free node other than the hook is
  `FREE_NODE_IN_CORE`, a plan that starts inside the core is `CORE_ENTERED_MIDWAY`.
- **What a free node may be.** Pre-region: `agent`, `cond`, `set`, `terminate`, the human nodes, and
  steps of the free class (reads, planning, parsing). Post-region: `agent`, `cond`, `set`,
  `terminate` and the steps `parseAgentOutput` and `retrieveKnowledge`. Never a `signal`, a `fanOut`,
  a step that acts on the repository (`FREE_NODE_TYPE_DENIED`, `FREE_STEP_DENIED`).
- **What a free node may write.** Under `context.scratch.*`; in the pre-region also
  `context.planNotes`, `context.ticket` (only `nodes.<id>.output.text` of a `gatherTicketContext`
  step) and `context.successCriteria` (only `nodes.<id>.output.successCriteria` of a
  `validateContext` step; the whole output, or another field such as `ambiguities`, is refused).
  Anything else is `FREE_WRITE_DENIED`. The core never reads `context.scratch.*`. A free node may
  stamp only the statuses `PLANNING` and `VALIDATING_CONTEXT` (`FREE_STATUS_DENIED`): the dashboard,
  review fixes and PR feedback act on `AWAITING_HUMAN_MERGE`, and the core stamps the others.
- **Validation is mandatory.** Every path from the entry to `implement` passes a `validateContext`
  step (`VALIDATE_MISSING`), so the review is judged against criteria the platform extracted. When
  a generated pre-region runs none, `applySkeletonPolicy` attaches the shipped validate phase
  ahead of the core.
- **The post-merge region returns to the lesson.** No post-merge node may end the run `SUCCESS`
  (a `SUCCESS` terminate, a node with no `next`, or a `SUCCESS` failure route): `POST_ENDS_SUCCESS`.
  The only road to `done` is through `commitLesson`.
- **One transition cap.** The interpreter counts every node entry of a run against one cap
  (`DEFAULT_MAX_TRANSITIONS`), so a pre-region could decide where the core dies. The policy bounds
  the worst case of pre-region, core and post-merge region together
  (`TRANSITION_BUDGET_EXCEEDED`): a node on no cycle counts once, a node with `maxVisits` counts
  `maxVisits + 1`, an unbounded node on a loop counts once plus every entry of the bounded nodes of
  its loop. The core's share is derived from `buildCanonicalCore()` by the same function, and a
  test runs the real interpreter over the core to show the bound holds.
- **The one channel into the core.** The pre-region reaches the implementer only through
  `context.planNotes`, which the guidance slot binds. It cannot reach a review input, the success
  criteria, the ticket or the code result: those inputs are core and bound from fixed paths, and
  an agent is not a source for any context path except the plan notes.
- **Node ids** match `^[A-Za-z][A-Za-z0-9_-]{0,63}$` and are not `constructor` or `prototype`
  (`NODE_ID_INVALID`): the interpreter splits a write path on `.`, so an id with a dot could write
  another node's output. The restriction is in the policy, not in `validateSpec`, because existing
  team templates may legitimately use other ids.

The structural checks stay on and run over free nodes and core alike, so a defect in the core
comparison is not the only line: allowlisted step config and input bindings, write rules (a derived
path takes only the output of the step that fills it in the template: never an agent), failure
policy (`onFail` is never `warn`, `onError` is never `continue` on a stage or fix node), ordering by
dominance, code not changing after a check, the review verdict (a cond on
`nodes.<id>.output.approved == true` is the only approving route), merge-wait timeout never ending
`SUCCESS`, and bounded loops.

**Injection.** When the spec has no node with a core id, `applySkeletonPolicy` attaches the core
after the pre-region's sole leaf: the one `SUCCESS` terminate (ordinary edges into it are pointed at
`implement` and it is dropped, because the core ends the run itself) or the one step with no
`next`. Several leaves, or none, attach nothing and report `AMBIGUOUS_ANCHOR`. A spec that has any
core id is never repaired; its mismatch is reported.

**Output-only plans.** The mandatory nodes are one or more `agent` nodes, a human review of an
agent's output before the run can end `SUCCESS`, and a terminate. A `humanDecision` never counts as
the review, because every one of its options is a continuation and it cannot approve or reject; a
`humanApproval` whose `contextFrom`, or a `humanReview` whose `contentFrom`, is exactly
`nodes.<agent>.output` of an agent that precedes it, does (`HUMAN_REVIEW_CONTENT_UNBOUND` for a
subpath, a scratch path or no path). No `agent` node may run after the last human review on a path
that can still end `SUCCESS` (`AGENT_AFTER_REVIEW`), so nothing is written after the human looked.
What the run returns is what was reviewed: a `SUCCESS` terminate's `result` may carry literals, the
request, and the output of an agent that a review dominating that terminate showed
(`RESULT_UNREVIEWED` for a hidden agent's output, a scratch path or an expression).

The free ends draw only from a **step allowlist** maintained in code beside the registry. The
allowlist excludes `runContainerStep` and any authored command, `submitPrdWorkRequests`, `runTool`,
`postTicketComment`, `createTrackerItems`, `publishOutcome`, `writeOutcome`, `mergeBranches`,
`applyRecipe`, and every step that pushes or posts. `agent` nodes may not name an agent on
`NON_LAUNCHABLE_AGENT_KEYS` or one outside the requester's launchable set; `validateSpec` gains a
`NON_LAUNCHABLE_AGENT` error for it.

### 4. Generation

`generateWorkflowSpec` gains a `profile: 'run-plan'`: the catalog is the allowlist above, the agent list
is the requester's launchable agents, shell and MCP are off, and the intent is only the user's own text.
For Slack the intent is the verbatim message text and thread excerpt the user wrote, not a model
paraphrase. The repair loop hard-gates on `validateSpec` errors and the skeleton policy, and every loop
node needs `maxVisits` and `onExhausted`. Generation is an async job; its `JobWorkflow` is the existing
`WorkflowAuthorJobWorkflow` shape and is not replay-affecting, because the output is recorded as an
activity result and the run pins the resulting spec.

### 5. Router

A seeded `runPlanRouter` agent (cheap model) receives the intent and the id, name and description of the
templates the requester can launch, and returns ranked ids with reasons and a "none fits" flag. Output
is intersected with the launchable set, so injected template text can influence only ordering. It is
named in the agent roster docs, `BUILTIN_MODELS`, `PREVIOUS_DEFAULT_MODEL_SPECS` handling and
`NON_LAUNCHABLE_AGENT_KEYS`.

### 6. Abuse and cost controls

Registry settings: plans per user per hour, pending plans per user, and a per-plan generation attempt
cap (default 3). Generation and routing spend is recorded against the team's budget. A sweeper expires
`PENDING` plans and deletes expired and rejected ones after a retention window.

### 7. Surfaces

- Gateway: `POST /run-plans`, `GET /run-plans/:id`, `POST /run-plans/:id/approve`,
  `POST /run-plans/:id/reject`. Every route has an `assistantPolicy` entry; creating is `confirm`, and
  approving is `never` for the assistant because it is the human decision.
- Web: a "Describe the goal" mode on `/start` showing the router's matches beside "Generate new", then
  the plan preview (outline, cost with unpriced nodes listed, mandatory nodes marked, warnings,
  pinned agent versions) and an Approve button.
- CLI: `auto-swe plan create|show|approve|reject`, and `run --describe "<goal>" --yes`.
- Slack: the channel assistant records a plan intent; fixed code creates the plan and posts it with an
  Approve button that only its creator can use. The channel path requires a linked, active ENGINEER with
  repository reach, as agent runs do.

### 8. Obligations

A hand-written `RunPlan` migration (see the `prisma-pgvector-hnsw` skill, `db:deploy` only) with an
owner-not-null CHECK; docs for the feature with a `## Limitations` section; the agent roster and model
docs for `runPlanRouter`; an `upgrade-notes.md` entry only if a deployment must act. PRs opened by a
planned run are marked so `evaluatePullRequest` skips `auto` mode for them. The spec moves to
`docs/history/` when the work lands.

## Phasing

1. Shared: step allowlist, skeleton policy with dominance checks, `NON_LAUNCHABLE_AGENT` lint, cost
   estimate helper, and the adversarial eval set (intents with expected graph properties, including
   hostile ones that try to disable mandatory nodes).
2. Data and worker: `RunPlan` model and migration, "Planned Run" system template, spec pinning in
   `createWorkflowRun`, approval re-checks, `run-plan` generation profile, planned-run PR marking.
3. Gateway: plan routes, quotas, expiry sweeper, assistant policy, router agent and ranking.
4. CLI and API documentation.
5. Dashboard mode.
6. Slack.

## Limitations

- The policy pins the core exactly; it does not judge whether the pre-region or post-region is a
  sensible way to do the task.
- Text an agent writes in the pre-region can become the implementer's guidance through
  `context.planNotes`. This is the one channel from free nodes into the core, and the policy cannot
  judge what the text says. The implementer receives it under the requester-guidance heading, and a
  prompt-injected ticket or knowledge-base page can steer the drafting agent. The review network,
  CI and the human merge still judge the result; the notes cannot touch what they are judged
  against.
- The canonical core has no quality-gate step, so a delivering plan has none; CI is its check.
- The transition bound is an over-approximation, so a plan whose real worst case fits can be refused,
  and it is computed against the default cap. An operator who pins a lower cap through the
  interpreter bounds can still have a plan that passes the policy die at that lower cap.
- Validation must run, but the policy does not require that its criteria are copied into
  `context.successCriteria`; a plan that validates and never copies them is reviewed against none, as
  a run whose validation found nothing is. The ticket is likewise optional.
- Only the `result` of a `SUCCESS` terminate in an output-only plan is bound to reviewed output. A
  `FAILED` or `TIMED_OUT` ending may carry other values, and a human who approves has judged the
  agent's whole output, not a particular field of it.
- A free node's status is limited to two words, so a generated plan cannot show progress beyond
  `PLANNING` and `VALIDATING_CONTEXT`.
- The implicit context reads in the worker are enumerated by a test that scans its source for the
  forms in use today (`lookupPath(ctx, '…')`, `ctx.context.<key>`); a read spelled another way is
  not seen until someone adds it to that list.
- A plan with an unusual shape is refused rather than adapted: the generator must produce a
  pre-region that ends in one place, and the core's ids are not available for its own nodes.
- Cost estimates use role defaults and a fan-out guess; unpriced nodes are listed, not costed.
- A plan is approved against agent versions and settings at that moment; a change afterwards makes the
  plan unapprovable and the user must regenerate it.
