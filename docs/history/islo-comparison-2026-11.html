Islo vs auto-swe

Islo (islo.dev) sells a governed sandbox-and-pipeline platform for AI software work. auto-swe is a durable, governed multi-agent workflow platform. This page compares what each offers, with auto-swe viewed as it runs in production: on Kubernetes, not just Docker.

Islo side: public marketing site + docs.islo.dev only auto-swe side: this repository's own docs Not a hands-on trial of either product
Verdicts across the comparison rows (unweighted)

Summary

The two overlap in intent but start from opposite ends.

1 · DIFFERENT CENTRE OF GRAVITY

Sandbox-first vs orchestration-first

Islo leads with the isolated machine and an egress gateway as the product. auto-swe leads with durable, replayable orchestration, review, memory and governance, and treats isolation as a hardening layer beneath it.

2 · ISOLATION IS CONFIG, NOT DEFAULT

Pods by default; VMs by choice

On Kubernetes an auto-swe workspace is a hardened pod sharing the node kernel. A Kata RuntimeClass gives VM-per-pod, which is roughly Islo's headline claim, but it is opt-in and verified by name only.

3 · THE REAL GAP IS CAPABILITY

What the Kubernetes backend cannot do

Shell and container steps are unavailable there, workspaces have no persistence or snapshots, and the worker is a single replica. Egress is host-level only, with no path or method rules and no generic credential injection.

Kubernetes deep dive

What auto-swe's production substrate actually gives and withholds. Applies when WORKSPACE_BACKEND=kubernetes.

Isolation ladder

Hardened pod

PodSecurity restricted, non-root with explicit UID, all capabilities dropped, no privilege escalation, RuntimeDefault seccomp, no service-account token, no host namespaces or paths, Guaranteed QoS, kubelet-enforced activeDeadlineSeconds (default 24 h).

DEFAULT
NetworkPolicy + admission policy

Default-deny ingress; egress only to DNS, the worker's proxy ports and the public internet (never metadata or private ranges). The worker proves enforcement at boot with a probe pod and refuses to start otherwise. A ValidatingAdmissionPolicy hardens the namespace on Kubernetes 1.30+.

DEFAULT
Restricted / blocked egress lock

The pod is relabelled onto a narrow policy and the worker proves the lock from inside the pod with TCP connect checks. restricted adds a host allowlist through the egress proxy.

POLICY
Sandboxed runtime (Kata, VM-per-pod)

Selected with K8S_WORKSPACE_RUNTIME_CLASS; K8S_REQUIRE_RUNTIME_CLASS=true makes the worker refuse to start without it. Needs KVM or nested virtualization on the nodes. The check validates the returned RuntimeClass name, not that the handler is really a VM.

OPT-IN
Per-workspace snapshots / persistence

The working tree is an emptyDir that dies with the pod. The only “pause” is SIGSTOP, used to quiesce for copy-out.

NOT AVAILABLE

Where credentials do and do not go

Kept out of the workspace pod

Agent in pod→model proxy (worker)→provider API

The model proxy is mandatory on this backend; the worker refuses to boot without it, so the provider key never enters a pod.

npm / pip / Go / Maven→registry proxy→upstream

Each workspace gets a per-workspace token; in lockfile mode only committed name@version pairs resolve.

Git credentials ride exec stdin and a per-pod Secret with an ownerReference; none appear in argv or the apiserver audit log.

What the proxy cannot do

Agent in pod→egress proxy→allowlisted host

Host-level allow/deny only (exact host or *.domain). CONNECT tunnels are not TLS-intercepted.

✕ no path / method rules✕ no intent judge✕ no generic credential injection

Each proxied request or tunnel is recorded as a metadata row (host, port, bytes, blocked flag, no bodies) in the database. There is no SIEM export.

Limits specific to the Kubernetes backend

LimitConsequence
Shell steps, container steps and shared-volume sidecars are unavailable (WORKSPACE_BACKEND_UNSUPPORTED) Templates that rely on them cannot run. Preview-service sidecars do work. This is the closest analogue to Islo's script stages, and it is missing.
Worker must be a single replica; proxies hold per-workspace state in memoryCaps horizontal scale and makes the worker a restart-sensitive component.
Service sidecars have a fixed 512 MiB / 1 CPU / 4 GiB ephemeral storageA heavier service is killed, and exceeding storage evicts the whole pod, workspace included.
No per-pod PID cap; relies on the node pool's podPidsLimitAn operator must set it on the node pool.
Runtime and network gates run only at worker bootChanges to the CNI, RuntimeClass or admission policy after boot are not re-verified until restart.
Per-pod egress policy is address-based (/32, /128)A host whose addresses change mid-run becomes unreachable.
DNS stays open to kube-dns in a locked podA low-bandwidth exfiltration channel unless a restrictive DNS server is added outside the manifest.
The worker holds create on NetworkPoliciesAdditive policies mean a stolen worker token could open egress for a pod. A ValidatingAdmissionPolicy mitigates this on Kubernetes 1.30+ only.

Opportunities

Where closing a gap would change the comparison most. These are directions, not commitments.

Make VM isolation the verified default

Provision Kata nodes, set a RuntimeClass, and enforce it with K8S_REQUIRE_RUNTIME_CLASS=true. Strengthen the check from a name match to proof the handler is a VM.

Mostly cluster work · needs KVM-capable nodes

A request-aware egress gateway

A TLS-terminating proxy built on the existing egress proxy would add path and method rules and generic credential injection, and would let outbound calls be exported to a SIEM.

New component · security-sensitive

Close the non-agent-step gap

Give shell and container steps a Kubernetes implementation, so templates are portable across both backends.

Driver work · shared-volume semantics are the hard part

Persistent, warm environments

Snapshotting a prepared workspace (dependencies, database state) would remove repeated setup, which is the strongest part of Islo's pitch.

Design needed · interacts with the security model

Enterprise sign-in and audit export

SAML and SCIM, and SIEM-friendly audit export, are listed gaps in the repository's own enterprise-readiness map.

Scoped issues already described in docs/enterprise-readiness.md

Evidence & caveats

Treat the Islo column as “as stated”. It comes from Islo's marketing site and docs overview, not from running the product. Certification badges (SOC 2 Type II), customer counts, dashboard numbers and funding were not independently verified. The auto-swe column comes from this repository's documentation and describes intended behaviour; its own docs state that the unit suite runs against mocked Docker, Temporal and LLM calls, and that gates such as the runtime and network checks run at worker boot only.
